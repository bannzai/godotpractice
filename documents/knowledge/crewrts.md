# こもれび回収隊の実装知見

## 状態と移動

ゲーム進行は Expedition autoload に集約した。描画はその座標と状態を読むだけにし、selfcheck で同じ移動・投擲・笛の命令を使って通常ステージをクリアできるようにした。仲間の状態は追従・待機・投擲・運搬・攻撃。必要人数は実人数で判定し、青の仲間は運搬速度、朱の仲間は攻撃力で区別する。

円柱障害物の手前では接線方向に迂回する簡易経路を使う。リーダーの位置制約、投擲の着地点、運搬物と仲間の通行制約を同じモデルに集約する。到着処理には delivered を持たせ、報酬の二重取得を防いだ。

投擲の最終フレームでは sin(PI) の丸め誤差が高さに残った。終了時に着地点を明示代入してから対象へ取り付けることで、着地条件を安定させた。

## 素材と表示

庭・ロボット・結晶は低分割のプリミティブで生成し、材質を共有する。初回実装では日本語フォントに静的 TTF の M PLUS Rounded 1c を同梱した。見た目の特色化ラウンドでは Klee One へ交換した。各 export preset の include_filter に OFL.txt を追加し、OS フォントへ依存せず Linux CI と Web でも同じ日本語を表示する。

BGM と SE は外部サンプルなしの数式合成。scripts/dev/generate_audio.py で冪等に再生成できる。BGM の残響を先頭へ折り返し、WAV のループ終端をサンプル数に合わせる。

## 検証で確認した点

- selfcheck は境界値、種類差、運搬人数不足、再集合による運搬中断、戦闘、敵の運搬物化、報酬一回性、時間切れ、全滅、通常ステージでのクリアを検査する。
- screenshot はタイトル・プレイ・投擲・笛・運搬・戦闘・成功・失敗を撮影する。結果画面の撮影だけは決定的な状態を投入し、クリア到達の正しさは selfcheck の操作経路で別途検証する。
- サンドボックス内では Godot の user:// ログのローテーションでクラッシュした。ゲーム内の tmp への --log-file 指定で回避した。共有 Makefile への同方式の適用を提案する。
- headless --quit で開始した WAV 再生が終了時にリークしたため、音を出さない headless では BGM を開始しない。描画付き起動では BGM を開始し、終了時に停止する。

## 判断と残りの検証

独自造形・独自音声で進め、追加の外部 API は導入していない。ゲーム仕様に関する判断待ちはない。ローカルの検証結果は以下。CI の最終結果と成果物確認は PR の検証欄に記録する。

## skill への改善提案

Godot の skill に「固定刻みモデルによる通常ステージの操作経路検証」「着地座標の確定」「サンドボックス内ログパス」「日本語フォントのライセンスを export に含める検査」を取り込むと、他ゲームでも再利用できる。共有 skill は本作業では変更しない。

## 検証環境に関する追加の知見

録画の `--quit-after` による即時終了では、再生中の WAV が終了時にリークした。録画用 SceneTree で終わりの6フレーム前に音声を停止する。性能計測・通常のウィンドウ終了では停止後に0.15秒を確保する。撮影は 0.15 秒の待ちが CI で足りない回があったため、時間ではなく WAV の解放を観測して待つ (後述「撮影の終了時のリーク (CI の flaky) と解放の観測」)。警告行を除外して成功にするのではなく、終了前の解放を行う。関連する Godot の報告: https://github.com/godotengine/godot/issues/76745 。

macOS の export は editor_settings を保存する。サンドボックス外への書き込みを避けるため、tmp 内へコピーしたバイナリに `_sc_` を置く self-contained mode を使用した。コピーしたバイナリには ad-hoc 署名を行い、既存 export_templates へは読み取り用シンボリックリンクを置いた。元の Godot.app やシステム設定は変更しない。仕様: https://docs.godotengine.org/en/4.7/classes/class_editorpaths.html 。既存の macOS zip を Godot がゴミ箱へ動かそうとするため、再生成可能な zip は export 前にゲームの build ディレクトリ内で除去する。

`documents/knowledge/crewrts.md` も変更すると、現行の changed-games.sh は共有変更と扱い全9ゲームを検証する。知見文書はゲームコードに影響しないので、司令塔への改善提案としてゲーム別文書の変更をCI対象の絞り込みに反映するとよい。共有スクリプトは本作業では変更しない。

入力統合検証は headless に加え macOS の実ウィンドウでも成功した。左右のマウス操作、照準の移動、F11 の全画面・ウィンドウ復帰を確認した。照準は InputEventMouseMotion.position を保持して計算し、入力イベントの座標とOSからのポインター再取得が混在しないようにする。

## 第 2 ラウンド (品質向上)

### 方針と仕様の維持

独自の絵本風 3D とし、濃緑・クリーム・朱・青・金で庭と HUD の配色を揃えた。ゲーム進行の正は既存の Expedition のまま。既存仕様にないボス・NPC・レベルアップは追加せず、投擲・運搬・笛・戦闘・回収・退場の表現を強化した。戦闘曲は既存の甲虫との遭遇に使う。

### 個別モデルと部位アニメーション

`assets/models/` に隊長、朱隊員、青隊員、甲虫、トゲ甲虫、結晶 3 種、回収基地を独立したシーンとして置いた。朱は角形の肩装甲とハンマー、青は長い受信耳と丸い背嚢、隊長はつば帽子と通信アンテナで識別する。UI の隊員画像とキーアートも実モデルの装備に合わせた。

モデルのゲーム座標を持つルートと、アニメーションで動く `Rig` を分けると、移動の同期で手足の動きが上書きされない。`AnimationPlayer` に待機・移動・攻撃・被弾・退場・投擲・運搬・笛のクリップを用意し、種類別に歩幅や顎の動きを変えた。一回の被弾や投擲が終わると、それまでの移動状態へ戻す。各クリップに基準姿勢のトラックを含め、前の動作の傾きや縮小を持ち越さないようにした。比較撮影では待機姿勢だけで余白を決めず、歩行時のアンテナ・被弾時の牙・退場時の脚が届く範囲まで確認する。撮影用モデルを同じ比率で縮め、行の見出しと分離した。昆虫の顎は頭部の子にし、頭を傾けても付け根が離れない構成にした。

個体ごとにノードと装備を持ち、同じ形のメッシュ・材質と種類別の AnimationLibrary は再利用する。見た目の独立性と描画資源の共有は両立できる。ただし、個別部品を増やした効果を第 1 ラウンドの性能値から推定せず、30 体の実描画で計測し直す。

### 庭・演出・HUD

地層、手前の草花、樹木、外周の遠景を高さと距離を変えて配置し、カメラ移動で奥行きが見える庭にした。草 380 本は MultiMesh を使う。GL Compatibility を維持し、環境光と方向光の影で形を見せる構成にした。

`CPUParticles3D` は投擲、笛、被弾、撃破、回収、隊員喪失に使い、一回放出後の `finished` で解放する。波紋と数字は Tween 終了時に解放する。継続攻撃のダメージは 0.28 秒ごとにまとめ、数字と打撃音を重ねすぎない。撃破・隊員喪失には 0.06 秒のシミュレーション停止と小さな画面揺れ、回収・喪失には HUD のフラッシュを加えた。演出はモデルの状態差分と一度だけ消費するイベントから発生させ、人数・HP・報酬を変更しない。

HUD は Theme リソースと同梱フォントを使い、回収進捗・残時間・隊員カードを画面の隅へ置いた。ボタンの拡縮、画面のフェードとスライド、数値のカウント、出来事の通知を追加した。表示数値の Tween を始めるのはモデルの値が変わった時だけとし、毎フレームの refresh で再起動しない。結果画面は遷移の途中を完成画面として撮らないよう、撮影前に 0.75 秒待つ。

### 素材生成の向き不向き

今回使ったのは独自の手続きモデル、SVG、数式合成音声で、外部のモデル・画像・録音は追加していない。既存の M PLUS Rounded 1c と OFL は引き続き同梱し、各素材の生成方法と帰属を `assets/CREDITS.md` に記録した。

- プリミティブの組み合わせは、装備や輪郭をコードで調整し、リグの部位を明示する用途に向いた。部品が増えるほど造形と関節位置の調整が必要になり、細かな表情や有機的な動きは別途作り込む必要がある。
- SVG はロゴ、隊員アイコン、結晶・太陽・笛、庭のキーアートのような輪郭が明確な絵に向いた。各ファイルを独立させると配色や装備の修正を照合しやすい。文字は SVG に埋めず Label で描き、日本語フォントの差を避けた。今回の表現は平面的な挿絵であり、立体モデルのアニメーションを代替するものではない。
- 音の数式合成は、固定 seed で同じ WAV を再生成し、場面ごとのテンポ・音色・音域を分ける用途に向いた。音量や波形を検査できても、聴き心地の判断は残る。画像生成サービスや外部素材との比較検証は行っていない。

### 音声と終了処理

BGM はタイトル・庭・戦闘・成功・失敗の 5 曲、SE は笛・投擲・回収・撃破・隊員喪失・打撃・切替の 7 種にした。木質の打音、弦、撥弦、息成分を含む音、低音、キック、シェーカーを倍音・包絡・ノイズで合成する。BGM は 2 台の AudioStreamPlayer を交差フェードさせ、危険が去っても 2.4 秒は戦闘曲を保つことで頻繁な切替を避けた。

終了時は再生を止めるだけでなく、フェードを止めて各 player の stream と保持している音源参照を解放する。通常のウィンドウ終了では停止後に 150 ms 待つ。`--quit-after` はウィンドウ終了通知を通らないため、終了 8 フレーム前に停止して音声スレッドの処理を待つ。短い起動検証と headless では音声を開始せず、即時の SceneTree 終了も `_exit_tree()` で扱う。ネイティブ終了時の待機を Web に持ち込まない。150 ms は今回の終了経路で検証した待機値であり、すべての端末に対する保証ではない。

`Makefile` の import は `tmp/.gdignore` と `build/.gdignore` を作る。撮影画像・録画・エクスポート成果物を次回 import の入力にしないため、生成物が増えてもゲーム素材と混ざらない。import も exit code に加えてログ全文の WARNING / ERROR を検査する。

### 実描画と Web の検証で得た知見

- 第 2 ラウンドの性能は、M4 Max / OpenGL Compatibility / 1280×720 / V-Sync 無効で、仲間 30 体・敵 2 体の 600 フレームが平均 151.0 fps、p95 8.74 ms。exit 0、警告なし。前段の第 1 ラウンドの値とは別の実測であり、他の端末の性能を保証しない。
- 描画付きの入力 integration でも、キー・マウス・ゲームパッドの InputEvent、F11 の全画面とウィンドウ復帰、休憩中のアニメーション停止、再出発時の演出リセットが成功した。実物ゲームパッドの操作感を測ったものではない。
- 通常の `run` をウィンドウ終了経路で終了した場合と、メインシーンの `--quit-after 180` がともに exit 0。検証ログ全文に ObjectDB・使用中 resource のリーク警告や WARNING / ERROR がないことを確認した。
- ローカルと CI の PNG 19 枚、起動録画の末尾、28 秒プレイ録画の 2 秒間隔 14 枚と最終フレームを目視した。キャラの装備接続・文字・HUD・結果からタイトルへの遷移終了を確認した。
- webtunnel の caller はポート 8000 を指定する。参照手順のサンプルにある 8080 をそのまま使うと接続拒否になるため、実際の workflow の設定を読む。`--software-webgl --ref polish/crewrts` で WebGL2 が有効になり、タイトル・プレイ・投擲・結晶回収・増員・通常の 5 分経過による結果表示・タイトル復帰を実入力で確認できた。撮影後は `down crewrts` で専用セッションを終了した。
- runner の SwiftShader は 640×360 でも約 2 fps で、ローカルの GPU とは挙動が異なる。状態遷移と入力経路の確認には使えるが、滑らかさの判定はローカル録画と実描画性能計測で行う。待機区間は 320×180 へ縮め、証拠撮影時に元の領域へ戻す運用にした。Web の通常の 5 分制限は変更していない。
- PR #33 の検証欄に、最終 CI の run、Web の結果画面と終了後の録画、アップロードした各証拠画像を集約する。画像が変わる変更を加えた場合は該当する撮影を更新する。

### 撮影の終了時のリーク (CI の flaky) と解放の観測

PR #23 の CI で `screenshot-and-movie (crewrts)` が 1 回だけ、撮影 19 枚の成功後の終了時に「2 ObjectDB instances were leaked」「1 resources still in use」を出して失敗した (再実行は成功。 https://github.com/bannzai/godotpractice/issues/24 )。ローカルで撮影と同じ起動 (`--audio-driver Dummy`・描画付き) に `--verbose` を付け、停止直後に終了させて再現した。リークしたのは再生中だった BGM の `AudioStreamWAV` (`title.wav` / `garden.wav`) とそれを参照する `AudioStreamPlaybackWAV` の対で、CI で出た 2 Object + 1 resource は playback 1 つと WAV 1 つに一致する。

原因は待ち方にある。`AudioStreamPlayer.stop()` は再生を即座には捨てず、音声スレッド (Dummy ドライバも独自スレッドで混合する) が次の周期でフェードアウトして削除待ちにし、その後のメインスレッドのフレーム (`AudioServer` の更新) で playback と WAV の参照を手放す。この完了は秒数ともフレーム数とも一致しない。ローカルの実測では停止から解放まで 20〜60 ms で、60 fps なら 2〜7 フレーム、120 Hz の画面では 10 フレームでも足りない回がある。CI の llvmpipe では逆に 1 フレームが長い一方、音声スレッドが描画スレッドに押されて 0.15 秒では周期が回らない回がある。

撮影 (`scripts/dev/screenshot.gd`) は停止後に `AudioDirector.is_released()` が true になるまで `process_frame` を待つ。`AudioDirector` は読み込んだ全 WAV (BGM 5 曲・SE 7 種) の `weakref` を持ち、`stop_audio()` で自前の参照 (`_streams` と各 player の `stream`) を捨てた後、weakref がすべて null になった時点を「音声スレッドが playback を手放して WAV が解放された」と判定する。`load()` のキャッシュは参照を保持しないため、解放されれば weakref は null になる (実測)。10 秒以内に解放されなければ `push_error` と `quit(1)` で明示的に失敗させ、リーク WARNING に頼らない。録画 (`movie.gd`) は Movie Maker が音声をフレームごとに同期で混合するため終了 6 フレーム前の停止で決定的に解放され、変更していない。通常のウィンドウ終了 (`NOTIFICATION_WM_CLOSE_REQUEST`) と `--quit-after` の 0.15 秒待ちも変更していない (CI の検査対象ではない。同じ観測で置き換えられる)。

共有物への提案: godot-development skill の雛形 `scripts/dev/audio_stop.gd` と `screenshot.gd` は停止後に 0.2 秒待つ方式のままで、同じ flaky が他ゲームでも起こり得る (issue #24 のコメントで cardbattle / deckrogue / fighter / platformer / survivors の `--quit-after` 終了でも同じ警告を実測)。雛形側でも WAV の weakref による解放の観測に置き換えるとよい。

## 手直しラウンド (見た目の特色化)

### 分かりにくかった原因と効いた表現

前の画面はタイトルから庭へ直接入り、画面下の共通操作ガイドに多数のキーを並べていた。初めて見る人には、出発前にどこへ行くのか、何を達成するのか、どの対象を選べるのかが分からない。プレイ中も照準と対象の関係、運搬にあと何人必要か、操作できない理由を操作一覧から推測する必要があった。四隅の整ったパネルと手続き SVG は情報を揃える一方、他ゲームと同じ画面構成に見える原因にもなった。

水彩の島全体を一枚絵で見せ、その上に「選べる庭」「橋がなく選べない丘」「霧で進めない沼」を直接書いた。選択中の庭には、結晶数・仲間数・体験内容・次に操作ノートが開くことを添え、主ボタンを一つに絞った。初回だけ開く3頁の操作ノートは移動、投擲と運搬、笛と隊列の順に説明し、読んでいる間は時間と操作を止める。スキップも同じ頁に置いた。プレイ中は対象を金色の輪で強調し、対象のそばと右側の鉛筆メモに必要人数・投げた結果・仲間不足の理由を表示する。画面下の共通操作ガイド行は廃止した。入口では地図、初回は短い練習、通常時は対象に応じた一手だけを示す分割が、情報量を減らしながら次の行動を明確にした。

### 生成画像と水彩トゥーンの手順・向き不向き

`game-asset-search` のライセンス確認手順で Klee One の Google Fonts 配布元と OFL 1.1 を確認し、フォント本体・著作権表示・ライセンス全文を保存した。画像は `image_gen` で、文字と既存作品を含めない条件を明記して、紙の繊維、水彩顔料のにじみ、3地域を持つ島の絵地図を別々に生成した。生成時の要点と利用規約は `assets/CREDITS.md` に残した。UI の文字や選択枠を画像へ焼き込まず Godot 側で重ねることで、生成画像内の不正確な文字を避け、操作状態も後から変更できるようにした。

紙の繊維は PanelContainer の StyleBoxTexture と全画面の薄い重ねとして使いやすく、Klee One と合わせるだけでノートの統一感が出た。島の一枚絵は地域の色・道・海岸線を一度に作れるため、手続き SVG より短い実装で背景の情報量を大きく増やせた。一方、島の道とボタン座標は構造化データではないため、マーカー位置は原寸 PNG を見て手で合わせる必要がある。顔料にじみ画像は単体では強い色を持つが、小さい3D部品へそのまま貼ると色と可読性を壊す。ワールド座標を混ぜた UV、低い混合率、元の識別色を保つ tint、紙の明度だけを使う構成にすると、輪郭線なしのトゥーン照明を残したまま面ごとの揺らぎとして使えた。遠景では差が弱くなるため、原寸テクスチャだけでなく実カメラのスクリーンショットで判定する必要がある。

画像生成は紙や植生の偶然のむら、複数地域を一枚にまとめる絵に強い。生成待ちとバイナリ容量が増え、同じプロンプトから同一ピクセルを再生成できず、局所的な位置・形・配色の修正もしにくい。前ラウンドの手続き SVG は git diff で変更を追え、色や座標を正確に直し、同じ出力を再生成できる反面、コードで指定した形以上の質感が出ず、複数ゲームで同じ図形語彙になりやすかった。今回は、状態を持たない紙・にじみ・背景を生成画像、状態と正確な文字を Godot、識別が必要な3D形状を既存プリミティブとシェーダに分けた。この組み合わせなら生成画像の長所を使いながら、操作表示とゲーム進行を画像へ固定せずに済む。

検証では生成した3枚を原寸で目視し、Godot の import、GL Compatibility の shader compile、headless のロジック検証、1280×720 の代表画面24枚を確認した。紙・地図・水彩にじみは外部素材を混ぜない生成物、フォントは OFL 1.1 として、入手元、生成手段、プロンプトの要点、加工内容を分けて記録した。環境音は固定式で風・葉音・鳥声を合成し、外部録音を使わず冪等に WAV を再生成する。波形とゲーム内の再生経路は機械検証できるが、主観的な聴感は音声入力のないエージェントだけでは判定できない。

### 探検ノート UI を Godot で作る時のハマりどころ

- `Control.size` を指定しても、子のフォントサイズ・余白・ボタンの minimum size の合計が大きいと `PanelContainer` は指定値より広がる。地図のプレビューは計算上の下端だけでなくスクリーンショットで実際の下端を確認する。
- 画面本体とは別にルートへ置いた紙メモは、親画面を非表示にしても残る。複数の紙を一画面として扱う場合は同じ親へ入れるか、画面遷移時にすべての表示を明示的に切り替える。
- ローカルでは同梱フォントにない記号を OS フォントが補完し、Web だけ豆腐になる場合がある。Klee One にない曲がった矢印は収録済みの直線矢印へ置き換えた。`hb-shape <font> '<使用文字>'` の `.notdef` と Web の実画面を確認すると、ローカルのフォールバックに隠れた不足を検出できる。
- 状態変更の同じフレームで、チュートリアル頁の更新より先に旧画面のフォーカスを解放すると、表示は出ても Enter / パッド A が反応しない。画面状態を先に確定し、その後に頁内容と主ボタンのフォーカスを更新する。この経路は実 `InputEvent` の integration で検査する。
- 3D 空間の `Label3D` はカメラ端で切れたり、対象の個数表示と重なったりする。通常の案内は画面座標の鉛筆メモへ置き、対象を選んだ時だけ短いラベルを対象付近へ出す。重要な必要人数は鉛筆メモにも重ねて、3D 投影だけへ依存しない。
- 初回チュートリアルのフラグを画面側だけに持つと、リトライとタイトル復帰で表示条件がずれる。進行モデルに `tutorial_seen` と現在頁を持たせ、チュートリアル中は物理処理と未処理入力の両方を止める。

### skill 化の候補

`game-asset-search` には、生成背景へ文字を焼き込まず状態表示をエンジン側へ残す判断、プロンプト・生成手段・加工内容を CREDITS に記録する雛形、生成画像と手続き素材を「偶然の質感」「局所編集」「再現性」「容量」で比較するチェックを追加できる。`godot-development` には、Container の実 minimum size、ルート直下の複数紙の表示切替、状態遷移と `grab_focus()` の更新順、`Label3D` と画面 UI の役割分担をスクリーンショットと実入力で検証する項目を追加できる。共有 skill は本作業の変更範囲外なので変更しない。

### 本番に向けて足りない道具

今回の比較撮影を再利用し、モデルごとの関節、装備の接続、退場時の縮小をまとめて確認する道具があると造形の修正を速められる。画面キャプチャと録画から同じ時刻のフレームを並べ、前のコミットとの差を見られると、静止画だけでは分からない動作の連続性も追いやすい。

音声は波形検査に加え、場面の交差フェードと SE の重なりを実際に聴ける確認経路が必要になる。性能は 30 体追従だけでなく、戦闘・運搬・パーティクルが重なる場面を同じ条件で測れる記録があると判断しやすい。これらは本ラウンドで追加した機能ではなく、今後の道具への改善提案として残す。
