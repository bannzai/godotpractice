# cardbattle の実装と検証

## 手直しラウンド (見た目の特色化)

### 着手時の観察と制作方針

変更前のタイトル・遊び方・初手・対戦中をゲーム内の撮影シナリオで確認した。決闘ルールと入力は成立している一方、タイトルは天体背景、対戦中は上部のライフ HUD・右の詳細サイドバー・下部の手札と操作ボタン列で構成され、木の机を囲むカード遊びには見えにくかった。次の操作は右下の短いメッセージと遊び方モーダルに分散し、選べないカードを見ただけでは理由が分からなかった。CPU 連戦を選ぶ地図も存在しなかった。

このラウンドでは、カード定義と決闘ロジックを維持したまま、表示層を金・深緑・象牙のアール・ヌーヴォー様式へ変える。画像生成で全30カードの絵と共通の装飾枠を制作し、既存の手続きSVGは前ラウンドとの比較資料として残す。5動作は生成した完成原画を1枚のセルとして移動・回転・拡大する方式へ作り直す。タイトルから額縁入りのトーナメント表を経て決闘へ進み、決闘中は木製机を俯瞰する構成にする。操作案内の共通行を廃止し、選択可能・選択不可の理由と選択後の結果予告をカードや場の上へ直接表示する。初回は盤面に重ねた短いチュートリアルで、フェイズ進行・手札の使用・攻撃対象の順に案内する。

### 分かりにくさの原因と効いた表現

以前の画面では、カードを選べない理由がルールの内部にだけあり、カード自身は押してみるまで結果を返さなかった。フェイズを進めるボタンも「次のフェイズ」とだけ表示し、押した後がメイン・バトル・相手の手番のどれかを事前に判断できなかった。タイトルから直接決闘へ入るため、連戦の現在地もなかった。画面下のキー一覧は操作装置の説明にはなっても、その場で選ぶ対象や次の目的の説明にはならなかった。

有効だったのは、選べるカードの金縁を脈動させ、選べないカードの原画上へ「メインで使用」「召喚は使用済み」「破壊対象なし」などの理由を臙脂の帯で重ねる表現だった。攻撃役を選んだ後は、相手カード上に「破壊する」「反撃 900」「相打ち」の緑帯を出す。フェイズボタンも「封蝋を押す　バトルへ」のように遷移先を含めた。タイトルではデッキ選択の行き先を「大会表へ」と書き、勝敗画面では「次の対戦札を開く」を最も大きくした。固定の操作ガイド行を置かなくても、場面ごとの対象と結果を近接させる方が次の一手を説明できた。

初回指南は3枚だけにし、フェイズ進行ボタン、手札、盤面の順に金の矩形で実物を囲む。指南の紙面は右側の記録欄へ置き、決闘盤を隠さない。各段階から閉じられるため、既にカードゲームを知る人はすぐにプレイへ移れる。

### image_genによる32画像の制作

OpenAIの組み込み`image_gen`へ参照画像なしで文章を渡し、24体のモンスター、6種の魔法・罠、共通装飾枠、木製卓上を個別に生成した。生成時はカード原画1448×1086のRGB PNG、装飾枠1060×1484のRGBA PNG、卓上1672×941のRGB PNGだった。実表示に対して過剰だったため、原本を目視した後、リポジトリへ置く画像は原画724×543、枠530×742、卓上1280×720へ縮小して合計容量を87MBから25MBへ減らした。各カードを別の呼び出しにし、カードIDをそのままファイル名へ対応させた。プロンプトには共通して、1900年前後のアール・ヌーヴォー印刷物、金箔、深緑、流れる植物曲線、文字・ロゴ・カード枠を描かないことを含め、個別の人物・獣・静物・姿勢・時間帯を追加した。

当たりだったのは、30枚を1枚にまとめて生成せず、被写体と構図を1枚ずつ指定した方法だった。前半を暖色の温室、後半を青銀の夜園に分けても、人物・獣・武具・花を個別に指定したため、SHA-256の重複は0件で、一覧でも全カードを識別できた。共通枠を別の透過画像にしたことで、金の蔓・百合・孔雀羽の意匠を揃えつつ、原画の差を残せた。生成結果を破棄して再生成した画像は0件だった。

想定どおりにならなかった点は、縦長カードを意図しても原画が4:3で返り、完成カードの比率と一致しなかったことだった。人物の全身をそのまま縮小すると余白が増えるため、Godotの`STRETCH_KEEP_ASPECT_COVERED`で共通枠の窓へ切り抜いた。上下左右の端に重要な顔や武器を置かない指示と、実カード寸法での目視が必要だった。生成PNGは手続きSVGより容量が大きく、Gitのテキスト差分では内容を確認できないため、30枚の一覧、実カード、タイトル、トーナメント表の4種類で見た目を確認した。

手間の中心は32回の生成そのものより、ファイル名との対応、寸法・色形式・透過の確認、30枚の一覧化、ゲーム内での切り抜き確認だった。原画30枚のハッシュ一意性、装飾枠の中央と四隅の透過、各PNGのロードを自己検証へ入れた。生成物には根拠なくCC0などのライセンスを付けず、生成手段、入力画像なし、プロンプトの要点、利用条件を`assets/CREDITS.md`へ記録した。外部素材はZen Antiqueだけで、Google Fontsから取得したフォントと同じ配布元のOFL 1.1全文を同梱した。

前ラウンドの手続きSVGは、再生成が決定的で、ソース差分を読め、部位分けした動作を調整しやすい。一方で、同じパレット・図形生成器・陰影処理が全カードへ現れ、人物画や印刷物としての密度を出しにくかった。image_genの完成原画は、布・植物・金属・光の情報量とカードごとの構図差に優れるが、同じプロンプトから同じピクセルを再現できず、バイナリの目視と利用条件の記録が必要になる。今回は特色を原画へ、再利用性を共通枠とGodot側の5動作へ分担した。

### Godotで画像生成素材を重ねる時の注意

- `CardView._draw()`は子の`TextureRect`より先に描画される。原画を子ノードにしたまま選択不可理由を親の`_draw()`で描くと、帯が原画の背面に隠れた。理由と結果予告は`z_index = 3`のLabelにし、原画、共通枠、状態帯の順に重ねた。
- チュートリアルの紙面も、詳細画像の`z_index`より低いと人物画が紙を突き抜ける。盤面ハイライトを4、紙を5、説明とボタンを6に分けると、盤面を示しつつ説明を読める。
- `_render()`でControlを解放予約して同じフレームに作り直した直後は、撮影側に旧Controlの描画が1フレーム残る場合があった。スクリーンショットは2描画フレーム待ってから保存し、実行時と同じ安定した画面を証拠にする。
- 4:3の原画を縦長の共通枠へ収める処理は、タイトル、対戦表、手札、盤面、詳細表示で寸法が異なる。原画と枠を同じノードへまとめ、原画だけを窓の内側へ配置すると、各画面で個別の切り抜き計算を持たずに済む。
- UI生成の追加で`main.gd`がlintの1000行上限を越えた。見た目を組み立てる冪等な部品だけを`main_ui.gd`へ分け、決闘の状態遷移や入力は`main.gd`に残した。

## 採用するルール

通常召喚は毎ターン1回、上級モンスターの生け贄は導入しない。召喚したターンも攻撃できるが、決闘の最初のターンだけバトルを行えない。守備表示同士の戦闘は行わず、攻撃表示のモンスターから攻撃する。罠は相手の攻撃宣言時に自動発動する。これらをゲーム内の遊び方にも表示する。

## 素材の生成と同梱条件

背景・四属性の精霊・カード裏はオリジナルの SVG とし、BGM・効果音は Python 標準ライブラリだけで正弦波を合成した。生成器は `games/cardbattle/scripts/dev/generate_assets.py`。プロジェクトのルートで次を実行すると、同じ設計の画像と音声を再生成できる。フォントのダウンロードは生成器に含めていない。

```bash
python3 games/cardbattle/scripts/dev/generate_assets.py
```

- 色は紺・青緑・金を基調とし、属性ごとの色と図形を併用した。SVG 内の星の配置には固定シードを使用する。全 6 SVG を XML パーサーで読み込み、構文が成立することを確認した。実際のゲーム画面での見た目の判定は描画検証で行う。
- 音声は 22,050 Hz・16 bit・モノラル PCM。16 秒の BGM は終端を越える音の残響を先頭に折り返して重ねる。効果音は短いアタックとリリースを持たせ、急な波形の切断を避ける。生成時の最大振幅は BGM が 0.212、効果音が最大 0.508 で、PCM の上限に達していないことを確認した。耳での聴取評価とは区別する。
- 日本語フォントは Google Fonts の Noto Sans JP を取得し、データを改変せずファイル名だけ `NotoSansJP.ttf` に変更した。取得したフォントに対応する著作権表示と OFL 1.1 全文を `assets/fonts/OFL.txt` に同梱した。ライセンス文書は Godot の通常のリソース検出だけではエクスポート対象にならないため、各エクスポート設定の `include_filter` にも含める。
- `game-asset-search` の `record-credit.sh` で全素材を `assets/CREDITS.md` に記録し、`check-credits.sh --assets games/cardbattle/assets` が `check-credits OK` となることを確認した。独自生成物に根拠なく CC0 を付けず、生成方法と第三者素材を使用していないことを記録した。

## Godot 4.7 の音声停止と終了時の解放

macOS の Godot `4.7.stable.official.5b4e0cb0f` で、`AudioStreamPlayer` に `assets/audio/bgm.wav` を設定して再生し、約 0.35 秒後に終了する最小構成を実行した。音声ドライバは Dummy。終了コードが 0 でも `AudioStreamPlaybackWAV` と `AudioStreamWAV` の 2 インスタンス、および 1 リソースの解放漏れを示す WARNING / ERROR が出る。このため終了コードだけで検証を成功扱いにしない。

最小再現スクリプトと実行ログは、作業時に `games/cardbattle/tmp/audio_shutdown.gd` と同ディレクトリの `audio-shutdown-*`・`audio-headed-*`・`audio-movie-*` に保存した。いずれも一時的な検証成果物であり、配布物には含めない。

| 終了前の処理 | 実測結果 |
| --- | --- |
| 再生中のまま `quit()` | 2 インスタンスと 1 リソースの解放漏れ |
| `stop()` と `stream = null` の直後に `quit()` | 同じ解放漏れ |
| 停止後に `await create_timer(0.2).timeout` を挟んで `quit()` | headless と Movie Maker の両方で WARNING / ERROR なし |
| 停止後に 8 回 `process_frame` を待って `quit()` | headless で WARNING / ERROR なし |
| 終了処理中の停止後に `OS.delay_msec(200)` | 通常の描画あり・Dummy では WARNING / ERROR なし。Movie Maker では解放漏れが残った |

Godot の上流 issue では、停止要求が AudioServer 内で即時に参照を破棄する処理ではなく、後続の音声処理でフェードアウトして解放する処理になることが説明されている。今回の即時終了と解放待ちの差はその説明と一致する。`_exit_tree()` で `stop()` するだけでは後続フレームを確保できない。Movie Maker は録画フレームに合わせて音声を処理するため、メインスレッドを単にスリープさせても解放処理を進められなかった。

https://github.com/godotengine/godot/issues/76745

https://github.com/godotengine/godot/blob/4.7/servers/audio/audio_server.cpp

最小構成で音声を停止してから 0.2 秒フレームを進めた録画は 18 フレーム・0.60 秒となり、ログ全文に WARNING / ERROR がないことを確認した。`ffmpeg` の `volumedetect` でも最大音量 -14.7 dB、平均音量 -26.8 dB を取得し、正常終了のために録画音声をすべて消していないことを確認した。この数値は最小構成の検証結果であり、ゲーム本体の最終録画結果とは別である。

`--quit-after` は指定したフレーム数でエンジンを終了させるため、終了時のノード解放から追加の描画フレームを待つ用途には向かない。cardbattle では専用の `scripts/dev/movie.gd` からシーンを起動し、終了 8 フレーム前に `main.stop_audio()` を呼び、残りの描画を進めてから `quit()` する形を採用した。既定の 150 フレームは維持し、Makefile から `-- --movie-frames $(MOVIE_FRAMES)` で渡す。30 fps の 8 フレームは約 0.267 秒に相当する。録画スクリプト追加直後の `gdlint scripts/dev/movie.gd` は成功した。本体を通した最終録画結果は後続の検証記録に記載する。

## Godot skill・共通 Makefile への提案

共有ファイルはこの作業では変更していない。次の内容を司令塔側で再利用すると、音声のある他ゲームでも同じ問題を調べ直す手間を減らせる。

- `godot-development` の `references/pitfalls.md` に、音声を再生中の終了で `AudioStreamPlayback` が残る再現条件と上流 issue、停止後に描画フレームを進める回避策を追加する。単なる `stop()` や Movie Maker での `OS.delay_msec()` では解消しない点も区別して記載する。
- 共通の録画テンプレートは、`--quit-after` に任せる方法に加えて、録画スクリプトが音声停止と終了を管理できる構成を提供する。`MOVIE_FRAMES` の外部インターフェースは維持し、音声が不要なゲームに一律の処理を強制しない。
- 音声再生を遅延タイマーで開始するゲームでは、終了準備後にタイマーが発火して音声を再開しないようにする。短い録画や起動確認でも停止済みの状態を保持する。
- 素材を扱う共通手順では、OFL 文書の取得とリポジトリへの配置だけでなく、各エクスポートの `include_filter` への追加も確認する。素材の生成スクリプトとクレジット検査を残す運用を継続する。


## UIと決闘の検証で得た知見

- カスタム `_draw()` で描く画像を、その呼び出しの中だけで `load()` すると、参照が保持されず背景やカード画像が白くなる事象を実測した。描画するテクスチャを定数の `preload()` で保持すると解消した。リソースの読み込み成功だけでは見た目を検証できない。
- `TextureRect` は `expand_mode` を先に設定し、Labelはフォントと折り返しの設定・親への追加後にサイズを適用する。設定順によって一時的な最小サイズが残り、詳細画像やテキストが右パネルからはみ出す事象を実測した。
- Noto Sans JPの可変フォントは初期ウェイト100だった。`FontVariation` の `variation_opentype` に `TextServer.name_to_tag("wght")` で得た整数タグと500を渡し、各OSで同じ太さを使う。文字列キー指定では薄いままの描画を実測したため、整数タグを採用した。
- macOSの全画面切替はアニメーションを伴い、入力の直後2フレームでは切替完了を判定できなかった。全画面とウィンドウの各切替後に1秒待つと、F11 / STARTの入力検証が成立した。
- CPUと人間は同じルールAPIを使うが、UI側でも人間の手番かを確認する必要がある。CPU思考中の場の選択からCPUの攻撃処理を実行できないようにし、CPUのドロー演出には非公開のカード名を表示しない。
- ロジックの乱数を固定seedで再現できるようにすると、カード保存則と終局の多数試行を描画なしで検証できる。一方、代表画面では既知のカードを配置し、決定入力と実際のルールAPIで勝敗まで進めることで、ロジック検証と表示検証の両方を持てる。

## 第 2 ラウンド (品質向上)

### 制作方針

四属性の共有図形から、24体のモンスターと6種の魔法・罠を個別のイラストへ置き換える。紺・青緑・金の天体ファンタジーを維持し、日輪と月影の陣営をシルエットと装備で区別する。既存のカード定義・決闘ルールは維持し、AnimationPlayer、パーティクル、画面遷移、場面別の音源を表示層に統合する。

初回の既存スクリーンショット検証は exit 0。タイトルと対戦盤を目視し、属性画像の共有、平坦な背景、文字主体のHUDを改善対象として確認した。作業開始時点で PR #25 は未マージのため、通常起動の確認には指示書で認められたゲームディレクトリの run target を使用する。

### 素材と表示の構成

- モンスター24体と魔法・罠6種に、計30枚の独立した320×240 SVGを用意した。王・騎士・獣・竜・魔術師などの輪郭と装備を描き分け、色だけに依存しない。モンスターは背景・胴体・頭・装備を各体4枚に分けた。3層の背景・キーアート・ロゴを含め、追加SVGは131枚。
- `generate_card_art.py` はカードごとの設計表から素材を生成する。固定値を変えて再生成でき、XML検査・透明部分の確認・30カードのハッシュ重複検査を行った。手続き生成は同じパレットの調整と部位分割に向くが、絵の説得力は設計表では保証できず、実際のカード寸法で輪郭を確認する必要がある。
- 手描きのフレーム差分ではなく、部位別画像を `AnimationPlayer` で動かす方式を採用した。各体に待機・召喚・攻撃・被弾・退場の5動作を持たせ、飛翔・走獣・人型などで支点と移動を変える。小さなカード内でも見分けられる動きを優先した。フルサイズの立ち絵芝居は今回の表現には含めない。
- ドロー・召喚・攻撃・破壊・ダメージ・強化・罠・伏せ・魔法の9演出を、CPUParticles2D・Tween・光の図形で構成した。既存ルールには回復やレベルアップがないため、演出例の追加のためにルールを増やさず、強化魔法を専用の演出にした。
- 紺・青緑・金を共通Themeと日本語フォントの太さ550にまとめ、ライフバー、フェイズ表示、詳細欄、ボタンのホバーと押下を整えた。背景の3層移動とCanvasItemシェーダの発光はGL Compatibilityのまま動く。

### アニメーションを統合した際の注意点

- 決闘ロジックの結果イベントは、表示の更新より先に破壊済みモンスターを取り除く。UIを直ちに再構築すると退場動作の対象まで消えるため、イベント列が終わるまで古いカードノードを保持し、最後に盤面を再構築する。召喚は先に新しいノードを生成する。
- 各イベントの待ち時間を固定にせず、カード側の動作と演出側の長い方まで待つ。命中時点から始まる被弾・退場も含める。演出中は画面切替を除く操作を止め、Esc・手札ページ変更・ホバーによる再構築も防いだ。入力で退場中のノードを消さないことを実入力の撮影検証で確認した。
- カード内の画像は小さいため、攻撃の前進・回転・拡大で剣や翼が枠を越えやすい。24体それぞれの5動作を開始・途中・終了の3列にした画像で目視し、竜や大型の装備を含めて移動幅を調整した。
- CPUのドローだけでなく伏せる演出にもカード名を渡さない。カード種別はIDの先頭文字では判定しない。罠の `mist` がモンスターの `mXX` と同じ先頭文字になるため、CardCatalogのtypeを使う。
- 自動プレイ録画は、時刻ごとの実入力を使いつつ、その時点の手札から召喚・魔法・攻撃を選ぶ。ランダムな初手でも、召喚と攻撃が実際に発生したことを最後に検査する。終了の4秒前にCPUの新規行動を止め、進行中の演出と音声停止を完了させる。

### 音色と終了処理

`generate_audio.py` は固定旋律と固定seedを使い、5 BGM・9 SEを22,050 Hz・16 bit・ステレオPCMに生成する。FMの鐘、倍音を持つ弦・金管風の音、低音、ノイズ打楽器、左右配置と残響を重ねた。タイトル84 BPM、対戦112 BPM、強敵140 BPM、勝利108 BPM、敗北64 BPMとし、旋律・密度・音色も場面ごとに変えた。王2体の召喚で強敵曲へ移行し、曲は0.5秒でクロスフェードする。

生成を2回実行して全14ファイルのSHA-256一致を確認した。最大振幅はBGM 0.72、SE 0.78でクリップなし。ループの継ぎ目のサンプル差は曲内の最大差未満。これらは機械検証であり、利用できる音声聴取機能がないため、耳による音楽的な評価は未検証。音源自体とゲーム中の再生・切替は実装済みで、録画にも音声を含む。

停止状態を保持し、停止後の遅延処理から再生を再開しないようにした。通常の終了処理では16描画フレームと実時間0.2秒を待つ。Godotが処理した `--quit-after` は `OS.get_cmdline_args()` に残らないことを実測したため、引数から終了時刻を推測する処理は使用しない。強制終了経路の `_exit_tree()` では再生停止とstreamの解放後に200msを渡す。Movie Makerは音声処理が描画フレームに連動するため、実時間の待機だけで代替せず、録画シナリオ内で停止後の描画フレームを確保する。

### 本番に向けた道具への提案

共有skill・共有Makefileは変更していない。`godot-development` に、24体を一覧化した部位アニメーションの撮影器、入力中のノード再構築を検査する操作例、終了前に音声を止める20〜30秒の録画シナリオを再利用可能な例として加えるとよい。開始・途中・終了直前の画像と完全終了後の画像は目的が異なるため、両方を撮れる仕組みが必要になる。音の品質を判断するには、波形検査に加えてエージェントが実音を聴ける道具が不足している。
