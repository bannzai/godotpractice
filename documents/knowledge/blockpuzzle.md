# 星つむぎの制作知見

## 制作判断

issue #42 の落ち物パズルを、夜の温室で精霊をつなぐ「星つむぎ」として制作した。盤面は6列×12行、4色の2個組。対戦はCPUの強さ3段階と2本先取、ひとりでは90秒のスコアアタック。色だけに頼らず、角のある丸い精霊・葉の精霊・星・しずく・歯車のおじゃまを別のSVGにした。

SVGとPCM音源は同梱スクリプトで生成する。手続き生成は、小さい盤面内で読める輪郭と一貫したパレットの調整に向く。写実的な絵や複雑な芝居は今回採用せず、顔のあるベクター画像をAnimationPlayerで伸縮・移動・回転・退色する表現にした。全5種に待機・移動・着地・被害・消去がある。背景は空・温室のアーチ・植物の3層とし、視差とGL Compatibility対応シェーダの淡い明滅を加えた。

音源は単純な正弦波だけにせず、倍音のある音・FM風の鐘・低音・ノイズ打楽器・残響を重ねた。タイトル・プレイ・危機・結果で旋律とテンポを変え、連鎖時には効果音の音程を上げる。フォントは既存ゲームから出典とOFL全文を確認して同梱した。assets/CREDITS.md と生成スクリプトが素材の一覧と再生成方法の正である。

## 盤面ロジックと進行

- 同色消去・重力・連鎖解決・回転の壁蹴りと床蹴り・CPUの評価・記録データ解釈を純粋関数に分離した。入力盤面は変更せず、新しい盤面を返す。連鎖の各段階を返すため、最終得点だけでなく消去前・消去後・落下後の期待値も検証できる。
- おじゃまは消える色付き精霊に隣接するものだけ消す。消去集合を走査中に増やすと、おじゃま同士を伝って遠くまで消す不具合になるため、色付き精霊の集合を先に固定する。
- CPUは高さを抑える初級、同色接続と確定消去を評価する通常、次の組を先読みする上級。出現位置が空いていても、盤内へ組を固定できる候補がゼロになる盤面がある。候補の空判定を決着へつなぐテストを追加した。
- ゲーム状態はautoloadのSessionに集約し、盤面表示はsignalを受けて更新する。落下中・消去中・落下演出中を分け、消去アニメーションが終わるまで精霊のノードを保持する。
- 接地猶予は0.42秒で、移動による猶予の更新には上限がある。入力を連打して永久に止めることはできない。左右の長押しは初回遅延と連続移動を分けた。
- おじゃまは予告して次の組の出現前に落とし、自分の消去による攻撃で予告を相殺する。一度の落下上限を設け、残りは予告に保持する。

CPUの候補を列ごとの落下だけで列挙すると、天井まで積んだ壁の向こうにも配置できることを独立レビューで発見した。現在位置から左右・下・回転の壁蹴りを探索し、到達可能な接地だけを評価する方式へ修正した。出現時点で越えられる壁でも、思考中に自然落下した現在位置からは越えられない場合があるため、出現位置を固定せず現在の姿勢を探索の入口に渡す。返された経路をCPUの画面上の移動にも使う。

探索時に姿勢ごとの衝突判定と同じ解決後盤面の先読みを共有し、検査盤面での強いCPUの探索は約395msから約90msへ短縮した。これはローカルの実測で、全盤面やWeb実行での応答時間保証ではない。

## 検証で得たこと

実入力の統合テストではInputMapの存在だけでなく、InputEventKey・InputEventJoypadButton・InputEventJoypadMotion・InputEventMouseButtonを本番シーンへ流した。パッドのAはGUIのui_acceptにも明示し、プレイ中は回転入力として一度だけ消費する。移動は押下状態を見るため、入力イベントの解放前にフレームを進める。

撮影用の既知の盤面と、通常のゲームへ実入力だけを送る26秒の録画を分けた。前者は連鎖途中・おじゃま落下・勝敗・各キャラの5動作×3時点を漏れなく比較する。後者は盤面と抽選列を書き換えず、現在の盤面を読み取ってキー入力だけで置くことで、通常の進行経路が成立していることを確認する。

Godotの型付き配列は、動的なNode参照経由で通常の配列を代入できない。撮影の勝敗fixtureで `wins = [0, 1]` が実行時エラーになり、`wins.assign([0, 1])` に修正した。gdlintだけでなく実シーンの撮影が必要だった。

サンドボックス内ではGodotのエディタ設定保存とGUI起動、Tailscaleの既存接続読み取り、PUTSのKeychain読み取りが拒否された。ゲームの失敗と混同せず、依頼された操作の実行権限で検証する。全Godotコマンドのログは作業ディレクトリ内の絶対パスへ向け、importも終了コードに加えてログ全文を検査するようにした。

## 音声を持つゲームの終了

音声停止後にもUIの毎フレーム更新からBGM切替が呼ばれるため、停止フラグを持たないと終了準備中に再生が再開する。stop_audioは停止状態を保持し、後続のBGM・SE再生を無視する。headlessでは音声の読み込み・ノード生成を省略する。

通常終了は音声の停止とstream解放後に描画フレームと0.2秒を待つ。Movie Makerでは終了16フレーム前に進行を止めて音声を解放し、表示シーンを保持したまま録画を終える。`--quit-after` の経路は事前通知がないため、ノード終了処理で音声スレッドへの反映を待つ。通常終了・GUI強制終了・録画終了をそれぞれ検証する。

## skill・共有物への提案

共有物は変更していない。godot-development skillへ、落ち物パズルの純粋な盤面fixture、実入力で置き場所を選ぶ録画シナリオ、5動作の開始・途中・終了を1枚にする撮影器を追加すると、次のゲームで再利用できる。音声の停止フラグと毎フレームのBGM切替の競合も終了処理のテンプレートへ加えるとよい。

## 最終検証

ローカルの `make test GAMES=blockpuzzle`・`make screenshot GAMES=blockpuzzle`・`make movie GAMES=blockpuzzle`・`make build-all GAMES=blockpuzzle`・`make build-web GAMES=blockpuzzle` はすべてexit 0。ログ全文にWARNING / ERRORと終了時リークはなかった。`make blockpuzzle-run` は実ウィンドウ表示後に通常終了してexit 0。`--quit-after` の1・8・30・120フレームもexit 0でリークなし。

撮影は23枚で、5キャラ×5動作×3時点と各画面、連鎖・おじゃまの途中と終了を目視した。固定秒数だけで連鎖を撮影するとフレーム速度によって目的の段階を外すため、状態のphaseとchainが一致してから撮影する。2連鎖終了後の空盤面も期待値で検査する。

通常起動は5秒、実入力プレイは26.03秒を録画した。後者では24回固定・10回消去し、2秒間隔のフレーム一覧と末尾を目視した。Windows／Linuxはエクスポート、LinuxはCIでも検証する。物理ゲームパッドの機種別互換性と各OSでの手動プレイ、音楽の聴感評価は未検証で、パッドは実InputEvent、音は波形と録画の音声ストリームを確認した。

Web検証では `--software-webgl` で起動し、`#status` が除去されることとcanvasのサイズを確認できた。一方でagent-browserの撮影が数分応答せず、直接CDPの撮影も期限超過した。起動判定の成功だけでは画面確認の代用にならず、転送量や接続遅延も切り分ける必要がある。最終のWeb実操作とCI artifactの確認結果、公開画像の証拠はPR #50に集約する。

## 手直しラウンド (見た目の特色化)

### 分かりにくさの原因と効いた表現

前の画面は、タイトルに同じ大きさのボタンが縦に並び、CPU対戦・90秒モード・CPUの強さ・遊び方の階層が見た目から分かりにくかった。プレイ中は操作説明を画面下の1行に集めたため、視線が盤面と離れ、現在操作できるか、薄いピースが何を示すか、消去中に入力できない理由がその場では伝わらなかった。連鎖数・スコア・経過時間も同じ強さの文章として並び、プレイの成果が画面の主役になっていなかった。

モード選択を横並びのタイル状カードへ変え、フォーカス中のカードだけを太い紫枠で示した。右側には「盤面数・目的・終了条件」のプレビューを置き、90秒計測を選ぶとCPUレベルを無効化して「CPU対戦を選択中のみ変更できる」と表示する。プレイ中は操作盤面の枠を紫、CPU盤面を青緑に固定し、操作可能なら「移動・回転できます」、不可なら「消去中」「落下中」など待つ理由と次に起きることを中央カードに表示する。共通の操作ガイド行は廃止し、初回だけ盤面・落下位置・連鎖グラフを順に強調する3手順の半透明チュートリアルへ移した。スキップしても同じ終了処理を通る。

連鎖数は中央の大きな2桁、スコアは時系列の折れ線として表示する。消去中の大きな連鎖ポップ、落下位置の薄い図形、予告数、次とその次の図形を同時に残したため、「今できる操作」と「選んだ先で起きること」を盤面の近くで確認できる。

### ColorRect / Polygon2D と Tween に限定した素材作り

今回は外部画像や画像生成を使わず、既存の手続きSVG 11点と画像用シェーダを削除した。背景・カードの色面・盤面セル・4色ピース・予告ブロック・消去片・折れ線を、実行時に `ColorRect` と `Polygon2D` から組み立てる。円は固定頂点数の多角形、折れ線は各区間を細い四角形にし、ピースは正方形・円・ひし形と内側の単色記号を組み合わせた。待機・移動・着地・被害・消去の5動作と背景の浮遊は `Tween` だけで再生し、顔・グラデーション・輪郭イラストを使わない。

当たりだった点は、色・寸法・余白をGDScriptからすぐ揃えられ、SVGの再生成・import・参照差し替えが不要になったこと、開始・途中・終了を時刻指定した撮影でも同じ形を再現できたこと、第三者画像のライセンス確認が不要なこと。情報デザインのように幾何形状自体が完成表現になる場合は、画像ファイルを経由するより調整箇所が少ない。外れだった点は、複雑な輪郭や描き替えアニメーションには向かず、円・線・枠の小さな生成ヘルパが複数スクリプトへ分かれやすいこと。消去片も粒子ノードを使えないため、個々の図形とTweenの寿命を明示する手間が増えた。

前の手続きSVGは、ピースごとに顔やシルエットを細かく描ける一方、生成スクリプト・11画像・11 import情報・実行時のSprite2Dが同じ表現を分担していた。今回は画面コードが形状の正となり、画像・import情報を持たない。ファイル数とライセンス確認は減ったが、表現の方向を「平面の幾何」に限定できる案件でなければ同じ方法を選ぶべきではない。

フォントは `game-asset-search` のGoogle Fonts検索・取得処理で Murecho の可変フォントを入れた。取得元は https://fonts.google.com/specimen/Murecho 、ライセンスはOFL-1.1、著作権表示は `Copyright 2021 The Murecho Project Authors (https://github.com/positype/Murecho-Project)`。`assets/fonts/OFL.txt` に著作権表示と全文を保持し、各export presetのinclude filterで同梱する。禁止された Noto Sans JP は削除した。

音声は前ラウンドの場面別BGM 4点とSE 8点を保ち、低い持続音と周期的な高音からなる8秒の環境音、モード・チュートリアルの選択音をPython標準ライブラリで追加した。生成スクリプトは同じバイト列なら書き直さない。14点すべてで形式・非無音・ピーク・クリップ・ループ端点と再生成SHA-256一致を検査できる。数値検査は音楽としての好みや長時間の聴き疲れを評価しないため、聴感評価とは区別する。

### Godotで情報デザインUIを作る時の注意点

- `ColorRect` は `Control`、`Polygon2D` は `Node2D` なので、両方を同じ変数へ入れて移動させると型が一致しない。消去片は `Node2D` の親を作り、その子にどちらかの図形を置くと、親のposition・rotation・modulateを同じTweenで扱える。
- 画面遷移でcontent全体を0.22秒フェードすると、撮影スクリプトが入力直後にPNGを保存した場合、完成画面ではなく半透明の途中フレームになる。チュートリアルの各段階はフェード時間を待ち、完成状態を撮る。
- 折れ線は値のSSOTであるSessionのscoreを1秒ごとに採取し、表示用の点だけを最大24件保持する。結果画面も同じ履歴を使うため、プレイと結果で異なるグラフを組み立てない。
- 初回チュートリアルの完了は既存の記録JSONにbooleanで保存する。古い保存データや数値を入れた不正データはfalseへ戻し、スコア・最高連鎖と同じ解析関数をselfcheckする。
- Tween完了後に消すラベルを別ノードとして追加した場合、それぞれに寿命を持たせる。大数字だけを解放して単位ラベルを残すと、連鎖のたびに表示ノードが蓄積する。

### skill化の候補

`game-asset-search` には、SVG・PCMの手続き生成とは別に「画像ファイルを作らず、ColorRect / Polygon2D等のエンジン標準図形で完結させる」経路と、第三者素材を使わないコード描画をCREDITSへ記録する例があるとよい。現行の `check-procedural-assets.sh` はファイル生成物の再現性検査には効くが、コード描画の禁止ノードや画像参照の混入は検査しない。

`godot-development` には、contentをフェードするゲームのscreenshot.gdで「画面遷移時間を待ってから撮る」例、初回チュートリアルの各段階・スキップ・操作可能／不可能表示を実入力で検査する例を追加できる。固定秒数より画面状態の成立を待つ方が堅いが、Tweenの完成状態には描画時間の待機も必要だった。
