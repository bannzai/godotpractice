# Monster Quest 開発ヒアリング

## 1. 開発の進め方

最初に `AGENTS.md`、`documents/PROJECT.md`、対象 Issue、既存の `documents/knowledge/monsterquest.md`、先行 PR の記録を読み、受け入れ条件と変更可能な範囲を確認した。その後、変更前のゲームを実際に起動し、タイトル、町、フィールド、戦闘、ヘルプの各画面を撮影した。近隣のゲームも確認し、このリポジトリ内で期待される画面密度、ピクセル表現、検証方法を把握してから実装へ進んだ。

実装はおおむね次の順で進めた。

1. タイトル、ワールド画面、戦闘画面、チュートリアル、地域マップの情報設計と画面構成を整理した。
2. 外部素材の出典とライセンスを確定し、元ファイルを保存した。
3. キャラクター、モンスター、タイル、背景、地図、UI 部品をピクセルアートへ置き換えた。
4. キャラクターの待機、歩行、攻撃、被弾、勝利を各 6 フレームで用意し、`AnimatedSprite2D` で再生した。
5. ボタンの選択状態、行き先のプレビュー、利用できない理由、チュートリアル、地域マップなど、操作前に結果を判断できる表示を追加した。
6. 町とフィールドの環境音を追加し、実際に聴いて音量、周期、耳につく成分を調整した。
7. `selfcheck.gd`、`screenshot.gd`、起動動画、操作動画を拡充し、デスクトップ版と Web 版を検証した。
8. macOS、Windows、Linux、Web のエクスポートを確認し、CI の成果物もダウンロードして目視した。
9. 実装中に得た知見を `documents/knowledge/monsterquest.md` に整理し、PR の説明と画像を更新した。

詰まった点と解決方法は次のとおり。

- DotGothic16 に三角形の記号 `▶` がなく、macOS では代替フォントによって表示される一方、Web 版では欠けた。文字によるカーソルをやめ、16×16 のカーソル PNG を作り、`Button.icon` で表示するようにした。これにより実行環境のフォント代替へ依存しなくなった。
- `agent-browser` の名前付きセッションが古い CDP 接続先を保持し、新しい `webtunnel` セッションへ接続できないことがあった。対象の名前付きセッションを閉じてから CDP へ再接続した。
- `webtunnel down` の直後は tailnet 側の後片付けが終わっておらず、同名セッションをすぐ作り直せないことがあった。状態を確認し、後片付けの完了後に `up` し直した。
- Web 経由のキー入力は、処理時間によって一度の入力が複数マスの移動になることがあった。画面状態を都度確認しながら入力し、操作動画ではローカル 30 fps の決められたフレーム数で入力時間を管理した。
- `puts preflight` は手元のバージョンで利用できず、`puts upload` も複数ファイルを一度に受け取らなかった。`puts --help` で実際の仕様を確認し、画像を 1 ファイルずつアップロードした。実行時に作業ディレクトリへ生成された `default.profraw` は `tmp` 内へ移した。
- ピクセルアートを SVG で作る方式は、Godot のラスタライズ、入れ子 SVG、アンチエイリアス、透明部分の扱いを揃えにくかった。最終的には Python から PNG の画素を直接生成し、4 色のパレットとニアレストネイバー拡大を固定した。
- `documents/knowledge/monsterquest.md` の変更はゲーム外の共有変更として CI の全ゲーム検証を起動した。`towerdefense` と `citybuilder` で終了処理時のリークによる一時的な失敗が出たため、GitHub API から該当ジョブのログを取得し、Monster Quest の失敗ではないこと、`citybuilder` のスクリーンショット生成自体は exit 0 だったことを確認した。その後、失敗したジョブを再実行し、全 64 チェックの成功を確認した。他ゲームのコードは変更していない。
- エクスポートへ不要な元素材や検証用ファイルまで含まれ、PCK が約 10 MB になった。エクスポート除外を設定し、必要な実行時素材だけを含めて約 3.6 MB まで減らした。

## 2. 使ったツール・skill・コマンド

### skill と補助ツール

- `godot-development`: Godot 4.7 の起動、headless 検証、スクリーンショット、動画、エクスポート、および既知の注意点を確認するために使った。
- `game-asset-search`: 画像素材の候補検索、ライセンス条件の確認、元ファイルの保存、クレジットと SHA-256 の記録に使った。
- `webtunnel`: GitHub Actions runner 上の Web エクスポートを配信し、手元から Chromium へ接続するために使った。
- `agent-browser`: `monsterquest` という名前付きセッションと明示した CDP 接続先を使い、Web 版を実際に操作した。
- `pr-attach-screenshots` と `puts`: 比較画像や検証画像をアップロードし、PR から参照できる URL を作るために使った。
- 画像の目視用ツール: 個別 PNG、比較用 montage、CI の PNG、動画から切り出したフレームを確認した。

### 実際に使った主なコマンドと用途

- `make test GAMES=monsterquest`: lint、起動、ロジック検証をまとめて実行した。
- `gdlint scripts/`: GDScript の lint に使った。
- `make import GAMES=monsterquest`: 追加・更新した PNG、WAV、フォントを Godot へインポートした。
- `make check GAMES=monsterquest`: シーンとスクリプトをロードでき、起動ログに WARNING / ERROR がないことを確認した。
- `make selfcheck GAMES=monsterquest`: セーブ、移動、戦闘、捕獲、保管、経路探索、入力、画像の色数、アニメーション時間などを検証した。
- `make screenshot GAMES=monsterquest`: 代表状態と各アニメーションのフレームを PNG にした。
- `make movie GAMES=monsterquest`: 起動からタイトル表示までを 5 秒の動画にした。
- `make movie-play GAMES=monsterquest`: タイトル、チュートリアル、地域マップ、フィールド、町、隊長戦、敗北結果、タイトル復帰までの実操作を約 37 秒、1110 フレームで録画した。
- `make build-all GAMES=monsterquest`: macOS、Windows、Linux のデスクトップ版をエクスポートした。
- `make build-web GAMES=monsterquest`: Web 版をエクスポートした。
- `make monsterquest-run`: エディタを介さずデスクトップ版を起動した。
- Godot 4.7 の headless 実行: `selfcheck.gd` などの自動検証に使った。
- Godot 4.7 の通常描画と Movie Maker: スクリーンショットと動画生成に使った。
- `ffmpeg`: MP4 の情報確認、2 秒ごとのフレーム抽出、末尾フレームの抽出に使った。
- ImageMagick の `montage`: 変更前後や複数状態を 1 枚に並べて比較するために使った。
- Python 3: PNG の直接生成、WAV の合成、画像の色数・透明度・寸法の検査、素材ファイルの処理に使った。
- `sha256sum` 相当のハッシュ確認: 保存した元素材と記録した SHA-256 の一致確認に使った。
- `gh pr`、`gh run`、`gh api`: PR、CI 状態、ジョブログ、成果物の確認と取得に使った。
- `puts upload`: PR 掲載用画像を 1 枚ずつアップロードした。

`make check-credits` も試したが、このリポジトリにはその target がなく成功していないため、使用できた検証には数えていない。素材の出典、ライセンス、ハッシュは `game-asset-search` の手順と現物の照合で確認した。

## 3. 欲しかったが無かったツール・skill・スクリプト

- CC0 スプライトシート取り込みスクリプト: URL、ライセンス、ダウンロード日時、SHA-256、採用セルの座標、切り出し倍率、変換後パレットを 1 つの manifest に残し、元ファイルの保存からクレジット生成までを一括で行えると手作業が減る。
- Godot 向けピクセル素材検証スクリプト: 元 PNG だけでなく Godot のインポート後テクスチャを検査し、フィルタが nearest か、各フレームが空でないか、意図しない半透明色やパレット外の色がないかを検出したい。
- 決定的なゲーム操作ドライバー: キーを何ミリ秒押すかではなく、「入力を 1 回処理して次の状態になった」という応答をゲームから受け取って次へ進める仕組みが欲しかった。ローカル動画と `webtunnel` の双方で、処理速度による入力回数のぶれをなくせる。
- PR 検証画像作成スクリプト: 変更前、変更後、参考画面の組み合わせ、montage 作成、ファイルごとの `puts upload`、URL の到達確認、PR 本文更新までを一括化したい。`default.profraw` のような副生成物も `tmp` 内へ閉じ込めたい。
- CI 成果物と失敗原因の収集スクリプト: 対象 run の全ジョブログ、PNG、MP4 を取得し、ゲーム本体の失敗と終了処理時リークのような既知の不安定要因を区別して要約できると調査が速くなる。
- Web フォントの字形網羅性検査: 画面文言に使う全コードポイントが同梱フォントに存在するかをビルド前に検査できれば、macOS の代替フォントで隠れた `▶` 欠落を早期に発見できる。
- 音素材のループ検証スクリプト: 先頭と末尾の波形差、DC オフセット、ピーク、ラウドネス、ループ境界のクリックを自動検査し、町とフィールドの周波数傾向も比較したい。ただし、耳につく周期や場面との相性は数値だけでは判断できないため、最終的な試聴は残る。

特に再利用価値が高いのは、CC0 素材取り込み、ピクセル素材検証、決定的なゲーム操作、PR 検証画像作成の 4 つである。今後ほかの 8 ゲームでも同じ作業が発生するため、個別スクリプトだけでなく skill として入力、成果物、完了条件を統一する価値がある。

## 4. 素材の準備方法と使い勝手

### 画像

外部の元素材として、OpenGameArt の CC0 素材を 2 点使った。

- ansimuz の TinyRPG Stranger Forest Pack
- devurandom の 16×16 8-bit RPG character set

元ファイルは削除せず保存し、配布 URL、作者、ライセンス、SHA-256 を記録した。ただし、配布素材を画面へそのまま置いたのではなく、人物の体格やポーズの基準として使った。切り出すセル座標を明示し、ニアレストネイバーで拡大し、4 色へ減色したうえで、装備や外見を Monster Quest 用に描き足した。この方法は、人物の自然な比率と動作の土台を短時間で得られる一方、スプライトシートごとのセル配置、余白、向き、ライセンス記録を人手で確かめる必要があった。

モンスター、タイル、背景、地域マップ、UI 部品は Python で画素を直接配置して PNG を生成した。合計 47 枚の PNG を生成し、通常は 4 色、戦闘で注意を引く部分だけ赤を許可した。キャラクターは 10 種類について、5 動作、各 6 フレームのシートを作った。直接生成は、輪郭、パレット、透過、寸法、再生成結果を厳密に固定でき、テストもしやすかった。反面、解像度やシルエットを大きく変えると座標指定の修正量が多く、人が自由に描く場合より試行錯誤の単位が細かくなる。

初期に試した SVG は、部品の再配置や拡大縮小には便利だったが、Godot 側でのラスタライズ結果、アンチエイリアス、透明部分、入れ子にした SVG の扱いがピクセルアートの要件と相性が悪かった。今回のように低解像度と少数色を保証したい場合は、PNG の直接生成の方が扱いやすかった。

### フォント

Google Fonts で配布される Fontworks の DotGothic16 を使い、OFL のライセンス文書を同梱した。日本語を含むゲーム UI を一貫した見た目にできたが、一般的な記号がすべて収録されているとは限らない。macOS のフォント代替では欠落に気づきにくいため、Web 版での確認と使用文字の字形検査が必要だった。選択カーソルは文字ではなく PNG に変更した。

### BGM と SE

既存の BGM と SE は維持し、町とフィールドを区別する 8 秒の環境音 WAV を 2 本追加した。Python 標準ライブラリで 32 kHz、16 bit、ステレオの WAV を生成し、発振器と決定的な LFSR ノイズを組み合わせた。生成処理を再実行しても同じ波形になり、外部ツールや新しいライセンスへ依存しない点は扱いやすかった。

一方、波形のピーク、長さ、チャンネル数、ループ端の数値確認だけでは音の良し悪しを判断できなかった。試聴すると、町の音が信号音のように聞こえることや、フィールドの高域とノイズが耳につくことが分かり、音量、周期、周波数成分を調整した。音素材は自動検査と実際の試聴を組み合わせる必要がある。

## 5. 動作確認の方法

### headless の `selfcheck.gd`

セーブデータの読み書きと厳密な型検査、ダメージ計算、捕獲、保管枠、経路探索、入力、ピクセル素材の色数、アニメーションの再生時間と非ループ終了などを高速に繰り返し確認できた。ロジックの回帰検出には最も効率がよかった。一方で、文字切れ、重なり、色の見え方、動きの自然さは headless では確認できない。

### `screenshot.gd`

最終版では 44 枚の PNG を生成した。タイトル、チュートリアル、地域マップ、ボタンの選択状態、利用できない行き先、攻撃の途中、捕獲、戦闘結果に加え、各キャラクター動作の一覧用フレームを撮った。実際の `AnimatedSprite2D.frame_changed` を待って開始、中間、終了付近を撮影したため、単に元シートを切り出す検査より、Godot が本当にそのフレームを表示したことを確認できた。

静止画はレイアウトと個々のフレームの確認には強いが、フレーム間の速度、つながり、入力に対する反応は判断できない。そのため動画を併用した。

### `movie` と操作動画

`make movie` で起動からタイトルまでの 5 秒を録画し、真っ黒な画面や初期描画の崩れがないことを確認した。さらに `make movie-play` で約 37 秒、1110 フレームの操作を記録し、タイトルからチュートリアルと地域マップを往復し、フィールド、町、隊長との会話と戦闘、敗北結果、タイトル復帰までを通した。

`ffmpeg` で操作動画から 2 秒ごとに全 19 枚のフレームを抽出し、流れの欠落がないか目視した。アニメーションは、元シートのフレーム一覧、実行中の開始・中間・終了フレーム、`selfcheck` による時間進行と非ループ終了、操作動画での連続再生を組み合わせて確認した。一覧用の静止画だけでは動きの滑らかさが分からないため、動画が不可欠だった。

### CI の artifact

CI が生成した 44 枚の PNG と 5 秒の MP4 をダウンロードし、ローカルだけでなく Xvfb と llvmpipe 上でも同じ画面が出ることを確認した。既知の VSync 警告を除き、Monster Quest の画像生成と動画生成は成功した。CI は別環境での再現性確認に有効だったが、入力を伴う一連のプレイや音の主観評価までは扱わない。

### `webtunnel`

GitHub Actions runner 上で Web エクスポートを起動し、`agent-browser` からタイトル、チュートリアル、地域マップ、フィールド、町、隊長との会話、戦闘、敗北結果、タイトル復帰まで操作した。ブラウザのコンソールとエラー表示が空であることも確認した。この確認で、デスクトップ版ではフォント代替に隠れていた選択カーソルの字形欠落を発見できた。

一方、runner の Chromium は 1280×656 でゲームの 16:9 座標と一致しないため座標変換が必要で、ネットワークや描画速度によってキー押下時間もぶれた。また Web 版では、フルスクリーン切り替えやゲームパッドなどデスクトップ固有の挙動を十分に検証できない。その範囲はローカル起動、デスクトップエクスポート、CI の画像と動画で補った。

## 6. Godot 固有のハマりどころと回避策

- `Button` のフォーカスと無効状態: マウスを置いた見た目とキーボードのフォーカスが別管理になる。利用不能なボタンにもフォーカスが残ると説明と選択状態が食い違うため、無効化、フォーカス、プレビュー更新を同じ状態変更処理で同期した。
- モーダル表示中の背面 UI: 見た目だけ前面に出しても、背面のボタンが入力を受けることがある。チュートリアルや地域マップを開いている間は背面ボタンを明示的に無効化し、閉じたときにフォーカスを戻した。
- ピクセル画像のフィルタ: ルートだけを設定しても、子ノードや動的に作ったテクスチャへ設定が届かない場合がある。対象ノードをたどって nearest を適用し、ピクセルスナップと整数倍率を併用した。
- `Label` の折り返し: コンテナへ入れただけでは期待どおりに折り返されない場合がある。幅、最小サイズ、autowrap を明示し、実際の日本語文言でスクリーンショットを確認した。
- 画面遷移中の撮影: ピクセル単位のワイプは非同期で進むため、遷移開始直後に撮ると状態が安定しない。安定後を待つ通常スクリーンショットと、遷移途中を意図的に撮るスクリーンショットを分けた。
- `TileMapLayer`: Godot 4.7 の構成に合わせ、従来の `TileMap` 前提の操作を持ち込まず、レイヤー単位で表示と座標を扱った。
- `AudioStreamPlayer.stop()`: 停止を呼んでもミキサー側の処理が完了するまで短い時間が必要になる。動画終了直前に音を止め、終了までの猶予を設けた。
- Movie Maker の終了タイミング: 最終フレームと音声を欠かさず、終了処理時のリークも避けるため、予定終了より 12 フレーム早く停止処理へ入り、残りのフレームで後片付けを進めた。
- `tmp` と `build` のインポート: Godot はプロジェクト配下を走査するため、生成物が再インポート対象になると警告、肥大化、再帰的な成果物混入につながる。`.gdignore` とエクスポート除外を併用した。
- JSON の数値型: JSON の数値は読み込み後に浮動小数点として扱われる場合がある。セーブデータは型と範囲を厳密に検証し、書き込みは一時ファイルを介して置き換える方式にした。
- `InputMap`: `ui_accept`、ゲームパッドの A、Tab によるフォーカス移動は UI の既定挙動と競合しやすい。ゲーム操作と UI 操作を区別し、モーダル状態と現在の画面に応じて処理対象を限定した。
- 戦闘イベントの表示値: イベント発生時の HP と、全処理後の現在 HP を混ぜると、途中の攻撃表示が最終結果へ飛ぶ。イベントごとに表示用スナップショットを保持した。
- `ProgressBar` の見た目: 最小サイズだけではゲージの太さや fill の見え方が安定しない。背景と fill の `StyleBox`、余白、最小サイズを明示し、実画面で確認した。

今回もっとも有効だったのは、ロジックを `selfcheck` で固定し、代表状態を `screenshot.gd` で大量に撮り、連続動作を操作動画で確認し、最後に CI と `webtunnel` という別環境で再確認する組み合わせだった。どれか 1 つだけでは、Web フォントの欠落、入力時間のぶれ、アニメーションのつながり、レイアウト崩れのいずれかを見落としやすい。
