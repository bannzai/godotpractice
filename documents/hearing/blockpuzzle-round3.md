# blockpuzzle 開発の振り返り

対象は issue #42、落ち物パズル「星つむぎ」。最終実装は `80cc73b`。以下は今回実際に行った作業と、その限界をまとめたもの。

PR: https://github.com/bannzai/godotpractice/pull/50

## 1. 開発の進め方

最初に作業指示書、AGENTS.md、PROJECT.md、issue、Godot の開発手順と既存ゲームの実装・知見を読んだ。まずタイトル→プレイ→結果の最小ループを作り、早い段階で draft PR を出した。その後、盤面ロジックと素材を担当ファイルごとにサブエージェントへ分担し、自分はゲーム進行・画面・入力・演出の統合を進めた。

中核は、6列×12行の盤面、4色の2個組、消去・重力・連鎖、CPU、おじゃま、2本先取、90秒のスコアアタックの順に組み上げた。盤面計算を純粋関数、ゲーム進行を autoload の Session、表示を盤面ビューと個別ピースに分けた。画像と音源が揃った後、着地・消去・連鎖の演出、背景、HUD、場面別BGMを統合した。

最後はロジック検査、実入力の統合検査、各画面の撮影、通常プレイの録画、終了時リーク、各形式のエクスポート、CI artifact、Web実操作の順に証拠を揃えた。撮影や独立レビューで見つかった問題を直し、画像とPR本文を更新した。最終CIの全31ジョブ成功と画像・動画の目視を確認してから、PRをready for reviewにした。マージはしていない。

特に詰まった点は次のとおり。

- CPUの候補を列ごとの落下だけで列挙すると、天井まで積んだ壁の向こうへ配置できてしまった。現在の位置・回転から左右・下・回転を幅優先探索し、到達可能な接地だけを評価するよう修正した。経路も返し、画面上のCPUがその経路を移動するようにした。思考中の自然落下を考慮するため、探索開始位置は出現位置に固定しなかった。
- 強いCPUの先読みが重くなったため、衝突判定と同じ解決後盤面の評価を再利用した。検査盤面で約395msから約90msへ短縮した。ただし全盤面やWebでの速度を保証する計測ではない。
- 固定秒数で連鎖を撮影すると、狙った消去・落下の段階を外した。実際のphaseとchainを待ってから撮るようにし、2連鎖終了後の空盤面も検査した。
- 再戦時にスコアのカウントアップ表示が前の試合から残った。値が下がるときは即座に表示を戻すよう修正し、回帰検査を追加した。
- Webの起動判定は成功しても、撮影が数分応答しないことがあった。直接CDPでも期限超過した。再開後の新しいセッションではJPEG撮影、その後agent-browserのPNG撮影が成功した。通信量を減らす切り分けは役立ったが、前回の停止原因を断定できるところまでは調べていない。
- CI artifactのダウンロードが長く無出力になった。ファイルの実体と通信状態を確認し、`gh api`によるZIP直接取得へ切り替えた。ZIPの整合性を確認してから展開した。

主な検証コマンドは次のとおり。`movie-play`はゲームのディレクトリで実行し、ほかの列挙したmakeはリポジトリルートから実行した。

```sh
make test GAMES=blockpuzzle
make screenshot GAMES=blockpuzzle
make movie GAMES=blockpuzzle
make build-all GAMES=blockpuzzle
make build-web GAMES=blockpuzzle
make blockpuzzle-run
# games/blockpuzzle/ で実行
make movie-play
```

Webは次の経路を使った。実行時は自分専用のブラウザセッション名を指定した。

```sh
WEBTUNNEL_REPO=bannzai/godotpractice bash ~/.agents/skills/webtunnel/scripts/webtunnel-cli.sh up blockpuzzle --software-webgl --ref game/blockpuzzle --wait
bash ~/.agents/skills/webtunnel/scripts/webtunnel-cli.sh cdp blockpuzzle
WEBTUNNEL_REPO=bannzai/godotpractice bash ~/.agents/skills/webtunnel/scripts/webtunnel-cli.sh down blockpuzzle
```

素材生成サービスのimage_gen・Gemini、外部の画像・音源素材サイトからのダウンロードは今回は使っていない。skillを読んだことと、そのskillが扱う全サービスを使ったことは区別している。

## 3. 欲しかったツール・skill・スクリプト

今回は次の機能を共通の仕組みとして使えず、ゲーム固有コードや一時スクリプトで補った。今後の再利用候補であり、今回新たなskillとしては作成していない。

- **アニメーション撮影の共通化**。キャラ、動作名、開始・途中・終了時刻を渡すと一覧画像を作るもの。ゲームのphaseを待って連鎖などの途中を撮る機能も欲しい。固定秒数の待機を各ゲームで書く手間と撮り逃しが減る。
- **実入力録画の共通化**。InputEventの押下・解放、固定フレームでの録画、終了前の音声解放、フレーム一覧と末尾画像まで一括で扱うもの。盤面を書き換える演出確認と、通常入力だけの確認を区別できるとよい。
- **音声終了処理の検査**。通常終了、複数のquit-after、Movie Maker終了を実行し、終了コードとログ全文からリークを検査するもの。音声停止後に毎フレームの更新から再生が復活するケースを含めたい。
- **証拠画像の公開とPR反映**。ファイルのハッシュを記録し、変更した画像だけPUTSへ公開、公開内容を照合してPR本文を生成するもの。今回の`upload-evidence.py`と`render-pr.py`を毎回作らずに済む。
- **Web接続・撮影の診断**。CDP疎通、ページ起動、PNG/JPEG転送を別々に検査し、期限付きで失敗箇所を示すもの。ブラウザ全体を触らず、自分のセッションだけを回復できるとよい。
- **CI artifact取得の進捗と検証**。無出力で待つ代わりに取得済み容量を示し、ZIP整合性検査、画像一覧、動画フレーム抽出、ログ検査まで行うもの。

落ち物パズル向けには、到達可能な配置を返す探索と、盤面の消去・落下・連鎖の期待値を並べる検査例も再利用できる。ただし別ジャンルの共通基盤にまで広げる必要はない。

## 4. 素材の準備方法と使い勝手

画像は`games/blockpuzzle/scripts/dev/generate_assets.py`で独自SVGとして生成した。精霊4種とおじゃま1種は別ファイルにし、角・葉・星・しずく・歯車で輪郭から見分けられるようにした。背景3層、パネル、キーアート、ロゴを合わせて11画像。色だけを変えたキャラにはしなかった。

SVGの手続き生成は、小さな盤面で読める顔と輪郭、統一した配色、サイズ変更、再生成に向いていた。外部画像を探して世界観と解像度を揃える作業を避けられた。一方、複雑な芝居や描き替え式のアニメーションは得意ではない。今回は独立した絵をAnimationPlayerで伸縮・回転・移動・退色させた。見た目の方向は「夜の温室とベクターの精霊」で、写実的な立ち絵や多数の描き替えフレームは採用していない。

BGM4曲とSE8種も同じPythonスクリプトで生成した。22050Hz・16bit・モノラルPCMで、FM風の鐘、倍音、低音、ノイズ打楽器、残響を重ねた。BGMはタイトル・プレイ・危機・結果で旋律とテンポを変え、ループの残響を先頭へ折り返した。連鎖時の音程変化は再生側でも付けた。

手続き音源は出典を明確にでき、操作音を短時間で揃え、長さや音量をコードで調整しやすかった。ただし、波形と録画の音声ストリームの検査だけでは音楽としての良さや長時間聴いたときの疲れを評価できない。今回、聴感評価は未検証なので「音楽の品質まで確認できた」とは言えない。

フォントは既存の`games/cardbattle/assets/fonts/`からNoto Sans JPとOFL全文を複製した。出典とライセンスがすでに揃っているため、再調達より扱いやすかった。字体データは変更せず、ロゴだけfontToolsでアウトラインに変換した。素材一覧・生成方法・元のフォントURLは`assets/CREDITS.md`に記録した。

素材サイトや画像・音声生成サービスは未使用のため、それらとの速度・品質の比較を今回の実績としては述べられない。

## 5. 動作確認の方法、効いたことと不足

**headlessのselfcheck**では、同色4個の消去、隣接おじゃま、重力、2連鎖、指数的な得点、壁蹴り、CPUの到達経路、保存データ解釈、2本先取、時間切れなどを既知の盤面と期待値で検査した。入力盤面を変えない純粋関数にしたことで、表示の揺れに影響されず原因を絞れた。

**実入力のintegration.gd**では、本番シーンへキー、パッドボタン、パッド軸、マウスのInputEventを投入した。InputMapの定義確認だけでは分からない、メニュー確定、回転、長押し移動、マウスクリック、再戦時の表示スコアを確認できた。ただし、物理ゲームパッドの接続や機種固有の軸割り当ての検証にはならない。

**screenshot.gd**では実描画で23枚を撮影し、全画像を目視した。タイトル・対戦・ひとりで・遊び方・一時停止・ラウンド結果・勝敗・タイトル復帰に加え、遷移、着地、連鎖、おじゃまの途中と終了を撮った。アニメーションは5キャラそれぞれに、待機・移動・着地・被害・消去の5動作を並べ、各動作の開始・途中・終了を1枚にした。消去の最後にキャラが残らないこと、着地のつぶれ、被害の色変化を比較しやすかった。

連続フレームの一覧は姿勢・色・消滅の確認に効くが、3時点だけでは補間の滑らかさや体感速度を十分に評価できない。その補完に実プレイ録画を使った。また、演出用の既知盤面を直接設定した撮影は、通常入力でその場面へ到達した証拠とは分けて扱った。

**movie**は通常起動からタイトルまで約5秒を録画し、一定間隔の画像と末尾を目視した。**movie-play**は通常の盤面と抽選列を変更せず、現在の状態を読んで実キー入力を送るシナリオで26.03秒を録画した。最終実行では24回固定・10回消去し、2秒間隔の一覧と末尾を確認した。静止画だけでは分からない通常進行中の連鎖とおじゃまの流れを追えた。ただし、抽出フレーム間だけに起きる瞬間的な崩れをすべて否定できる方法ではない。

**終了検査**は、自分の実ウィンドウの通常終了と、quit-afterの1・8・30・120フレーム終了を確認した。どれもexit 0で、ObjectDBやresources still in useのリーク警告はなかった。ローカルの最終検証ログは全文を検査し、警告・エラーがないことを確認した。

**CI artifact**も使用した。最終CIは全31ジョブ成功。artifactの23PNGと約5秒のMP4を取得し、0.5秒間隔の10フレームと末尾を含めて目視した。macOSだけでなくLinuxのXvfb・llvmpipeでも表示を比較できた。撮影・動画ログにはV-Sync設定非対応のドライバ警告が各1件あったが、既存CIの許容対象で、ゲームのエラーや終了時リークはなかった。警告が存在しなかったことにはしていない。

最終CI: https://github.com/bannzai/godotpractice/actions/runs/34046939215

**webtunnel**では、最終コードのWeb版で実際にクリックして「ひとりで」を開始し、左右移動・回転・ハードドロップ、積み上がりによる結果表示、クリックでのタイトル復帰まで確認した。タイトル・プレイ・入力後・結果・復帰の5PNGをPRへ掲載した。再読み込み後のタイトルとIndexedDBの保存ファイルも確認した。今回のWebプレイは0点・0連鎖であり、非ゼロ記録のWeb再読込までは確認していない。非ゼロ記録への更新と保存データの解釈はローカルselfcheckで検査した。検証後にdownを実行し、専用セッションの終了を確認した。

Web実操作: https://github.com/bannzai/godotpractice/actions/runs/34046961990

Windows・Linux向け成果物はエクスポート成功を確認したが、それぞれのデスクトップでの手動プレイ、実機パッドの機種別互換性、音楽の聴感評価は未検証。Web版の成功をデスクトップ固有機能の代わりにはしていない。

## 6. Godot固有のハマりどころと回避策

- **型付き配列への代入**。動的なNode参照を通じて`wins = [0, 1]`を代入した撮影コードが実行時エラーになった。型付き配列を維持して`wins.assign([0, 1])`に変更した。lintやロード確認だけでなく、該当の撮影経路を実行する必要があった。
- **消去の論理状態と描画寿命**。論理盤面から消えた瞬間に表示ノードも破棄すると、膨らんで消える動作を最後まで見せられない。消去・重力・通常落下の段階を分け、消去演出中は表示ノードを保持した。消去0.48秒とヒットストップ0.06秒を考慮し、進行側の待ちを0.55秒にした。
- **InputEventの押下と解放**。移動は押下状態を毎フレーム読むので、イベントを押してすぐ解放するだけでは移動を確認できない。解放前にフレームを進めた。ゲームパッドAはGUIのui_acceptにも割り当て、プレイ中は回転として一度だけ消費してGUIへ流さないようにした。
- **音声停止後の再生復活**。毎フレームのBGM切替処理が終了準備中にも走る。音声のstopだけでは足りず、停止フラグで以後のBGM・SE再生を抑えた。通常終了ではstream解放後に描画フレームと0.2秒を待ち、Movie Makerでは終了16フレーム前に音声解放を始めた。quit-after経路ではノード終了時の処理で音声スレッドへの反映を待った。
- **headlessと実描画の違い**。headlessでは音声ノード生成を省き、ロジックを検査した。見た目と録画は描画付きで実行した。headlessの成功だけでは、Theme・フォント・アニメーションや実描画時の警告を判定できない。
- **Web起動と座標**。WebGL2が必要なのでwebtunnelはsoftware-webgl付きで起動した。Godot標準HTMLのstatus要素が消えることを起動判定に使ったが、最終判断はスクリーンショットで行った。ブラウザの1279×656のcanvasに1280×720のゲームが比率を保って収まるため、左右の余白と縮尺を含めてクリック位置を合わせた。
- **ログと実行環境の区別**。GodotのGUI・エディタ設定保存や、周辺ツールのTailscale・Keychainアクセスがサンドボックスで拒否されることがあった。ゲームの不具合と混同せず、必要な実行権限で再検証した。ログ出力は作業ディレクトリ内の絶対パスへ向け、終了コードと全文の両方を検査した。

最も再利用価値が高いと感じたのは、「純粋な盤面の期待値検査」「本番シーンへの実入力」「状態に合わせた演出撮影」「音声を含む終了経路の検査」を別々に持ち、最後に通常プレイとWebでつなぐ進め方だった。
