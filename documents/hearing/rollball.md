# rollball 開発の振り返り

対象は「ころころ工房」の実装、PR作成、画像添付、通常起動の確認まで。実行結果と残したファイルに基づく記録。PRは https://github.com/bannzai/godotpractice/pull/20 。この文書はコミットしない。

## 1. 開発の進め方

最初に作業指示書、AGENTS.md、PROJECT.md、issue #9、既存のGodotプロジェクトとMakefileを読んだ。受け入れ条件を、ゲーム本体・入力・素材・描画・ロジック・エクスポート・CIに分けた。

素材、純粋ロジックとselfcheck、部屋と配置をそれぞれサブエージェントに分担し、主担当は移動・巻き込み・カメラ・HUDを実装した。担当ファイルと関数の受け渡しを先に決めたことで、同じファイルの同時編集を避けられた。後半には既存担当へ統合検証、性能測定、独立レビューを依頼した。

実装順は次のとおり。

1. 体積から直径を求めるRunState、制限時間と勝敗、初期化を作る。
2. 玉の移動、接触回収、メッシュ付着、反発と脱落、追従カメラを作る。
3. 189個の小物・家具・部屋を統合し、タイトル・HUD・結果画面と音を入れる。
4. lint・起動・selfcheckを通し、通常移動による回収と勝敗をintegrationで検証する。
5. 実描画を見て照明を調整し、コミット・push・draft PR作成を行う。
6. 録画・性能測定・全エクスポート・CIを実行し、レビューで見つかった入力とカメラの不具合を直す。
7. 最終CIの成果物を目視し、PRをレビュー可能にする。追加指示で画像をアップロードし、make runも確認する。

詰まったのは、Godotのユーザーデータ領域への書き込み拒否、Dummy音声の終了時リーク、録画出力先の解釈、ゲームパッドのメニュー決定だった。ログ全文、verbose出力、実入力イベントで原因を絞った。最初のテストが通っても実操作レビューで矢印の割り当てと結果メニューの不具合が見つかったため、成功したテストだけで完成と判断しない進め方が効いた。

反省点として、draft PRは中核実装と最初の描画確認後に作った。もっと小さい完成単位で先に出せば、CI固有の問題を早く確認できた。画像添付とmake runの確認も、最初から完了手順へ含めるべきだった。

素材担当が実行したskillのスクリプトは `search-assets.sh`、`fetch-asset.sh --list / --pick`、`record-credit.sh`、`check-credits.sh`。`Rounded` と日本語subsetでフォントを探し、MPLUSRounded1c-Medium.ttfを取得した。

Godot skillの取得は `gh api repos/bannzai/castle/contents/home/.agents/skills/godot-development/SKILL.md --jq .content | base64 --decode`。雛形とexport templatesは既にあったため、scaffold・templates導入スクリプトは実行していない。コミット前・push前には電話番号差分検査スクリプトも実行した。

## 3. 欲しかったが無かったツール・skill・スクリプト

- **Godotの実入力検証の雛形**。アクション定義の存在だけでなく、矢印、スティック、十字キーでフォーカス移動後の決定まで送るもの。今回integration.gdへ自作した部分を再利用したい。
- **通常起動の撮影と終了をまとめた仕組み**。make runで起動した自分のプロセスだけを特定し、ゲーム内描画を保存し、ソースを変更せず正常終了できるとよい。今回はOS撮影が失敗し、一時コードの挿入・実行・復元が必要だった。
- **PR画像更新のスクリプト**。代表画面の収集、動画末尾の抽出、putsでのアップロード、PR本文の指定範囲の置換、公開URLと元画像の一致確認までまとめたい。今回は個別に実行した。
- **通常操作の録画と実時間性能測定の共通部品**。起動録画だけでは成長が見えない。movie-growthとperformanceをゲーム側へ追加したが、別ゲームでも流用できる枠組みが欲しい。
- **フォントの帰属情報の検査**。取得したOFL文書の著作権者がプレースホルダのままなら失敗させ、配布元情報と照合する機能が欲しい。
- **ゲーム別の知見ファイルを理解するCI対象判定**。rollballだけの作業でもknowledge文書を含むことで全9ゲームが実行された。共有物は変更せず改善案として残した。

skillそのものを今回新設・更新したわけではない。ゲーム内のスクリプトとdocuments/knowledge/rollball.mdに再利用候補を残した。

## 4. 素材の準備方法と使い勝手

| 素材 | 準備方法 | よかった点・限界 |
| --- | --- | --- |
| 玉・背景・家具・小物 | GodotのSphereMesh、BoxMesh、CylinderMeshなどをGDScriptで組み合わせた | 見た目・大きさ・衝突をすぐ調整でき、外部モデルのライセンス確認が不要。作り込みは単純な形状に留まる |
| アイコン | Codexで独自のball-mark.svgを記述し、rsvg-convertでPNG化して目視 | 色や輪郭を直しやすく、画風を統一できた。画像生成モデルは使っていない |
| BGM・SE | Python標準ライブラリで独自の音列と正弦波・倍音・減衰を合成 | 再生成が同じバイト列になり、短い効果音を揃えやすい。音楽的な豊かさや長時間聴いた快適さは数値検査だけでは評価できない |
| 日本語フォント | Google FontsのM PLUS Rounded 1c Medium、OFL文書を同梱 | LinuxでもOSフォントに依存しない。フォント約3.4MBと帰属情報の確認が必要 |

BGMは19.2秒のループ、SEは回収・衝突・成功・失敗の4種類。22050Hz・モノラルのWAVとして生成した。再生成前後のSHA-256一致、非無音、最大振幅、端点の連続性を検査した。これは音質の聴覚評価そのものではない。

フォント取得では、OFLの汎用文面に著作権のプレースホルダが残った。fontToolsで実フォントのnameテーブルを読み、Google FontsのMETADATA.pbと照合して著作権表示を補った。

素材源は https://fonts.google.com/specimen/M+PLUS+Rounded+1c 。画像・音源は独自制作で、外部のCC0モデルやBGM集は採用していない。imagegen、Gemini、Blenderは使っておらず、その使い勝手は今回評価していない。生成物を自動的にCC0とはせず、由来と生成手段をCREDITS.mdへ記録した。

## 5. 動作確認の方法と足りなかった点

**headless検証**ではselfcheck.gdでサイズ境界、体積保存、脱落、勝敗後の状態固定、再挑戦、シーン、素材記録を確認した。さらにintegration.gdで実シーンを動かし、通常の移動・接触から70個回収、直径3.204mのクリアを再現した。無操作180秒による失敗、キー・ゲームパッドイベント、棚裏のカメラも検証した。純粋ロジックだけではGUIのフォーカスとconfirmの競合を検出できなかった。

**screenshot.gd**では描画付きでタイトル・プレイ・成長・クリア・時間切れを保存し、PNGを目視した。白飛びを発見できた。半透明フッターの背景が文字欠けに見えたが、画素比較と別担当の目視では文字の消失はなく、不具合と断定しなかった。

**movieとアニメーション**では、標準movieの5秒は起動からタイトルの確認に使った。成長の検証には不足したため、同じ物理処理で自動移動するdemo.gdとmovie-growthを追加し、約20秒を録画した。ffmpegで2秒間隔のフレーム一覧を作り、玉の回転・付着物の増加・サイズとカメラの変化・回収演出・結果への遷移を確認した。成長途中のPNGも撮った。連続動画をプレイヤーで通して鑑賞した検証ではなく、抽出フレームによる目視なので、短いちらつきや音と演出の同期の保証には限界がある。

**CI artifact**は初回と最終コミットの両方をダウンロードし、PNG5枚とmp4からの抽出フレームを目視した。最終CIはrun 34014049315で全件成功。Linux/llvmpipeでの描画と日本語表示を確認できた。許容対象のVSync非対応警告と、ゲーム由来のエラーを区別した。

**性能**は固定fps録画とは別に、M4 Max・1280×720・VSync無効で実時間を測定した。最終Dummy音声の計測は189物体で平均452.86fps、成長中480.86fps。通常音声ドライバでの初回も平均145fps以上だった。両計測の差の原因までは切り分けておらず、他機種や全環境の性能を保証する値ではない。

**通常のmake run**も実行した。OS側のウィンドウ撮影が失敗したため、ゲーム内から描画を保存する一時コード付きで同じtargetを実行し、タイトルを目視、正常終了、元ソースの復元まで確認した。F11の全画面切替と復帰は描画付きの実キーイベントで確認した。

**webtunnelは未使用**。PROJECT.mdにSecretsとソフトウェアWebGLの前提が記載されており、今回はローカルとCI artifactを用いた。Webエクスポート自体は成功したが、ブラウザ上の実操作は未検証。Windows/Linuxもエクスポート成功と各OSの実機プレイは別。ゲームパッドは入力イベントで検証し、物理コントローラーの接続は確認していない。

**共有**はputs uploadのMarkdownをPRへ貼り、公開URLから取得した画像が元PNGと一致することまで確認した。最初はartifactへの案内だけで、PR本文の画像添付が抜けていた。ユーザーの追加指示後、代表5画面・動画末尾・通常起動の画像を掲載した。

## 6. Godot固有のハマりどころと回避策

| 問題 | 今回の対処 |
| --- | --- |
| headlessでは描画を評価できない | ロジックと描画の検証を分け、PNGは描画付きプロセスで保存 |
| 初回importやユーザーデータ書き込み | importを先に実行。sandboxで標準データ領域が拒否された場合は、許可された環境で再実行 |
| Dummy音声でWAV再生後に終了時リーク | verboseでAudioStreamPlaybackWAV等を特定。Dummyでは再生せず、録音が必要なMovie Makerは例外化。通常終了でも音声を停止 |
| 録画パスの二重指定 | --path後の相対パスはプロジェクト基準。ゲームディレクトリからtmp/growth.aviへ出力 |
| 録画失敗でもexit 0になる場合がある | exit codeに加えてログ全文、成果物、末尾フレームの輝度を検査 |
| 特殊キー番号の誤り | 左がRight、右がPageUpになっていた。正しい値へ直し、実InputEventKeyで回帰検証 |
| ゲームパッドで選択と決定が食い違う | ui_acceptへAを追加するだけでは解決せず、未処理confirmをフォーカス中のButtonへ渡して入力を消費 |
| 棚の裏で玉が隠れる | カメラ座標の壁内制限だけでは不十分。視線のraycastで家具を検出し、手前へ寄せる |
| 成長と大量の付着物の物理負荷 | 取得ボディを解放し、表示だけを玉へ付着。球の衝突半径を更新 |
| 明るい材質の白飛び | 環境光と指向性ライトを実描画を見ながら下げる |
| 日本語のOS依存 | フォントを同梱しThemeへ設定、OFLもexport対象へ含める |

Godot以外にも、putsはsandbox内でKeychain取得に失敗したが、許可された実行で成功した。公開画像の検査はPython urllibで403となり、curlでは取得できた。ウィンドウ撮影の失敗原因は断定せず、ゲーム内描画で検証した。
