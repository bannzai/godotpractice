# モンスター収集RPG「こもれびの調査隊」開発の振り返り

対象は issue #2 の実装から、PR の画像掲載と通常起動の追加確認まで。実行ログ、実装、素材クレジットを照合して記載した。以下の相対パスはこの worktree の直下を基準とする。

## 1. 開発の進め方

1. 作業指示書、issue #2、プロジェクトの制約と受け入れ条件を読み、オリジナルの町・草むら・モンスター6種・隊長戦という構成を決めた。Godot の開発手順と素材の扱いを skill で確認した。
2. 種族・技の定義を `Catalog`、進行状態・戦闘・保存を `Game` autoload、地形と描画を `QuestWorld`、画面と操作・演出を `main.gd` に分けた。先にモンスターID、素材パス、マップ座標、建物の入口、戦闘イベントの受け渡しを揃えた。
3. ロジック、素材、フィールドを3つのサブエージェントに担当してもらい、親はUIと統合を進めた。担当ファイルを限定し、Godot のインポートと全体検証は親側でまとめた。素材待ちの間も既知のパスと寸法で画面を作れた。
4. タイトルから探索、遭遇、戦闘、捕獲、手持ち・預かり、回復、保存、全滅・クリアまでを接続した。その後、選択した先頭個体を戦闘開始で上書きしてしまう問題、保存の異常入力、壁の中への復元などを修正した。
5. ロジック検証に地形の到達可能性と実入力の検証を加えた。画面を撮影しながら、モーダルの背面操作、描画順、ゲームパッドの決定、Tabの取りこぼし、全画面切替の待機を修正した。
6. 音声再生中の終了警告と、撮影画像の不要なインポートを解消し、ローカル検証・録画・各OSとWebのエクスポートを実施した。commit・push・PR作成後、CIの画像と動画も取得して確認した。PRはレビュー可能な状態にしたが、マージはしていない。
7. 追加依頼で代表PNGと動画末尾の画像を `puts upload` し、PR本文に9枚を掲載した。さらに通常の `make -C games/monsterquest run` で実ウィンドウの生成と正常終了を確認した。通常ウィンドウそのものの画像取得はmacOSの画面収録権限に阻まれ、その回のタイトル表示は未検証としてPRに明記した。

詰まった時間が大きかったのは、ゲームの計算式よりもGUIの入力配送と音声の終了処理だった。宣言したInputMapやheadlessの起動成功だけでは分からず、本番シーンへ入力を送り、終了時を含むログ全文を調べることで原因を絞れた。並列化は素材・地形・ロジックで有効だった一方、共有APIや状態の意味を親が先に揃え、統合時に見直す作業は必要だった。

| 独自素材生成の検証例 | SVG透過、WAV形式・音量、再生成ハッシュ、生成物のクレジットの検査を個別に組んだ。`game-asset-search` に一式の例があると使いやすい。 |

## 4. 素材の準備方法と使い勝手

### 画像

`scripts/dev/generate_assets.py` でSVGを生成した。モンスター6体は192×192、主人公は48×48、地形は48×48の6タイルを横並びにした。丸い輪郭、共通の紺色の線、柔らかい配色をコードで揃えた。既存作品の画像や画像生成APIは使っていない。

小規模な2Dゲームでは、色・寸法・透過・輪郭を揃えやすく、待ち時間やAPI認証もない点が使いやすかった。再生成前後のSHA256一致とXMLの構文を検査できる。ImageMagickで一覧画像を作り、見た目も確認した。一方、ポーズの多いキャラクターや複雑な描き込みではコード作成の負担が増える。今回は単一画像をGodot側で動かす演出なので成立した。ラスター生成サービスとの品質比較は行っていない。

透明度検査では、ImageMagickの背景指定により出力が変わった。明示的に `-background none` を指定し、各モンスターの四隅のalphaが0であることを確認した。

### BGM・SE

同じPythonスクリプトの `wave` / `math` / `struct` による加算合成で、探索・戦闘の16秒BGMと、攻撃0.35秒、捕獲・回復各0.9秒のSEを生成した。22050Hz・16bit・モノラルのPCM WAVで、外部録音や既存曲は使っていない。

短い音や繰り返しのBGMを再現可能に作れ、画像と同様に生成元を残せる点がよかった。作曲・音色設計の豊かさを自動で得られる手段ではなく、音楽的な品質は別途聴いて評価する必要がある。今回の音声確認はWAV形式・長さと、録画音声に信号があることの検査が中心だった。録画の測定値は平均-40.1dB、最大-29.0dBであり、これだけで聴感上の音量バランスやループの自然さを検証したとは扱っていない。

### フォントとライセンス

Google FontsのM PLUS Rounded 1c Regularを `game-asset-search` の検索・取得スクリプトで入手した。候補を一覧してファイルを選べるため、ブラウザでダウンロードを繰り返さずに済んだ。日本語UIを同じフォントで揃えられた。

取得元:
https://fonts.google.com/specimen/M+PLUS+Rounded+1c

フォント内部の著作権情報を確認し、OFLの著作権表示とライセンス全文を同梱した。各素材は `assets/CREDITS.md` に素材名・作者・URL・ライセンス・改変・生成手段を記録した。独自生成物を根拠なくCC0とせず、プロジェクトのオリジナル生成物として記録した。記録漏れ検査と、exportへのOFL・CREDITS同梱も確認した。

## 5. 動作確認の方法と限界

| 方法 | 使用状況・効いた点 | 足りなかった点 |
| --- | --- | --- |
| headlessの起動確認 | 使用。シーン・スクリプトのロードと `monsterquest boot`、終了コード、ログ全文の警告・エラーを検査した。 | 描画やフォーカスの見た目は分からない。 |
| headlessのselfcheck | 使用。相性、既知のダメージ、行動順、経験値・技習得、捕獲成功/失敗、預かり、交換、全滅・クリア、保存の正常/異常系を検査した。 | 画面の崩れや、実機固有の入力・音声は分からない。 |
| 地形・実入力検証 | 使用。BFSで歩行セル・草むら・隊長の隣への到達と入口往復を確認。キーボード・パッドのイベントを本番シーンへ送り、開始・移動・手持ち・先頭交代・対話・攻撃まで確認した。 | ゲームパッドは合成したイベントで、USB/Bluetooth接続の実機認識は未検証。 |
| `screenshot.gd` | 使用。本番シーンの状態を整えて14画面を描画し、viewportからPNG保存して目視した。攻撃途中やモーダル、結果画面を再現可能に確認できた。描画付き実行ではF11往復も確認した。 | 状態を直接設定して撮る画面もあり、画像だけでは到達経路の正しさを証明できない。ロジック・入力検証を併用した。 |
| `make movie` | 使用。30fps・150フレームの5秒録画をmp4に変換し、毎秒の画像と終了付近の画像を目視した。輝度の自動検査もあり、真っ黒な起動動画を成功にしにくい。 | 操作なしの起動動画なので、戦闘アニメーション全体の録画にはなっていない。輝度だけではUIの正しさは判定できない。 |
| CI artifact | 使用。全28ジョブ成功を確認し、LinuxのXvfb・llvmpipeで作られたPNG14枚とmp4をダウンロードしてローカルと同様に目視した。 | 実機GPUや各OSの配布バイナリの起動確認をすべて代替するものではない。 |
| webtunnel | 未使用。Webエクスポートは成功したが、ブラウザ上で操作していない。 | WebGL・ブラウザ入力・ブラウザ固有の音声挙動は未検証。 |
| 通常の `make run` | 使用。`Godot --path .` の実ウィンドウ生成、bootログ、正常終了を確認した。 | macOSの画面収録権限がなく、その起動ウィンドウのタイトル表示は目視できなかった。専用撮影によるタイトル確認とは区別した。 |

アニメーションは、実際の攻撃処理を開始して0.25秒後にPNGを撮り、移動・ダメージ表示の途中を目視した。その後 `main.busy` が解除されるまで待ち、演出の終了も検査した。入力テストからも攻撃を起動して完了まで追った。これにより途中描画と処理の停止は検査できたが、戦闘全体の滑らかさ、捕獲演出の全フレーム、音と動きの同期を動画で通して評価したわけではない。

https://github.com/bannzai/godotpractice/actions/runs/34014076527

## 6. Godot固有のハマりどころと回避策

| 実際に遭遇・対応した点 | 回避策・次回への教訓 |
| --- | --- |
| ゲーム用の `interact` にAボタンを足してもGUIのButtonが反応しない | 今回の実行環境では既定の `ui_accept` にパッドAがなかった。`ui_accept` と方向の `ui_*` に必要なキー・ボタン・軸を明示し、実際のButtonへ入力を送って確認した。 |
| Tabがメニュー処理まで届かない | GUIのフォーカス移動に先に消費されていた。メニュー開閉は `_input` で扱い、現在の状態に応じて処理するようにした。 |
| モーダルの背面ボタンを押せる、主人公が前面に飛び出す | 背面ボタンを無効化してフォーカス対象から外し、モーダル先頭へフォーカスを置いた。プレイヤーの高い `z_index` も見直した。単に上から描くだけでは入力は遮断されない。 |
| macOSのF11往復テストで2回目が失敗 | 全画面切替にはOSのアニメーションがあり、0.2秒待機では短かった。モード変更を待ち、次の入力まで1秒置いた。headlessでは全画面テストを行わない。 |
| `--quit` / `--quit-after` 終了時にWAV再生リソースのリーク警告 | 起動時の再生開始を2フレーム待つ。録画は終了12フレーム前に音声停止し、通常終了時も停止後に待機する。音声由来の警告を無視するのではなく終了手順を直した。 |
| `.gitignore` の `tmp/` がGodotの素材走査を止めない | 撮影PNGがインポート対象になっていた。`tmp/.gdignore` と `build/.gdignore` を作り、exportでも `tmp/*,build/*,scripts/dev/*` を除外した。GitとGodotの除外は別設定。 |
| JSONから読む数値の型と不正データ | 数値はfloatとして読み込まれるため、整数性・境界・必須項目・不明キーを検証してからintに戻した。種族と歩行可能座標も検査し、失敗時は現在の冒険を維持した。保存は一時ファイルからrenameし、検証用保存先はプロジェクトのtmp内に置いた。 |
| headlessで見た目を検証できない | selfcheckと描画付きの撮影を分けた。ローカルはGL Compatibility、CIはXvfbとllvmpipeで描画した。 |
| Godotの `user://` ログ出力と実行環境の権限 | 通常起動時にプロジェクト外のユーザーデータ領域への書き込みが必要だった。必要な実行権限を付けて同じ起動コマンドを実行した。テスト用の保存データはtmpに閉じ、通常セーブとは分離した。 |

音声終了問題の調査時に参照した既存issue:
https://github.com/godotengine/godot/issues/76745

地形はGodot 4系の `TileMapLayer` と `TileSetAtlasSource` で実装した。旧 `TileMap` への移行作業が発生したわけではなく、最初から現行APIを選んだ判断である。

Godot以外では、`puts` のKeychainアクセスが制限下で失敗し、必要な権限で再実行してアップロードできた。公開画像の確認もPythonの取得では403になったが、`curl` で取得して内容を照合できた。macOSの画面収録権限は別の制約であり、実ウィンドウの撮影は未解決のまま検証範囲を明記した。
