# boardrogue 開発ヒアリング

対象は今回新規実装した「宵の陣」。削除済みの旧実装についての記録とは区別する。実装・検証の当時のツール出力と、今回読み直したローカルログを根拠に記載した。

## 1. 開発の進め方

### 作成した順序

1. 指定された `boardrogue-idea.md`、プロジェクト指示、Gitの状態を確認した。企画書のコマンドから元の札棋のルールをGitHub APIで取得した。
2. `games/boardrogue/` が存在しない一方、知見ファイルには旧実装の記録が残っていた。Git履歴で「やり直しのため削除」が確認できたため、旧コードや画像を復元せず、新しく作った。
3. 企画の中心を、小さな盤面・王への直接攻撃・将軍の道と希少札・相手の台詞に置いた。3×2・5×2は盤全体の大きさと解釈し、自陣と敵陣を各一行、王を盤外に配置した。五夜の遠征を完走する構成にした。
4. 戦闘エンジンと素材制作を独立したサブエージェントへ委譲し、本体では遠征状態・保存・画面・入力を実装した。先に札IDと戦闘APIを合わせ、各担当の編集範囲を限定した。
5. 戦闘、街道、戦利品、勝敗、手ほどき、札帳、音切り替えをつないだ。画像・音声が揃ってからGodotへインポートし、起動・実入力・描画を確認した。
6. 不正な操作の拒否、治癒上限、保存データの整合、入力座標、音声終了処理を修正した。敵の一手番を一括処理すると読み取りにくいため、一枚ずつ配置・公開・攻撃する形に変更した。
7. デスクトップ向け書き出し、差分検査、コミット・push・PR作成、検査済み画像4枚の添付まで行った。知見ファイルには現在の実装の記録を先頭に追加し、従来の記録を削除済み実装の履歴として区別した。

### 詰まった点と解決

- 初期の戦闘テストが成功していても、伏せ札の移動・攻撃と非隣接交換を拒否する条件が不足していた。実ファイルと画面の案内を照合して発見し、拒否した後も伏せ状態や交換権が保たれる回帰テストを加えた。
- 敵を一操作ずつ表示するため、一時的にUIへCPU判断を複製してしまった。`enemy_step()` に判断を集約し、一括実行の `play_enemy()` も同じ入口を繰り返す形へ戻した。
- 撮影用入力が届かなかった。Controlがイベントの座標ではなくOSの現在のマウス位置を参照していたため、イベントの `position` を使うよう修正した。
- サンドボックス内の描画付き起動は終了コード134になった。許可されたサンドボックス外の同じGodotコマンドで撮影できた。別の検証経路に置き換えて成功扱いにはしなかった。
- 書き出しと撮影を同時に動かした回では描画待ちが進まずタイムアウトした。書き出し完了後に撮影だけを実行すると正常終了した。同時実行が直接の原因かまでは特定していない。

## 2. 使ったツール・skill・コマンド

### ツール

- `functions.exec` と `exec_command`：ローカルコマンド、独立した読み取りの並行実行、実行結果の確認
- `apply_patch`：GDScript、設定、Makefile、ドキュメントの作成・修正
- `collaboration.spawn_agent`・`send_message`・`followup_task`：戦闘と素材の委譲、API調整、回帰テスト追加。報告だけでなく、成果物とログを本体で確認した
- `view_image`：Godotが撮影したPNGの表示確認と、アップロード前の目視検査
- `write_stdin`：自分が起動したコマンドの終了コードと残りの出力の受け取り

### 実際に参照・使用したskill

- `commit-create-pr`：差分点検、PR本文、セッション再開コマンド、画像添付の手順を参照した。プロジェクトの変更範囲制約に従い、共有workflow追加などは行わなかった。
- `pr-attach-screenshots`：画像の機械検査、目視検査、PUTSへのアップロード、公開画像のハッシュ一致、PR本文への埋め込みに使用した。
- 電話番号検査は `github-repos-phone-number-check` の `check-diff-for-phone-numbers.sh` を直接実行した。リポジトリ全履歴の棚卸しskillを一式実行したわけではない。

`godot-development` と `game-asset-search` は参照先の存在を探したが、その時点で確認したローカルのパスには存在しなかった。使用済みskillには含めない。画像生成サービス、ブラウザ操作skill、webtunnel、コードレビューskillは使っていない。

ほかに `python3` で素材生成・音源検査、`ditto -x -k` でmacOS書き出し物の展開、`git diff --cached --check`、電話番号検査の `--staged`・`--unpushed`、`git commit`・`git push`・`gh pr create`・`gh pr view`、`puts ls --number 1`、画像添付スクリプトを実行した。残った撮影プロセスはそのコマンド行に限定して `pkill` で停止した。

## 3. 欲しかったが無かったツール・skill・スクリプト

- **Godotをこの環境で検証する入口**：サンドボックス内でできる処理、ウィンドウ表示に必要な実行権限、ログ出力先、専用保存先、タイムアウト、終了時のプロセス停止をまとめた手順があるとよかった。今回は個別に切り分けた。
- **Godotの実入力検証部品**：Viewport座標でのクリック、キー押下と解放、描画完了待ち、表示倍率変更、失敗時の証拠保存を共通化できると、撮影・入力検証スクリプトを毎回書かずに済む。ゲームの画面構成を固定するテンプレートではなく、入力と観測だけを担う部品が欲しい。
- **CPUの逐次実行と一括実行の整合検査**：同じseedで最終状態とイベント列を比較する小さな検証例があれば、演出追加時に判断ロジックをUIへ複製する失敗を防ぎやすい。
- **素材のまとめ検査**：画像サイズ・透過・小さい表示での識別、音源の無音・ピーク・ループ境界、ライセンス同梱を一括点検する道具が欲しかった。今回はXML解析、音声数値検査、Godotの実画面を別々に確認した。
- **書き出し前の設定検査**：macOS universalの必須設定、エクスポート対象からの開発スクリプト除外、OFL同梱を先に検出できると、書き出してから設定不足を直す往復を減らせる。

これらは今回の作業からの候補であり、新しい共有skillや外部連携を作成したわけではない。

## 5. 動作確認の方法

### 何をどう確認したか

- **戦闘の純ロジック**：`selfcheck.gd` で3列・5列それぞれの配置、移動、公開、交換、戦力比較、相討ち、奇襲、治癒、王撃破、捨て札再循環を検証した。CPU対局は各8シード、合計16対局。札の総数が保存されることも確認した。
- **CPUの共通化**：`enemy_step()` を繰り返した結果と `play_enemy()` の盤・手札・体力・イベント列が一致することを確認した。守護札を対面の敵に対して伏せて維持する条件も検証した。
- **遠征と保存**：`runcheck.gd` で通常と将軍の分岐、希少報酬、報酬の重複拒否、最終勝利、敗北後の再開不可、保存復元、不正な型・小数・不整合の拒否を検証した。100シードを合法手だけで進め、最終仕様で制覇32回・敗北68回。途中の49回・51回は、守護札の伏せ維持を追加する前の結果である。
- **実入力**：描画環境で `inputcheck.gd` を実行し、18項目を確認した。マウスでの敵札撃破・前進・捨て場への移動、数字・矢印・Enter・R・Space・Kによる配置から王攻撃、メニューと手ほどきの背面入力遮断、音切り替えを検証した。
- **実画面**：`screenshot.gd` で14枚を撮影。表紙、手ほどき、街道、戦闘、配置、攻撃対象、王への被弾、敵手番後、札帳、五列、縮小ウィンドウ、報酬、制覇、敗北を確認した。1152×720でも画面全体が収まった。
- **書き出し**：Linux・Windows・macOSへの最終書き出しが正常終了し、最終ログにwarning/errorがないことを確認した。macOSの書き出し済みバイナリはheadlessで起動・終了し、終了コード0だった。
- **公開前点検**：差分の空白検査、電話番号検査、秘密情報の確認を行った。PRへ載せた画像4枚は機械検査と目視検査に合格し、アップロード後に公開画像とローカルのハッシュ一致を確認した。

### 効いた方法

- 合法手の成功に加えて、不正な入力を拒否した後の状態まで検査すること。
- UI関数を直接呼ぶだけでなく、`Viewport.push_input()` から入力を配送すること。座標の取り違えを実際に発見できた。
- 戦闘中の秘密情報を含むイベントを除去前に保存すること。消えた札の正体を後から画面に案内できた。
- 担当者の「成功」報告だけで判断せず、ログ全文・実行終了コード・変更ファイルを確認すること。
- ロジック用と描画用の検証を分け、表示確認用の盤面と自然なプレイ進行を混同しないこと。

### 足りなかった確認

- 100シードの遠征はロジック層の自動対戦であり、人がUIを操作して五夜を通して遊んだ結果ではない。面白さ・説明の理解しやすさ・実際のプレイヤーに対する難易度は保証できない。
- 五列の満員盤面、希少報酬、勝敗の代表画像は表示専用の状態を設定して撮った。これだけでは自然な到達を証明しないため、合法手の遠征テストと分けて記録した。
- 静止画で演出途中は確認したが、今回動画は録画していない。連続したテンポや音と絵の同期を映像全体で検査する手順は不足していた。
- Windows・Linuxの実行環境では、書き出したバイナリを起動していない。macOS書き出し物の確認もheadless起動までで、操作検証はGodot本体からソースを起動した環境で行った。
- 人が耳で聴く音質評価、ゲームパッド操作は未検証。ゲームパッド操作自体も今回実装していない。
- プロジェクトの指示どおり、CIとコードレビューは行っていない。

## 6. Godot固有のハマりどころと回避策

### サンドボックスと保存先

Godotの既定のユーザーデータ・エディタ設定はワークスペース外に作られる。初回にユーザーディレクトリやエディタ設定の作成で失敗した。ログは `--log-file` で作業ディレクトリへ出し、ゲームの検証保存先は独自の `--save-path` で分離した。ウィンドウ表示とエディタ側の書き込みが必要な処理は、許可された実行経路を使用した。

### 型付き配列

`Array[String]` を要求する関数へ、型を付けていない配列を変数経由で渡すと実行時に型不一致になった。入力テストのfixtureで発生し、デッキを `Array[String]` として宣言して解消した。検証コード自身の失敗が後続の盤面アクセス失敗を引き起こすので、最初のエラーを直す必要があった。

### Controlの入力座標

描画座標・イベント座標・OSマウス位置を混ぜない。Controlへ届いたクリックは `event.position` で判定し、検証側は `root.push_input(event, true)` でViewport座標を指定すると、実入力とテストが一致した。画面の拡縮も別途撮影して確認した。

### 描画完了待ち

PNG取得にはheadlessを使わず、描画付き起動で `RenderingServer.frame_post_draw` を待った。描画が進まなくなる場合に終了できるよう、撮影・入力スクリプトには45秒のタイムアウトを入れた。タイムアウトした回を撮影成功には含めず、正常終了した単独実行の画像で確認した。

### 音声再生中の終了

`--quit-after` で即時終了すると、AudioStreamWAVとAudioStreamPlaybackWAVが残る警告が出た。`--verbose` の出力で対象を特定し、音声ノードの `_exit_tree()` で再生停止・stream参照解放を行い、音声スレッドへの反映のため60msだけ同期で待つようにした。同じ起動・終了で警告が消えることを確認した。終了時は次のフレームに依存するawaitでは処理を完了できない。

### macOS universalのエクスポート

GL Compatibilityの2Dゲームでも、universal書き出し時にETC2/ASTCのインポート設定不足で拒否された。`textures/vram_compression/import_etc2_astc=true` を追加した後、macOSの書き出しが正常終了した。レンダラは変更していない。

### リソースと配布物

`.import` と `.uid` はコミットし、`.godot/` と `build/` は除外した。開発用検証スクリプトはエクスポート対象から除外し、リソースとして自動では含まれないOFL全文とクレジットはinclude filterで明示した。
