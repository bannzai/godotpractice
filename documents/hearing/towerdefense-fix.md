# towerdefense 手直しラウンドの開発ヒアリング

## 1. 開発の進め方

### 着手から実装まで

1. 最初に `AGENTS.md`、`documents/PROJECT.md`、issue #39、前回の PR #49、既存の `documents/knowledge/towerdefense.md` とヒアリング資料を読み、前回までの受け入れ条件と今回だけの方針を分けた。
2. `make towerdefense-run` で変更前を実際に操作し、タイトルからすぐ戦闘へ入り、光る地点・塔選択・襲来開始の関係が初見では読み取りにくいことを確認した。変更前のタイトル、準備、プレイ画面も比較用に保存した。
3. 見た目の核を先に決めた。OpenAI image_gen で塔4種、敵5種、森から灯砦へ続く横長風景の3枚を生成し、PNGを先にコミットした。実装と同時に画像を作るのではなく、採用する素材を確定してから表示領域や配色を合わせた。
4. 素材の基盤を組み込んだ。Zen Kurenaido と OFL、生成物のクレジット、固定seedで合成する環境音、画面全体の織物シェーダー、生成画像を読む AtlasTexture を追加した。
5. ゲームの導線を変えた。タイトルと戦闘の間に正式な地図状態を追加し、初回4手順の指南、スキップと既読保存、地点・紋章盾・襲来開始のハイライト、建設後の姿と残金、強化前後、売却後資金、選択不可理由を実装した。画面下の共通操作ガイド行は削除した。
6. 実装直後から `make lint`、`make test`、`make screenshot` を繰り返し、ロジックと画面を並行して直した。その後、起動録画、実操作録画、デスクトップ全OS向けエクスポート、Webエクスポート、通常ウィンドウ操作へ広げた。
7. 変更前後、他ゲームとの識別、全キャラクターの全動作、指南と選択不可理由を比較画像にまとめ、`puts upload` でPR本文へ載せた。実装上の知見は `documents/knowledge/towerdefense.md` に記録した。
8. CI artifact と webtunnel を最後の確認ではなく、追加の不具合検出経路として使った。Web録画の87キーフレームを確認したところ、結果画面の右端320pxだけ灰色になる不具合を発見した。`Board` が横960pxまでで、結果画面も残りの領域を塗っていなかったため、同じ羊皮紙色のパネルで右端を埋めた。修正後にローカル、CI、webtunnelをもう一度確認してからPRを ready for review にした。

### 詰まった点と解決方法

- 敵5種の生成画像は余白と上下位置が不均等で、画像を単純に5等分すると隣の敵が混ざったり小鬼群が欠けたりした。実画像を拡大して種類ごとの切り出し矩形を個別に決め、塔と敵で表示高さも分けた。全9種を同じ接触シートに出して切り出し結果を確認した。
- 1枚絵にはアニメーションの差分がない。待機・移動・攻撃・被弾・消滅ごとに、位置、拡縮、回転、色、透明度を6フレームで変え、刺繍人形らしい揺れとして成立させた。9種×5動作×開始・途中・終了を一覧化して、止まって見える動作や欠けを確認した。
- GL Compatibility で画面全体を `SCREEN_TEXTURE` から読み直す織物シェーダーは、再帰的に画面を写したような残像になった。画面をサンプリングせず、透過した縦糸・横糸だけを最前面の ColorRect に描く方式へ変えた。
- タイトルから地図へのフェード直後に自動撮影すると、地図だけ暗い状態で保存された。遷移完了後0.4秒待ってから撮影するようにした。
- 全キャラクター撮影で敵側のフラグを渡しておらず、敵の欄が塔用atlasを参照して空になった。キャラクターごとに塔か敵かを明示して撮影するよう修正した。
- macOSの通常ウィンドウと音声出力はサンドボックス内では失敗した。headless検証は自己完結したGodot設定で続行し、GUIと `afplay` は必要な実行権限を得て検証した。失敗したログを成功扱いにはしていない。
- webtunnel録画のダウンロードが終盤で接続リセットになった。artifactの存在を確認して再取得し、最終的に47分40秒の録画を取得した。agent-browserでは古いCDP接続のキャッシュと多数のデーモンによるリソース不足も起きたため、固有セッション名を使い、必要時は同じChromiumへ直接CDP接続して実キー入力とJPEG撮影を続けた。デーモン削除は dry-run の結果、最近使われたものしかなかったため実行しなかった。

## 2. 使ったツール・skill・コマンド

### skill

- `godot-development`: Godot 4.7の起動、headless実行、selfcheck、スクリーンショット、Movie Maker、エクスポート、ログ検査の方針に使用した。
- `game-asset-search`: 画像生成を素材経路として選ぶ判断、生成物・フォント・音声のライセンス記録、透過・寸法・目視検査の基準に使用した。
- `imagegen`: 塔、敵、横長風景を入力画像なしで生成した。用途、対象数、並び順、余白、透過、限定色、刺繍技法、禁止事項までプロンプトに明記した。
- `webtunnel`: GitHub Actions runnerでWebエクスポートを配信し、Tailscale越しにChromiumへ接続するために使用した。Godot向けの座標変換手順も参照した。
- `agent-browser`: Web版への接続、キー入力、スクリーンショット、ブラウザエラーとconsoleの確認に使用した。
- `video-frame-reader`: webtunnel録画から87キーフレームと接触シートを作り、長時間録画を見落としなく確認するために使用した。
- `gh-r2-image`: PR用画像を `puts upload` でR2へ置き、公開URLをPR本文へ埋め込むために使用した。
- `commit`、`commit-create-pr`、`update-pr-body`: 差分検査、個人情報検査、段階的なコミット、draft PR作成、PR本文更新に使用した。
- `write-adr`: 今回の判断が共有アーキテクチャの長期決定に当たるかを判定した。ゲーム固有の一回限りの表現変更だったため、ADRは作らなかった。
- `agent-browser-reaper`: agent-browserのプロセス状態を dry-run で調べた。削除対象がなかったため停止処理は行わなかった。

## 3. 欲しかったが無かったツール・skill・スクリプト

- 複数キャラクター入りPNGを解析し、各像の実寸・透明余白・重なりを一覧化して、等分可能か判定し、AtlasTextureの矩形候補と接触シートまで出すスクリプトが欲しかった。今回もっとも手作業が多かったのは敵atlasの切り出し調整だった。
- `screenshot.gd` の全画像、CI artifact、動画のキーフレーム、音量検査、WARNING / ERROR検索を一括で実行し、PR用の証拠一覧を生成する `make visual-check` 相当の仕組みが欲しかった。今回は複数コマンドと接触シートを手動で組み合わせた。
- Godotの画面遷移完了を待ってから撮影する共通ヘルパーが欲しかった。固定秒待ちは今回の0.4秒では安定したが、Tweenやマシン速度が変わると再調整が必要になる。
- webtunnelの録画取得に、途中再開、取得済みサイズの検証、接続リセット時の自動再試行が欲しかった。長時間録画の再ダウンロード待ちを減らせる。
- agent-browserが保持するCDP接続先の失効検出と、worktree単位の安全なデーモン整理が自動化されているとよかった。今回は固有セッション名、dry-run、直接CDP接続を使い分けた。
- 長いゲーム録画を「状態が大きく変わったフレーム」と「画面端の未描画領域」に分けて自動検出する視覚回帰ツールが欲しかった。キーフレーム化は有効だったが、最終判断は87枚の目視だった。
- 音について、形式・無音・クリッピング・平均/最大音量・ループ境界・スペクトログラムを一度に検査するゲーム素材向けスクリプトが欲しかった。音色の好みは人間の聴感が必要だが、機械的な確認はまとめられる。

## 4. 素材の準備方法と使い勝手

### 画像

- 新規画像はOpenAI image_genで3枚生成した。塔4種と敵5種は透過PNGの横一列atlas、地形は月夜の森、川と石橋、灯砦へ続く横長PNGにした。粗い亜麻布、太い毛糸、チェーンステッチ、平面的な横向き像、亜麻・茜・褪せた藍・煤茶・苔緑・黄土の限定色を共通指定し、文字、ロゴ、枠、透かし、既存作品の再現を禁止した。
- 3枚とも初回出力を採用でき、前回の手続きSVGよりも、背景・塔・敵の質感と物語性を短時間で揃えやすかった。特に横長風景は、タイトル・地図・戦闘を同じ旅程として結ぶのに効いた。
- 弱点は再生成しても同一バイト列にならないことと、複数キャラクターの寸法・余白が揃わないことだった。PNG自体を正として保存し、実画像に合わせた切り出し領域と目視検査を採用した。塔は4等分で使えたが、敵は個別調整が必要だった。
- 生成画像には入力画像を使っていない。OpenAIの利用規約URL、生成手段、プロンプト要点、Godot側で行った切り出し・シェーダー・アニメーション加工を `assets/CREDITS.md` に記録した。
- 前回の手続きSVGは、固定条件で再生成でき、セル境界、各コマの差、SHA-256一致を自動検査しやすい。一方、コードで描く単純形状が他ゲームにも現れ、固有性を出しにくかった。画像生成PNGは特色で優れ、手続きSVGは再現性と検査容易性で優れていた。

### BGM・SE・環境音

- 前回作成済みの5場面のBGM、塔ごとの発射SE、建設・撃破・拠点被害などのSEは維持した。外部の市販音源や録音素材は追加していない。
- 今回は風、旗布、焚き火、木の軋みをPythonで合成した16秒の環境音を追加した。固定seedなので同じスクリプトから同じ内容を再生成でき、外部素材の個別ライセンス確認が不要だった。
- `ffprobe`、`ffmpeg volumedetect`、生成スクリプトの検査で、WAV形式、長さ、非無音、非クリッピング、録画への収録を確認した。`afplay` でmacOSの再生開始も確認した。機械検査はしやすい一方、「世界観に合うか」「長時間聞いて疲れないか」は数値だけでは決められない。

### フォント

- Google Fonts公式のZen Kurenaido Regularを取得し、TTF、配布元URL、著作者、OFL-1.1全文を同梱した。禁止されていたZen Old Mincho、Noto Sans JP、M PLUS Rounded、従来の無名 `font.ttf` は使用箇所と生成スクリプトから外した。
- Google Fontsは配布元とライセンスが明確で、公開リポジトリへ同梱しやすかった。日本語の読みやすさを維持しながら手書きの巻物らしさも出せた。画像生成で文字まで作らず、文字はフォントで描画したため、誤字や解像度の問題も避けられた。

## 5. 動作確認の方法

### headless・自動検証

- `make test GAMES=towerdefense` で gdlint、import、起動、selfcheck、入力統合、指定フレーム終了をまとめて実行した。既存の全10ウェーブ、塔4種、敵5種、建設・強化・売却・勝敗・保存を維持しつつ、正式な地図状態、指南の初回表示、完了記録の冪等な保存、破損JSONから未読へ戻ることもselfcheckへ追加した。
- integrationでは実際のInputMapイベントとボタンクリックを使い、タイトルから地図、地図から準備、指南の地点選択・塔選択・建設・襲来開始、Qでのスキップを通した。状態関数だけを直接呼ぶselfcheckでは拾いにくい、入力とUIの配線確認に効いた。
- headlessはロジック回帰、リソースのロード、保存、終了時リークの検出に強かった。一方、織物の質感、文字の重なり、画面端の空白、生成画像の切り出しは判定できなかった。

### `screenshot.gd`

- タイトル、地図、指南4段階、建設プレビュー、選択不可理由、強化・売却プレビュー、準備、休止、通常戦闘、ボス、勝利、敗北、各演出を撮影した。
- アニメーションは塔4種と敵5種について、待機・移動・攻撃・被弾・消滅の各6フレームから開始・途中・終了を固定して撮影した。9種×5動作×3時点を1枚の一覧にまとめ、動作差、欠け、隣のatlas混入、空表示を目視した。単一のプレイ画面だけを見るより、全組み合わせを同じ縮尺で比較できたことが効いた。
- ローカルと最新CI artifactの双方で38枚すべてを接触シートにして目視した。自動撮影は再現性に優れるが、遷移中の暗転や、撮影用に高速化した戦闘と表示アニメーションの時間差を考慮する必要があった。

### movie・通常ウィンドウ

- `make movie` は起動からタイトル表示までを5秒録画し、真っ黒、初期描画崩れ、音声トラックの欠落を確認した。
- `make -C games/towerdefense movie-play` は実入力でタイトル、地図、指南、塔2基の建設と強化、3倍速、第4波までを録画した。2秒間隔のフレームと末尾を見て、静止画では分からない遷移と戦闘の進行を確認した。
- `make towerdefense-run` はmacOSの通常ウィンドウで、タイトル、地図、指南、建設、襲来、休止、タイトル復帰、Esc終了を実入力した。headlessでは確認できないウィンドウ描画と通常終了に効いた。
- movieは連続性と音声収録には効くが、5秒または30秒の定型録画だけでは10ウェーブ後の結果画面まで届かない。そこでwebtunnelの長時間実操作を併用した。

### CI artifact・webtunnel

- 最新CIではLinux/Xvfb/llvmpipe上の38枚と5秒録画をダウンロードした。全画像、録画の5フレームと末尾、AAC音声、ログ全文を確認した。ローカルmacOSだけでは分からないLinuxレンダリングと、PR headそのものの再現確認に効いた。V-Sync非対応は実行環境由来の既知警告で、それ以外のWARNING / ERRORやリークはなかった。
- webtunnelではWebエクスポートをrunner上のChromiumで開き、ゲーム状態を書き換えず、タイトルから地図、指南、建設、強化、3倍速、全10ウェーブ、結果まで実キー入力した。先行runはHP4で勝利し、修正後runは敗北結果まで到達した。
- 長時間録画をキーフレームへ分解したことで、短いmovieと代表スクリーンショットが見逃した「結果画面右端だけ背景がない」不具合を発見できた。修正後は最新Web画面、ローカル勝敗画面、CI artifactで右端まで確認した。
- Web版は実導線を最後まで通すのに強い一方、Web固有の描画・入力しか確認できない。フルスクリーン、物理ゲームパッド、デスクトップ固有の音声やウィンドウ終了は、通常ウィンドウやCIと役割を分ける必要がある。

## 6. Godot 固有のハマりどころと回避策

- **GL Compatibilityの画面サンプリング**: 全画面の `SCREEN_TEXTURE` を同じCanvasItem上で使うとフィードバック状の残像になった。全画面質感は、元画面を読まずに糸模様だけを描く透過オーバーレイにする。
- **TextureRectの横長背景**: 横長風景はコンテナ任せにせず `STRETCH_KEEP_ASPECT_COVERED` を明示する。タイトル・地図・戦闘で同じ画像を使う場合も、各画面の切り抜かれ方を撮影して確認する。
- **Tween直後の撮影**: 画面状態が切り替わってもTweenが終わる前は暗転が残る。固定待ちより、可能ならTweenの完了signalを待ってから `RenderingServer` の描画完了後に撮影する。今回は0.4秒待機で安定させた。
- **AtlasTextureの等分前提**: 生成画像の複数キャラクターは等間隔とは限らない。先に実ピクセルの境界を調べ、種類ごとの矩形を定義する。塔と敵で同じスケールを無理に使わず、全種類の接触シートで隣の像の混入と欠けを検査する。
- **1枚絵のSpriteFrames**: 元画像が1コマでも、同じatlas領域を複数フレームへ登録し、transformとmodulateをフレームごとに変えればアニメーションにできる。ただし、各動作が本当に違って見えるかを固定フレーム一覧で検査する必要がある。
- **色だけの状態表示**: 織物シェーダーと背景の色むらで選択色が埋もれた。二重枠、線幅、＋、斜線、四角、脈動、半透明プレビュー、理由文を併用した。アクセシビリティだけでなく、質感の強い画面でも有効だった。
- **初回指南の保存先**: 指南既読を戦闘の `new_run()` で消すと毎回出てしまう。戦績とは別の `user://` JSONへ保存し、同内容の再保存を冪等にする。テスト時だけ `res://tmp/` の専用パスへ差し替え、プレイヤーの実データを変更しない。破損JSONは安全側の未読へ戻す。
- **高速シミュレーションと表示時間**: スクリーンショット用にゲームを高速で進めると、ゲーム時間とTween・アニメーションの実時間がずれる。ボスや勝敗を撮る直前に表示ノードを同期し、死亡済みノードや過去の演出を残さない。
- **画面を部分ノードで塗る構成**: `Board` が960px、画面全体が1280pxのように担当範囲が分かれていると、特定状態だけ右端が未描画になり得る。タイトル・地図・プレイだけでなく、勝利・敗北・休止を含む全状態の画面端をCIと長時間録画で確認する。
- **headlessと音声**: headlessでは音声再生を開始しない構成にし、Movie Makerと通常起動では再生する。終了時はAudioStreamPlayerを停止し、stream参照を外して数フレーム待つ。`--quit-after` とEscによる通常終了を分けて検証し、ObjectDBやリソースのリーク警告をログ全文で確認する。
- **JoypadMotionの向き**: `InputEvent.is_action_pressed` は既定ではスティック軸の正負を厳密に区別しないことがある。方向入力には `exact_match=true` を使い、X/Y軸の正負を個別の入力イベントで検証する。
- **Web版の座標**: runnerのChromiumは1280×656でゲームの1280×720と縦横比が異なる。canvasの実表示サイズと左右余白からゲーム座標をブラウザ座標へ写し、クリック後の選択状態を画面で確認する。配信URLの8000番とCDPの9222番も混同しない。
