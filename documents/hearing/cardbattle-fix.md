# cardbattle 手直しラウンドの振り返り

## 1. 開発の進め方

### 進行順

1. `AGENTS.md`、プロジェクト文書、issue #8、前ラウンドのPRと知見文書を読み、維持するカードルールと今回変える表示層を分けた。
2. 変更前のゲームを `make cardbattle-run` で操作し、`make screenshot GAMES=cardbattle` でタイトル、遊び方、初手、対戦中を保存した。次の操作が右欄と画面下のキー一覧へ分散していること、連戦の現在地を示す画面がないこと、他ゲームと同じHUD構成に見えることを改善対象にした。
3. draft PRを早期に作り、まず調査結果と変更前画像を載せた。その後は生成素材、UI、知見の順に3コミットへ分け、各段階をpushした。
4. OpenAIの組み込み`image_gen`で、24体のモンスター、6種の魔法・罠、透明な共通枠、木製卓上の計32画像を参照画像なしで生成した。原本を目視してからImageMagickで実表示向けに縮小し、約87 MBを約25 MBにした。
5. カード定義と決闘ロジックは変えず、タイトルから招待状、額縁入りトーナメント表、決闘、結果へ進む表示層を作った。画面下の共通操作ガイドを廃止し、3段階の初回指南、選択可能な札の金色の脈動、選べない理由、次のフェイズ名、攻撃結果予告を対象の近くへ置いた。
6. 生成原画を共通枠へ合成し、24体の待機・召喚・攻撃・被弾・死亡を、原画の移動・回転・拡大・色変化で表現した。9種類の盤面演出も維持した。
7. selfcheckと撮影シナリオを拡張し、全30札、24体の5動作、9演出、指南、選択可否、勝敗、次戦解放を機械検査と画像で確認した。ローカルの全ターゲットを通した後、Web実操作とCI artifactを確認した。
8. 変更前後、近いジャンルの3ゲームの識別比較、指南、全札、連続フレーム、実入力録画、Web実操作を9枚に整理し、`puts upload`経由でPR本文へ添付した。全CI成功を確認してPR #67をReady for reviewにした。

### 詰まった点と解決

- 生成原画は縦長を指示しても4:3になった。重要な顔や武器を端へ置かないプロンプトにし、Godotの`STRETCH_KEEP_ASPECT_COVERED`で共通枠の窓へ切り抜いた。タイトル、対戦表、手札、盤面で同じ合成ノードを再利用した。
- 親`Control`の`_draw()`に描いた選択不可理由が、子`TextureRect`の原画の後ろへ隠れた。原画、共通枠、状態表示を別のCanvasItemにし、状態表示を`z_index = 3`へ上げた。指南も盤面ハイライト、紙面、説明の順にz-indexを分けた。
- UIを同一フレームで解放・再構築すると、撮影画像へ旧Controlが1フレーム残った。保存前に描画を2フレーム待つようにした。
- UI追加で`main.gd`がgdlintの1000行上限を越えた。状態遷移と入力は`main.gd`へ残し、冪等なUI生成部品だけを`main_ui.gd`へ分離した。
- webtunnelの配信ポートを当初8080と見込んだが、実際のworkflowは8000だった。workflowとサーバーログを正として接続先を直した。CDPのWebGL撮影は一部でdaemon busyや描画途中のフレームが出たため、MJPEGプレビューの後続フレームを取り、正常描画を確認した。
- `gh run download`は53 MBのCI artifact取得で長時間進捗が出なかった。GitHub APIが返した公式Azure Blob URLの`Accept-Ranges`を使って12区間に分けて取得し、公称サイズ53,236,365 bytesとの一致とZIPのCRCを確認してから展開した。
- `pr-attach-screenshots`の`--caption`を拡張子なしで渡すと入力検証で停止した。スクリプト実装上のキーが`compare-title.png`のような拡張子込みbasenameだと確認し、修正後の1回で9枚を公開・ハッシュ検証・本文更新した。最初の失敗時点ではアップロードは0件だった。

## 3. 欲しかったが無かったツール・skill・スクリプト

- **画像生成の一括管理器**: カードID、共通プロンプト、個別の被写体指定、出力ファイル名を表で受け取り、`image_gen`の実行結果を原本として保存し、寸法・色形式・透過・SHA-256重複・一覧画像・実表示向け縮小・CREDITSの下書きまで一括で行う仕組みが欲しかった。今回は32回の対応付けと後処理を個別に管理した。
- **Godot向け生成カード検査器**: 4:3原画と縦長枠の合成を複数の実表示寸法で撮り、顔や武器の切れ、枠からのはみ出し、文字の可読性を一覧化する再利用可能な撮影器があると、カードごとの確認が減る。
- **アニメーション行列の共通撮影器**: `キャラクター数 × 動作数 × 開始・途中・終了・完全終了後`を宣言から撮る仕組みが欲しかった。今回は`screenshot.gd`へゲーム固有処理を書き、24体×5動作×3時点と9演出×3時点を生成した。
- **webtunnel用Godot座標変換・撮影補助**: 1280×720のゲーム座標を実canvasの1279×656へ写す計算、起動完了待ち、WebGLの安定フレーム取得をまとめた補助があると、DOM確認、座標計算、MJPEGフレーム選別を手作業にしなくて済む。
- **進捗・再開付きCI artifact取得器**: `gh run download`が大きなartifactで止まった時に、APIから署名URLとサイズを取り、Range並列取得、再開、結合、CRC検査まで行うスクリプトが欲しかった。
- **音を直接評価できる手段**: codec、波形、音量、ループ境界、録画への混入は機械検査できたが、環境音が世界観に合うか、BGMとの音量バランスが快適かをエージェント自身が聴感評価する道具はなかった。

## 4. 素材の準備方法と使い勝手

### 画像

- カード原画30枚、共通枠、卓上背景は`image_gen`で新規生成した。入力画像、既存作品名、既存ロゴは使わず、1900年前後のアール・ヌーヴォー印刷物、金箔、深緑、植物曲線を共通条件にした。24体は暖色の温室と青銀の夜園に分け、人物・獣・武具・植物・姿勢を個別指定した。魔法・罠は花冠、封印鏡、書物、蔓の罠、霧の香炉、火花の機巧として指定した。
- 30枚を一度に生成せず1枚ずつ生成したことは有効だった。カードごとの構図差と情報量は、前ラウンドの手続きSVGより明確に増え、生成結果を破棄して再生成した画像はなかった。一方、同じピクセルを再現できず、Gitのテキスト差分でも品質を読めないため、原本保管、一覧画像、実寸表示、利用条件の記録が必要だった。
- 共通枠を別の透過PNGにしたことで、全カードの統一感を保ちながら原画の差を残せた。生成原本はカード1448×1086、枠1060×1484、卓上1672×941で、実装用を724×543、530×742、1280×720へ縮小した。
- 前ラウンドの手続きSVGは固定seedで再生成でき、差分と部位アニメーションの調整が容易だったが、同じ図形・色・陰影が全カードへ出やすかった。今回は特色を生成原画へ、統一と再利用を共通枠とGodot側の動作へ分担した。

### BGM・SE・環境音

- 既存の場面別BGMとSEは維持した。いずれも既存曲、録音、サンプルを使わず、`generate_audio.py`が固定旋律・固定seedとPython標準ライブラリの倍音、FM、ノイズ、打楽器合成で生成する22,050 Hz・16 bit・ステレオPCMである。
- 今回は暖炉の小さな爆ぜ、紙の擦れ、左右へ揺れる振り子、低い室内の響きを表す12秒の環境音を同じ方法で加えた。決定的に再生成でき、ライセンス源を増やさず、機械的なクリップ検査をしやすい点は便利だった。生演奏らしい質感や聴感での最終調整には弱かった。

### フォント

- Google FontsのZen Antiqueを取得し、フォント本体を変更せず、同じ配布元の著作権表示とSIL Open Font License 1.1全文を`assets/fonts/OFL.txt`へ同梱した。
- 日本語の雰囲気を一つの静的フォントで大きく変えられ、画像生成より導入と再現が容易だった。OFL本文をエクスポート対象へ含める設定と、実画面で小さい日本語が読めるかの確認は別途必要だった。

### 記録

- 生成画像には根拠なくCC0等を付けず、OpenAIの組み込み`image_gen`、入力画像なし、加工寸法、プロンプトの要点、利用条件を`assets/CREDITS.md`へ記録した。独自音声は生成方法と第三者素材不使用、Zen Antiqueは取得URLとOFL-1.1を記録した。

## 6. Godot固有のハマりどころと回避策

- **親の`_draw()`と子CanvasItemの描画順**: 親の描画は子より先なので、親で後から呼んだつもりの帯も子画像の背面になる。重ねたい表示を子Labelや専用Controlにし、原画、枠、状態表示のz-indexを明示する。
- **Control再構築直後の旧フレーム**: `queue_free()`したControlを同じフレームで作り直すと、撮影側に旧描画が1フレーム残ることがある。スクリーンショット保存前に2描画フレーム待つ。
- **異なる縦横比の画像合成**: 4:3の生成原画を縦長カードへ単純縮小すると余白が増える。原画と共通枠を一つの部品にし、原画だけを`STRETCH_KEEP_ASPECT_COVERED`で窓へ切り抜く。重要部分を端へ置かない素材設計も必要になる。
- **動的`load()`した描画リソースの寿命**: カスタム`_draw()`の中だけで読み込んだTexture参照が保持されず、背景やカードが白くなったことがある。描画で継続使用するTextureは`preload()`またはメンバーで保持する。
- **Controlの最小サイズ確定順**: `TextureRect`は`expand_mode`を先に設定する。Labelはフォント、折り返し、親への追加後にサイズを設定する。順序が逆だと一時的な最小サイズが残り、詳細画像や文章が欄外へはみ出す。
- **録画・終了時の音声リソース解放**: `AudioStreamPlayer.stop()`直後の`quit()`だけでは、Godot 4.7でAudioStreamの解放警告が出る場合がある。遅延した再生開始を停止状態で抑止し、停止後に描画フレームを進めてAudioServerへ処理時間を渡す。Movie Makerでは`OS.delay_msec()`だけで代替せず、録画シナリオ内で終了前のフレームを確保する。
- **`--quit-after`の限界**: 指定フレームでエンジンが終了するため、ノード解放後に追加フレームを待つ用途には向かない。音声付き録画では専用シナリオが音声停止と終了時刻を管理する方が確実だった。
- **headlessだけでは描画不具合を検出できない**: リソースのロード成功やselfcheckのexit 0だけでは、白画像、切り抜き、重なり、旧フレームを見つけられない。`screenshot.gd`、Movie Maker、CI artifactの実画像を必ず併用する。
