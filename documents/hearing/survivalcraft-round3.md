# survivalcraft「灯守の島」開発の振り返り

対象は issue #46 の3Dサバイバルクラフト。実装・検証ログ、素材クレジット、知見文書、PRに残した証拠をもとに記述した。

PR: https://github.com/bannzai/godotpractice/pull/52

## 1. 開発の進め方

最初に作業指示・issueの受け入れ条件・プロジェクトの制約を確認し、既存ゲームの検証用Makefileや撮影・録画・終了処理の構成を参考にした。まずタイトル→プレイ→結果の画面遷移と起動ログを作り、この段階でコミットしてdraft PRを出した。

次に、島の生成・採集・クラフト・生存状態を作る担当、一人称の移動・衝突・昼夜の環境を作る担当、キャラクターモデル・アニメーションを作る担当に分けた。担当ファイルを決めて並行し、主担当がHUD・素材生成・音・演出・各部分の接続と最終検証を進めた。状態をautoloadに集め、表示と入力が同じ状態を参照するようにしたことが、統合時の確認をしやすくした。

中核は、32×32×16の決定的な島、チャンク描画と衝突、採集と設置、9枠のホットバーと拡張持ち物、8レシピと道具段階、空腹・落下ダメージ、昼夜・敵2種、家の囲い判定、3日間の生存、保存・再開の順に接続した。見た目は並行して整え、最後に本番の一人称画面で手元の大きさやHUDを調整した。

詰まった点と解決は次のとおり。

- 復活地点が建築したブロックに埋まる場合があった。初回生成時の座標をそのまま信用せず、復活時に安全な空間を再探索し、回帰検証を加えた。
- 「3日目になった」と「丸3日間生存した」が一致しなかった。開始時刻からの経過で判定し、4日目の朝にクリアするようにした。
- 遊び方を閉じた後にボタン操作のフォーカスが戻らない問題を修正し、実入力の検証に含めた。
- タイトルの挿絵が切れた。数値上のサイズ指定だけで判断せず、撮影画像を見ながらTextureRectの設定順とツリー追加後のサイズ指定を直した。
- macOSのsandbox内では描画付きGodotがexit 134となった。元のアプリやOS設定を変更せず、許可を得た同じ描画コマンドで検証した。
- Web撮影が応答しなかった。ページの応答とrunnerの画面プレビューを別々に確認し、再起動したセッションでCDPの撮影に `fromSurface:false` を指定して実画面を取得した。撮影方式だけが原因だったとまでは断定していない。
- CI artifactの取得が一時的に停滞した。最初の取得ではHTTP Rangeごとの応答と長さを検査してZIPを復元した。最終CIのartifactは通常の `gh run download` で取得できた。

実装コミットの後に全検証と証拠を揃え、知見文書の事実修正・性能計測結果を追加コミットした。最終CIの成功とartifactの画像を確認してPRをレビュー待ちにした。マージは行っていない。

## 3. 欲しかったツール・skill・スクリプト

今回、個別のスクリプトや診断で補ったものを再利用できると、次回の作業を減らせる。既存skill全体を棚卸しして「存在しない」と確認した一覧ではない。

- **モデル単体と一人称画面を一緒に撮る入口**：モデルの種類、各AnimationPlayerの動作、開始・途中・終了を列挙し、本番カメラでの手元も撮るもの。単体ギャラリーでは正常でも、ゲーム内では手が大きすぎる問題を早く検出できる。
- **ボクセルゲームの境界検証集**：斜めの照準、面に隣接する設置、プレイヤーとの重なり、建築後の復活地点、入口のある家の判定。今回のselfcheckから、ゲームごとの定義を差し替えて使える部分を切り出したい。
- **描画許可と保存先の事前診断**：headlessのログ保存失敗、macOSの描画付き起動失敗、実際のゲームエラーを区別するもの。既存のsandbox用Godot準備に加え、どこまで確認できたかを出せるとよい。
- **Web撮影の診断と代替取得**：CDPのページ応答、Godotの起動表示、画面プレビューを確認し、撮影に時間制限を設けるもの。実際に取得できた画像と採用した方法を記録できると、応答待ちだけで時間を使わずに済む。
- **証拠の一覧管理**：画面名、元ファイル、対象コミット、アップロードURL、目視済みかどうかをまとめ、PR本文を更新するもの。今回はアップロード再開用JSONと本文生成処理を個別に用意した。
- **音声の検査補助**：無音・クリッピング・音量差・ループ境界の検査と、場面別に聴ける試聴一覧。数値検査だけでは、曲が単調か、SEが耳障りかまでは判断できない。

共有skillへの変更は行っていない。今回の知見を追加する候補は `godot-development` の撮影・終了検証、 `game-asset-search` のモデルとクレジットの照合、 `webtunnel` の撮影診断。

## 4. 素材の準備方法と使い勝手

共通の色を青緑・真鍮色・濃紺に決め、画像・モデル・UIの方向を揃えた。既存作品の画像・名前・音・モデルは使わず、フォントを除く主要素材をこのプロジェクトで生成した。

| 素材 | 準備方法 | 良かった点 | 足りなかった点・注意点 |
|---|---|---|---|
| アイコン | `generate_assets.py` でブロック・道具・食べ物・キャラクターを独立したSVGに生成。 | 色や輪郭の統一、個別修正、再生成が速い。アイテムごとのファイルを確実に用意できる。 | 小さいホットバー内での判別性は元SVGだけでは分からず、実画面で確認が必要。 |
| キーアート・ロゴ | 同じスクリプトで島・海・灯りを組み合わせたSVGを生成。 | パレットがゲームと揃い、拡大しても輪郭が保たれる。外部画像の権利確認やテイスト合わせが不要だった。 | 複雑な質感や絵画的な表情は今回の方法では作っていない。TextureRectで意図した範囲に収まるか確認が必要だった。 |
| 3Dモデル | 主人公の手とつるはし、石殻獣、浮遊灯精を別々のGDScriptで定義。低分割メッシュとマテリアルを組み合わせた。 | 色違いだけに頼らず、甲羅・四肢・籠・垂れ布など形で区別できる。部位の位置や動作をコードから調整できた。 | 本番カメラでの大きさ、部位の回転中心、消滅後の復帰姿勢は追加検証が必要。外部DCCツールでの造形はしていない。 |
| BGM | Python標準ライブラリによる加算合成でタイトル・昼・夜・成功・失敗の5曲を生成。倍音・包絡・ノイズ・残響を組み合わせた。 | 外部サービス待ちや音源購入がなく、曲とゲーム状態の対応を確実に用意できる。再生成可能。 | 主観的な聴き心地は未検証。生成・再生・数値検査だけで商用品質とは判断できない。 |

## 5. 動作確認の方法

headless、描画付き撮影、録画、CI artifact、webtunnelをすべて使った。それぞれ確認できることが違うため、同じ「成功」にまとめないことが有効だった。

| 方法 | 確認したこと・効いた点 | 限界 |
|---|---|---|
| headlessのselfcheck | 同一シードの生成再現、地上スポーン、露出面、実PhysicsServerの衝突、斜め照準、クラフト材料と道具段階、設置の重なり、家、日境界、空腹、復活、保存データの破損入力。境界条件の修正を短時間で繰り返せた。 | 画面の崩れ、見やすさ、音の聴き心地は分からない。 |
| 実入力integration | InputEventを本番シーンへ投入し、パッドの決定・移動・右スティック・ジャンプ、マウス長押し、GUIクラフト、休止、結果と復活を検証。描画付きではF11の全画面往復も確認。 | 物理的なゲームパッドを人が長時間使った評価ではない。 |
| `screenshot.gd` | 代表画面と演出途中を計15枚撮影し、一覧と必要な個別画像を目視。タイトルの挿絵、HUD、手元の縮尺の修正に効いた。 | 夜・家・成功などは撮影用に固定条件を作るため、通常プレイでその状態まで到達できる証明にはならない。 |
| 起動movie | 5秒の起動動画を生成し、輝度検査と末尾フレームの目視で真っ黒な動画やタイトルの崩れを確認。 | 操作中の不具合は対象外。 |
| プレイmovie | `demo.gd` の実入力で28秒録画。2秒間隔の14枚と末尾を目視し、採集・クラフト・画面遷移を確認。木の前への初期配置だけ短縮し、材料は入力で採集した。 | 2秒間隔では短い不具合を取り逃す可能性がある。丸3日分の通常入力による通しプレイではない。 |
| CI artifact | 最終CIのPNG15枚と起動動画の末尾を取得・目視。LinuxのXvfb＋llvmpipeでも同じ画面構成を確認。31ジョブすべて成功。 | 仮想画面ドライバはV-Sync変更非対応警告を出す。描画速度をローカルGPUと比較する用途には向かない。 |
| webtunnel | 作業ブランチをChromiumで開き、タイトル→プレイ→休止・保存→遠征終了の結果→タイトル→保存から再開を通常入力で確認。6画面を掲載し、終了後にdownした。 | Webでの結果画面は「遠征を終える」からの遷移。3日間のクリア到達をブラウザで通し操作した検証ではない。デスクトップ固有の動作も別検証が必要。 |
| 終了検証 | 通常終了と `--quit-after 120` の両方を実行し、ログ全文にObjectDB・resourceのリーク警告がないことを確認。 | 描画が正常でも解放は別に確認する必要がある。 |

アニメーションは3種類のモデルそれぞれについて、待機・移動・行動・被弾・消滅の5動作をAnimationPlayerで実装した。ギャラリーでは各動作を並べ、開始・途中・終了の3時点を撮影し、部位の変化と消滅後の状態を比較した。さらに一人称の手元、採集のひび割れ段階、破片、被弾フラッシュを本番画面で撮った。ギャラリーだけでは分からなかった手元の大きさを、本番カメラの画像で直せたことが特に有効だった。全動作を人が等速動画で連続視聴したという検証ではない。

性能はM4 Max・1280×720・GL Compatibility・V-Sync無効・画面内の敵6体で300フレーム計測した。平均約162fps、フレーム時間の中央値5.611ms、95パーセンタイル8.239ms。ただし16.667ms超過が2回、最大65.31msあり、全フレームが60fps相当だったとは報告していない。

## 6. Godot固有のハマりどころと回避策

- **TextureRectの表示サイズ**：先にsizeだけ指定すると、素材の最小サイズや後からの設定によって意図より大きくなった。expand_modeを先に設定し、ツリー追加後に `set_deferred` でサイズを指定した。設定値だけで済ませず、タイトルの実画像で確認した。
- **AnimationPlayerが動かす階層**：移動用ルートと部位アニメーション用Rigを分けた。移動とアニメーションが同じtransformを取り合わない構成にすると接続しやすい。
- **消滅アニメーション後のモデル再利用**：最後の姿勢や動作ロックが残る場合がある。再利用時にロックを解除し、待機の先頭姿勢を明示的に適用した。
- **headlessの保存先**：描画しなくてもGodotの既定ログやeditor_settingsへの書き込みがある。ゲーム内tmpへの絶対log-fileとself-containedなコピーでheadless検証を実行した。描画付き検証・最終exportは許可を得て既存Godot.appを使った。
- **終了時の音声解放**：画面を閉じるだけでは音声参照の解放が間に合わない可能性がある。音声を停止し、stream参照を外し、音声スレッドに解放の時間を渡してから終了した。通常終了と時間指定終了の両方で確認した。
- **ボクセルの描画数**：ブロックごとの独立MeshInstance3Dを増やす構成を避け、8×8のチャンクごとに露出面だけをまとめた。島は16メッシュ・22,674頂点。描画用と衝突用で同じ面を使い、見た目と当たり判定のずれも防いだ。
- **ボクセルの照準と設置位置**：固定間隔でレイ上を調べる方法では斜めに格子境界を飛ばすことがある。DDAで境界を順にたどり、実際に当たった面に隣接するブロックを設置候補にした。プレイヤーのAABBとの重なりも検査した。
- **毎フレームのUI処理**：HUDで同じStyleBox・アイコンを作り直す処理と、同じmouse_modeを再設定する処理を避けた。変更前後を実際の描画時間で計測し、平均fpsだけで判断しなかった。
- **Webの起動判定と入力**：Godot既定HTMLの `#status` が消えたことを起動判定に使い、さらに画面を見た。今回のChromiumでは最初のEscapeがマウス捕捉解除に使われ、次のEscapeで休止した。canvasが1279×656でゲームの1280×720と一致しなかったため、黒帯と縮尺を含めてクリック位置を計算した。
- **WebGLと撮影**：runnerでは `--software-webgl` を付けた。CDPのページ応答が正常でも撮影が止まることがあり、画面プレビューと `fromSurface:false` の撮影を使って確認した。SwiftShaderでの速度をデスクトップ版の性能保証には使わなかった。
- **ログの警告の区別**：Linux CIの撮影・録画に出たV-Sync変更非対応警告はドライバ由来として記録した。警告を消えたことにせず、ゲームのERROR・リークと分けて報告した。ローカルの最終検証ではこの警告も出ていない。
