# deckrogue 第2ラウンドの開発ヒアリング

対象は「燈火の巡礼」の品質向上ラウンド。第1ラウンドで成立していたカード戦闘・8階層の分岐・報酬・遺物・勝敗を維持し、キャラ別素材、アニメーション、画面、音と検証を強化した作業を振り返る。

開発完了時点のコミットは `5a5176c`。PRはレビュー可能にし、チェック30件の成功を確認した。本書はヒアリング用の一時ファイルで、コミット対象にはしない。

https://github.com/bannzai/godotpractice/pull/29

## 1. 開発の進め方

### 実際に進めた順序

1. 作業指示書、AGENTS.md、PROJECT.md、issue #6、既存のknowledgeと第1ラウンドのhearingを読んだ。既存ゲームを起動・撮影し、残すべきゲームルールと、絵・動き・音の不足を確認した。共有物と他ゲームを変更せず、ゲームのディレクトリとknowledgeに変更を閉じた。
2. 紺・青緑・羊皮紙色・金・朱色を使う、切り絵と細い線画の美術方向を決めた。早い段階で方針をコミットし、draft PRを作成した。
3. 担当ファイルを分け、素材、アニメーション・演出、音声を3つのサブエージェントへ分担した。主担当は既存コードの調査、画面への組み込み、検証スクリプト、統合後の確認とPRを担当した。画像名・シートの寸法・動作名を合わせてから接続した。
4. キャラ7種の独立シート、カード18種、遺物・道のアイコン、背景3層、ロゴとキーアートを制作した。同時にBGM6曲とSE7種を作り直した。素材生成は画像用・音声用のPythonへ分け、既存の生成入口から呼べる構成にした。
5. `AnimatedSprite2D` を画面へ配置し、攻撃・被弾・防御・回復・強化・死亡の反応、ダメージ数字、HPと結果の数値変化、ボタンの反応、画面遷移を組み込んだ。共通Themeと背景の霧・視差を整えた。
6. 既存のselfcheckを通しながら、コマの検査、全キャラの連続撮影、演出の途中撮影、実入力の30秒録画を追加した。Godotで生成した画像を見て修正し、通常終了・強制的なフレーム期限での終了を別々に検証した。
7. デスクトップ3種とWebをエクスポートし、webtunnelでタイトルから敗北・タイトル復帰まで操作した。CIの画像と録画も確認し、画像50枚と30秒録画をputsで公開してPRへ掲載した。知見を追記し、最終CIとPR本文の一致を確認してレビュー可能にした。

### 詰まった点と解決

- **生成器では正しく見えたシートがGodotで崩れた。** 入れ子のSVGの位置指定がGodotでは期待どおりに解釈されず、30コマが左上に重なった。グループの平行移動へ変え、Godotが実際にインポートした各コマまで検査するようにした。
- **被弾の後半と数字が途中で消えた。** 手札や画面の再構築が演出ノードを破棄していた。被弾の完了を待ち、同じ戦闘中の演出と背景を手札の再構築から独立させた。
- **30秒以内に自然敗北とタイトル復帰まで入らなかった。** 録画の試作では敵の行動と入力間隔が時間枠に合わなかった。通常開始後に乱数種だけを固定し、入力間隔と録画時間を調整した。HPやデッキを撮影用に変更する方法は採らず、最終版は750フレームで敗北、813フレームでタイトル復帰、900フレームで正常終了した。
- **音を止めても終了時にリソースが残った。** 音声スレッドが停止を処理する前にツリーが解放されていた。通常終了には停止後の待ち時間を設け、`--quit-after` には終了処理内での同期的な待機を用意した。
- **変更していないゲームのCIが失敗した。** knowledgeの変更が共有変更として扱われ、全9ゲームのCIが走った。crewrtsの終了時リークが断続的に発生したため、失敗ジョブだけを再実行した。最終CIは初回失敗後に3回再実行して成功した。deckrogueは初回から成功しており、他ゲームの不具合を修正したわけではない。この区別をPRへ残した。
- **putsの一部アップロードが遅延・失敗した。** 180秒のタイムアウトと、保存済み設定を読む際のCoreDataエラーがあった。成功したURLをJSONへ逐次保存し、失敗分だけを新しいプロセスで再実行した。設定や認証情報の変更は行っていない。最後は公開先から全51ファイルを取り直し、元ファイルとSHA256が一致することを確認した。

進め方として効いたのは、素材制作と画面実装を並行しつつ、統合の合否をGodotの実描画で判断したことだった。一方、素材生成器での見た目だけを先に信用したことで、SVGの解釈差の発見が後ろに寄った。次回は全キャラを作る前に、1キャラの全動作をGodotへ入れる小さな確認を先に済ませたい。

## 4. 素材の準備方法と使い勝手

### 画像

新しい画像は既存作品の素材や画像生成APIを使わず、CodexでSVGの図案と生成コードを記述し、`scripts/dev/generate_art.py` で決定的に生成した。画像生成API、Gemini、外部の画像配布サイトからの新規取得は今回使用していない。

- キャラは主人公、蛾、甲冑の番人、岩角の四足獣、仮面の霊炎、冠と六腕のボス、鳥面の司祭の7種。配色だけでなく輪郭・装備・部位を変えた。
- 1キャラにつき256×320のコマを6列×5行に並べた、1536×1600の独立したシートを用意した。待機・移動・攻撃・被弾・死亡が各6コマ、合計210コマ。
- カード18種、遺物3種、道の種類ごとのアイコン、UIアイコン、パーティクル用画像、3層の背景、ロゴ、キーアートも別ファイルにした。既存名との互換用の画像を含め、SVGは56点。
- 全SVGの構文、再生成したSHA256の一致、描画範囲を検査し、Godotでのコマ検査も追加した。

手続きSVGは、共通パレット・透過・部位の寸法・コマ間の対応を正確に保ちやすい。腕、翼、燈籠、冠などを少しずつ動かす用途や、カード挿絵とUIアイコンの量産に向いていた。ファイルを再生成しても同じ結果になるので、担当者間の修正も追いやすかった。

一方で、身体の複雑な変形や絵画的な質感は、図形の組合せと変形を自分で設計する必要がある。今回は切り絵の方向に合わせられたが、別の美術方向でも同じ方法が最適とは判断していない。また、一般的なSVG描画器とGodotの解釈が一致する保証はなく、外部プレビューだけでは不十分だった。

### BGM・SE

`scripts/dev/generate_audio.py` で、Python標準ライブラリによる倍音・ノイズ合成、音量変化、左右定位、短い反射音を組み合わせた。既存の録音・楽譜・外部音源・音楽生成サービスは使っていない。

- BGMはタイトル・探索・戦闘・ボス・敗北・勝利の6曲。笛と持続音、撥弦とベル、弦の反復と打楽器、低い金管と銅鑼、疎な下降旋律、明るい和声という違いをつけた。
- SEはカード・攻撃・防御・回復・強化・死亡・遷移の7種。
- 出力は22050Hz、16bit、ステレオPCMのWAV。固定seedで再生成し、13点のハッシュ一致、PCMの読取り、非無音、非クリッピング、両端ゼロを検査した。

コード生成は長さ、音域、音量、場面別の編成を揃えやすく、短いSEを調整する際も再現性が高かった。単純な正弦波から音色を増やす要求には対応しやすかった。一方、音楽としての好みや楽器の自然さを機械検査で保証することはできない。音声付き録画と比較用WAVは用意したが、聴感品質の確定的な試聴評価まで実施したとは扱っていない。美術・演出と音楽の密度はPRの判断点に残した。

### フォント・クレジット

第1ラウンドから同梱していたZen Old Mincho Regularを継続使用した。このラウンドでは新しいフォントを取得・改変していない。日本語を含む雰囲気とThemeの統一に使いやすく、OSにインストールされたフォントへの依存を避けられた。

クレジット上の素材源は次のとおり。OFL全文を同梱した構成を維持した。

https://fonts.google.com/specimen/Zen+Old+Mincho

画像・音声・Theme・シェーダの制作方法を `games/deckrogue/assets/CREDITS.md` に記録した。ファイル名単位でのクレジット検査は、追加したシェーダなどの記録漏れを拾うのに役立った。外部素材配布サイトや画像生成APIとの制作速度・品質の比較は、今回は未実施。

## 5. 動作確認の方法と、効いた点・足りなかった点

### headlessのselfcheck

既存のカード効果、山札・捨て札・廃棄の扱い、状態異常、報酬、遺物、巡礼の勝敗、入力イベントの検査を維持し、新しい画像への変更でゲームルールを壊していないことを確認した。追加した素材検査では、Godotがインポートした各コマの非透明領域とポーズの差を調べた。

短時間で繰り返せるため、表示差し替え中の土台として有効だった。ただし、headlessの成功だけではUIの重なり、フラッシュの強さ、演出の途中消失、音声スレッドを伴う通常終了は判断できなかった。

### screenshot.gdとアニメーション検証

描画付きの `screenshot.gd` で最終的に42枚を撮影した。

- 全7キャラを並べ、5動作それぞれの開始・途中・終了を撮る15枚。
- 攻撃・被弾・防御・回復・強化・死亡の演出途中を撮る6枚。
- タイトル、巡礼路、戦闘、ボス、報酬、イベント、休憩、勝敗、デッキ、状態異常、手札のホバー・スクロール、ドロー・使用・捨て札、背景の視差を撮る21枚。

アニメーションの素材検査と撮影では再生を止め、`seek_pose()` で同じコマを指定した。全210コマの描画範囲を検査したうえで、開始・途中・終了の姿勢が判別でき、端で欠けていないことをPNGで確認した。演出についてはパーティクル、数値、フラッシュが見える途中のタイミングを撮った。

固定コマの撮影は、素材の欠けや姿勢の差を比較するのに効いた。ただし、コマを固定した静止画だけでは、実際の再生順序、待ち時間、操作との同期は分からないため、実入力録画も使った。

### 起動movieと30秒の実入力録画

既存の `make movie` で5秒の起動録画を作り、起動後に黒い画面のままにならないことと、タイトル表示を確認した。

追加した `demo.gd` は `Input.parse_input_event()` で実際のマウス・キーイベントを投入する。クリックによる開始、地図の選択、カード2枚の使用、Eによる敵行動、自然敗北、タイトル復帰を行い、手札とエネルギーの消費や結果への到達も検査する。再現用に通常開始後の乱数種だけを固定し、HP・敵HP・デッキは変更しなかった。

最終録画は30fps・900フレーム・30秒。`demo OK` とexit 0を確認し、ffmpegで2秒間隔の15枚と末尾を抽出して目視した。被弾の後半が切れる問題や、結果への遷移が時間内に終わるかを確認する際に有効だった。

確認の限界もある。2秒間隔の一覧だけでは65msのヒットストップのような短い演出の全過程は追えない。固定コマ・演出途中の撮影、入力ログ、実際のフレーム数と組み合わせて確認した。また、固定fpsの録画は実ゲーム時間を再現するが、利用端末上の実時間での快適さを測る性能検証ではない。

### CI artifact

LinuxのXvfbとllvmpipeで生成した `deckrogue-screenshot-and-movie` を `gh run download` で取得した。実装コミットと最終コミットのPNG42枚を確認し、起動mp4もフレームへ分割して確認した。ローカルのmacOSだけに依存せず、GL Compatibilityでの描画を確かめるのに役立った。

自分のブランチを `--software-webgl` 付きで起動した。Godotの起動はstatus要素が消えることを確認し、画面は実際のスクリーンショットで判断した。Enterでタイトル・地図・戦闘へ進み、カード使用後に敵HP、エネルギー、手札が減ったことを確認した。Eで敵行動を進めて自然敗北し、マウスで「タイトルへ」を押して復帰した。

6枚のスクリーンショットを撮り、ブラウザーの実行エラーは0件。最後に `down deckrogue` と専用agent-browserセッションの終了を行い、Web操作の録画artifactも取得した。

Godot内部の撮影スクリプトだけでは見落とす、ブラウザーへの入力経路とWebエクスポートの動作を検証できた。canvas内のUIにはDOMのボタンがないため、通常のWebページの要素探索は使いにくかった。キーボード入力を主に使い、クリックは実際のcanvas領域と余白を考慮した。SwiftShaderとリモート撮影では数秒の待ちが生じるため、短いアニメーションの時間評価には向かなかった。

## 6. Godot固有のハマりどころと回避策

以下は今回のGodot 4.7環境で確認したもの。別バージョンでも同じ制約があるとまでは判断していない。

| ハマりどころ | 起きたこと | 回避策 |
|---|---|---|
| SVGの入れ子と位置指定 | librsvgでは正しく配置されたシートが、Godotでは30コマとも左上に重なった。 | `<svg x="..." y="...">` に頼らず、`<g transform="translate(...)">` で配置した。Godotでインポートしたコマの検査を追加した。 |
| スプライトシートのコマ境界 | 腕・武器・死亡時の傾きが大きいと、コマ外にはみ出して欠ける。 | 256×320のコマ内に余白を取り、210コマの非透明領域を検査した。AtlasTextureの領域を明示し、`filter_clip` を設定した。 |
| UI再構築とノードの寿命 | 手札の更新で、被弾アニメーションの最終コマやダメージ数字が消えた。背景の視差と霧も先頭へ戻った。 | 同じ戦闘中の演出と背景を独立して保持し、被弾の必要時間を待ってから画面を更新した。場面を変える際には不要な演出を片付けた。 |
| ヒットストップの対象 | 全体の時間を止めると、UIや音楽、入力待ちまで巻き込む。 | 被弾キャラの `AnimatedSprite2D.speed_scale` だけを65ms止め、Tweenで戻した。ポーズを切り替える際に残ったTweenと速度・色・位置をリセットした。 |
| ProgressBarの最小サイズ | パーセント表示を消す前に高さを設定すると、既定の最小高さが残ってHUDの文字を覆った。 | スタイルと `show_percentage = false` を確定してからサイズを再設定した。 |
| CanvasItemシェーダの色 | キーアートのフェードで、すでにテクスチャ色が入ったCOLORへ再度色を掛け、画像が暗くなった。 | 目的の境界フェードに必要な `COLOR.a *= smoothstep(...)` だけを適用した。 |
| 音声停止とスレッド間の処理 | `stop()` 直後のツリー解放では `AudioStreamPlaybackWAV` が残り、終了時リークになった。 | 通常終了は音源停止・stream参照解除後、出力遅延の2倍以上かつ120ms以上と数フレームを待つ `Sound.shutdown()` を通した。 |
| `--quit-after` と終了通知 | 終了引数はGodotが消費して `OS.get_cmdline_args()` に残らず、終了通知後のawaitでツリーを延命することもできなかった。 | `_exit_tree()` の終了経路では停止後に実時間を同期的に待った。同期する理由をコメントへ残し、通常終了とは別に検証した。 |
| 撮影中の入力タイミング | 戦闘の演出中に次の入力を送り、`busy` によりターン終了が無視された。 | 撮影スクリプトと実入力録画で、演出完了・操作可能状態を待ってから入力した。入力後の状態変化も検査した。 |
| 生成した証拠画像の再インポート | Godotプロジェクト内のtmpに撮影PNGが溜まると、それらも素材としてインポートされる。 | tmp作成時に `.gdignore` を置いた。Gitのignoreとは別の指定が必要だった。 |
| Web版のcanvasと座標 | ブラウザーの表示領域が1280×720と異なり、ゲーム座標をそのままクリック座標にするとずれる。 | `getBoundingClientRect()` と中央寄せの余白から座標を求めた。キー入力で済む操作はキー入力を使った。 |
| WebGLと描画環境 | runnerのChromiumではGodotに必要な描画環境を明示する必要があった。 | webtunnelを `--software-webgl` 付きで起動した。デスクトップ描画にはheadless検証を流用せず、描画付きGodotとCI artifactを使った。 |

一番大きな学びは、素材生成器での確認、headlessのロジック検査、実際の画面、実入力の録画、終了処理をそれぞれ確認する必要があったこと。今回新たに作ったコマ検査・撮影・実入力録画・音声終了の検証を再利用できる形にすると、次のゲームでは制作そのものに使える時間を増やせる。
