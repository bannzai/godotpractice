# survivalcraft「灯守の島」手直しラウンドの振り返り

対象は、issue #46 の機能を維持しながら、既存の汎用的な濃色 HUD と単色ボクセルの見た目を「暗い机の上で折る紙工作の島」へ作り替えたラウンド。実装コミット、検証ログ、素材クレジット、知見文書、PR #83 に残した証拠をもとに記述した。

PR:

https://github.com/bannzai/godotpractice/pull/83

## 1. 開発の進め方

最初に `AGENTS.md`、`documents/PROJECT.md`、issue #46、前ラウンドの PR #52、既存の知見文書とヒアリングを読み、維持すべきゲーム機能と今回だけの見た目の方針を分けた。その後 `make survivalcraft-run` で変更前を実際に起動した。変更前は、単色の低ポリゴン島、左上の生存値、右上の目標文、画面下のホットバーと共通操作ガイドという構成で、移動やジャンプは動く一方、最初に木へ向かう順序、採掘できない理由、配置結果、クラフト後の結果が画面から分かりにくかった。他ゲームと同じ画面骨格に見えることも確認した。

実装は次の順で進めた。

1. 紙工作の方向を先に固定し、image_gen で折り紙、浅い折り目の接線空間法線、青緑の色画用紙を生成した。Zen Maru Gothic と OFL 原文を取得し、旧フォントを置き換えた。
2. ボクセル面へ UV と接線を追加して紙の albedo と normal map を適用した。空、海、雲、遠島にも紙素材を広げ、昼夜の BGM と並行して鳴る紙擦れ入りの環境音を追加した。ここまでを `9088ecb` としてコミットした。
3. HUD を紙片へ作り替えた。共通操作ガイド行を廃止し、今の目標を示す工作メモ、紙片ホットバー、状態で進む4ページの初回手順書、金／赤の対象表示、配置予想、材料不足と作業台不足の理由、クラフト結果の予告を追加した。実際の現在の島を別の 3D world へ組み直して俯瞰する机上模型も追加した。ここまでを `34a5757` としてコミットした。
4. 表示だけで終わらせず、`selfcheck.gd` に可否理由のロジック、`integration.gd` に初回手順書の表示・スキップと地図の開閉、`screenshot.gd` に新 UI と連続状態を追加した。ここまでを `2e07918` としてコミットした。
5. 19枚のスクリーンショットと録画を目視し、紙テクスチャの import 設定、地図の案内文、証拠用の配置予想シーンを修正した。素材の当たり外れ、ライセンス、Godot 固有の注意を知見文書へまとめ、`e4cbf50` としてコミットした。
6. 最終コミットでローカル一括検証、全プラットフォームの export、実ウィンドウ起動、CI artifact の目視、webtunnel での Web 実操作を行った。変更前後、他ゲームとの識別テスト、アニメーション連続フレーム、Web 実操作の比較画像を作り、PR body へ掲載して ready for review にした。

詰まった点と解決は次のとおり。

- ボクセルへ UV を足した時、ループ変数を `index` から `corner_index` へ変えた一部で古い名前が残り、`make import` が Parse Error になった。ログ全文から `voxel_world.gd` の該当行を特定し、全参照を同じ変数名へそろえた。
- 最初の `gdlint` は、同じテクスチャの重複 `load` が3件、`placement_reason()` の return 数超過が1件で失敗した。テクスチャはファイル先頭の `preload` 定数へ集約し、配置理由は `reason` 変数を分岐で設定して最後に1回返す形へ直した。
- 法線 PNG を動的にマテリアルへ設定するだけでは、import 側が normal map として扱うことや遠景での縮小品質が保証されなかった。`.import` の `compress/normal_map=1` と mipmap 生成を明示し、`SurfaceTool.generate_tangents()` と組み合わせた。
- 配置予想の最初の撮影では、木を採った直後に照準先が空になり、予想ブロックが写っていなかった。撮影 fixture だけに土を1個与え、実際の配置判定を通して予想を撮り、直後に在庫を戻すようにした。通常プレイの成功証明と画面比較用の固定状態は分けた。
- タイトルから机上地図を開いた場合も「M / View でも閉じられます」と表示していたが、M の入力処理はプレイ中だけだった。入力範囲を広げて仕様を変えるのではなく、タイトルでは「戻る」で戻る、プレイ中では M / View で閉じる、と実際の操作に合わせて案内を分けた。
- macOS の sandbox 内では描画付き Godot が正常に起動できず、puts は Keychain にアクセスできず `OSStatus -25291` になった。どちらもファイルや OS 設定を変える迂回はせず、内容と対象を確認したうえで許可された同じコマンドを sandbox 外で実行した。puts の都度確認を減らしつつ機密検査を残す改善は castle issue #945 にした。
- webtunnel の Chromium は 1280×656 でゲームの 1280×720 と一致せず、CDP のキー入力は Pointer Lock の user gesture として扱われなかった。黒帯と縮尺を含めてゲーム座標をクリック座標へ写し、キーボード操作で画面遷移を検証した。マウス視点と採掘はデスクトップ実起動、integration、操作録画で補った。

## 3. 欲しかったが無かったツール・skill・スクリプト

次は、今回の範囲で見つけられず、手作業またはゲーム固有コードで補ったもの。既存の全 skill を棚卸しして不存在を断定した一覧ではない。

- **公開前検査付きの PR 証拠画像アップローダー**: 画像を目視または機械検査し、機密情報・個人情報・非公開 URL・QR コードなどがない時だけ `puts upload` を許可し、同じ添付作業の画像へ許可を引き継ぐもの。安全な開発画面でもファイルごとの sandbox 承認が必要になったため、castle issue #945 を作成した。
- **証拠画像 manifest と PR body 生成**: 撮影名、対象コミット、ローカル／CI、目視済み、公開 URL、PR の掲載箇所を1つの manifest で管理し、未撮影・未確認・リンク切れ・プレースホルダー残りを検出するもの。今回は複数の一覧画像作成、URL 差し替え、HTTP 200 検査を個別に行った。
- **image_gen 面素材の受入検査**: 正面、全面、継ぎ目、文字・ロゴなし、接線空間法線らしい RGB、解像度、mipmap、Godot の normal map import を一括で確認するもの。今回は原寸目視と `.import` の確認を別々に行った。
- **フォント本体・OFL・CREDITS の相互照合**: TTF 内部の family／copyright、OFL 冒頭の著作権者、CREDITS の作者を比較するもの。`check-credits.sh` はファイル名の記録漏れには効いたが、旧フォントの著作権行が残る内容不一致までは検出しなかった。
- **Godot 用の撮影シナリオ manifest**: 代表画面だけでなく、状態遷移、採掘の開始／途中／完了、全キャラクター動作の開始／中間／終端を宣言し、欠けた画像や同一フレームを検出するもの。今回は `screenshot.gd` と ImageMagick のコマンドを手で対応させた。
- **Godot Web の操作座標変換と Pointer Lock 診断**: ゲーム解像度、canvas、ビューポート、黒帯から座標を変換し、CDP 入力では検証できない操作を明示するもの。webtunnel の既存資料は考え方を示してくれたが、実際の操作列は個別に組み立てた。
- **`SubViewport` 俯瞰地図の再利用例**: 現在の 3D 状態を別 world に再構築し、専用の Environment、ライト、カメラ、更新タイミングを含めて UI に埋め込む最小例。今回の実装を `godot-development` へ一般化できる。

## 4. 素材の準備方法と、素材源・生成手段ごとの使い勝手

| 素材 | 今回の準備方法 | 良かった点 | 手間・注意点 |
|---|---|---|---|
| 紙の画像3枚 | OpenAI built-in image_gen で、暖色の折り紙、青紫の接線空間法線、青緑の色画用紙を各1枚生成。正面、全面、継ぎ目を目立たせない、文字・物体・ロゴなしをプロンプトへ入れた。 | 手続き SVG では出しにくかった繊維、細かなむら、浅い折り目が得られ、同じ頂点色のボクセルでも紙工作に見えるようになった。色画用紙を空、海、机上地図へ流用して画面全体をそろえられた。 | 生成は非決定的で、同じ入力から同じ SHA-256 を再現できない。3枚で約8.3 MB 増え、生成待ち、原寸目視、import、UV、接線、normal map 設定が必要。浅い法線だけでは特徴が弱く、albedo、面ごとの色、紙片 UI との併用が必要だった。完全なタイル素材ではないため、広い面の繰り返しも目視が必要。 |

## 6. Godot 固有のハマりどころと回避策

- **ボクセル面の normal map**: 頂点色だけだった `SurfaceTool` の面へ、面の角と対応する UV を必ず頂点より先に設定し、法線と UV がそろってから tangent を生成する。Godot の texture import 側も normal map と mipmap を明示する。マテリアルへ PNG を設定しただけでは完了としない。
- **動的 load と gdlint**: 同じ texture path を複数箇所で `load()` すると `duplicated-load` になる。スクリプト先頭の `preload` 定数へ集約すると、lint と実行時の参照が分かりやすい。
- **`StyleBoxTexture` の余白**: 紙片の texture margin と content margin は別物。前者だけでは紙端が伸び、後者だけでは文字が端へ寄る。少しずつ `rotation_degrees` を変える時は、見た目だけでなくボタンのフォーカス枠とクリック範囲を実入力で確認する。
- **明るい3D背景上の文字**: 白文字を直接重ねると、紙の空や砂で読めなくなる。対象名、配置予想、理由を半透明の紙片へ載せ、濃いインク色にすると昼夜の両方で読みやすかった。
- **机上地図の構成**: メインカメラを一時的に上空へ動かすと、プレイ側の world と停止状態へ影響しやすい。`SubViewport.own_world_3d`、専用の `WorldEnvironment`、ライト、カメラを用意し、同じボクセルデータから別 world を再構築すると、ゲームを止めたまま実際の島を俯瞰できる。開くたびに再構築することで建築も反映できる。
- **説明と実処理の二重化**: レシピ不足や配置不可の条件を HUD に複製すると、表示は不可なのに操作できるなどのずれが起きる。状態側の `recipe_reason()` と `placement_reason()` を純粋な問い合わせにし、表示と実行の両方から使った。
- **初回手順書の進行条件**: 入力回数で進めると、キーボードとゲームパッド、撮影用入力で挙動がずれる。開始地点からの距離、照準対象、木材、板の所持というゲーム状態で進めると、入力機器に依存しない。
- **画面 phase と案内文**: 同じ地図 UI でもタイトルとプレイで使える入力が違う。共通文言を固定せず、現在 phase から閉じ方を出し分ける。表示された操作が実際に通ることを integration と Web 実操作で確認する。
- **音声ループと終了**: BGM と環境音は別プレイヤーにし、昼夜の曲変更と同じタイミングで環境音も切り替える。終了時は再生を止め、stream 参照を外し、音声スレッドが解放する時間を取らないと、終了時リークの切り分けが難しい。
- **macOS sandbox の描画**: headless でも既定ログや editor settings の書き込み先が問題になり、描画付き起動は sandbox 内で exit 134 になることがある。ログはゲーム内 `tmp` の絶対パスへ出し、headless は self-contained な環境、最終の描画と export は対象を限定して許可された Godot.app で実行する。コマンド失敗だけでゲームの Parse Error と断定せず、ログの有無と同じコマンドの許可付き実行を比較する。
- **Web の canvas と Pointer Lock**: Chromium の viewport と Godot の設計解像度は一致するとは限らない。実 canvas の位置とサイズを取得して座標を変換する。CDP 入力で Pointer Lock が拒否された時は、エラーを隠さず、Web で検証できた画面遷移と、デスクトップ側で補ったマウス操作を分けて記録する。

最終的に、全受け入れコマンド、ローカルと CI の画像目視、Web の実操作まで完了した。共有 skill や共通ルールそのものはこの worktree では変更せず、再利用候補を `documents/knowledge/survivalcraft.md` に残し、puts の承認改善は castle issue #945 として分離した。
