# 「灯守の島」開発の振り返り

対象は actionadventure、issue #44。実装・検証の最終コミットは `181b832`。この文書は開発中のコード、実行ログ、素材クレジット、開発知見と会話の記録に基づく。今回新たにゲームを実行した結果ではなく、完了した開発の振り返りである。

PR:
https://github.com/bannzai/godotpractice/pull/57

## 1. 開発の進め方

### 作った順序と分担

1. 作業指示書、プロジェクトの制約、issue の受け入れ条件、既存ゲームの構成と知見、Godot・素材関連の skill を確認した。
2. 素材生成、UI・演出、状態管理・検証をサブエージェントへ分担し、担当ファイルを決めた。親はゲーム進行、戦闘、部屋、仕掛けをつなぐ実装と全体の検証を担当した。共有ファイルを複数人で同時編集しない分け方が有効だった。
3. タイトル、開始、探索・戦闘、敗北から再開、宝を取って結末へ進む基本ループを作り、最初の実装コミットと draft PR を出した。永続状態を `AdventureState`、部屋内の動作を `world.gd`、UI を `presentation.gd` に分けた。
4. フィールド6画面と遺跡6部屋、風の輪・爆弾・押石・鍵・床スイッチ・穴、敵5種と二段階ボス、会話・店・保存を揃えた。並行してキャラ別シート、景観、照明、UI、BGM・SEを組み込んだ。
5. 個別の仕掛けを検査する統合テストと、通常入力だけで全12室を攻略するテストを追加した。見た目は実描画の画像・録画で確認し、HUD、ボスの体力バー、部屋遷移、起動直後と録画末尾を修正した。
6. 各OSとWebのエクスポート、ローカル実起動、webtunnel、CI artifactまで確認した。65枚の検証画像をPRへ添付し、最終CI全33件成功を確認して ready for review にした。マージは行っていない。

コミットの流れは、基本ループ → 景観・光源・実入力検証 → 画面遷移と演出の重なり修正 → 起動直後と録画末尾の修正だった。

### 詰まった点と解決

- **起動環境**：sandbox内の `user://` 作成で失敗した。ログ出力先の絶対パス指定だけでは解決せず、許可されたsandbox外実行で通常のGodotを使って検証した。exit 0でもログにエラーが出るため、終了コードとログ全文を別々に確認した。
- **操作の接続**：InputMapのキー・パッド番号の誤りを、実入力テストとGodotの定数の照合で修正した。アクションが登録されているだけでは正しく操作できるとは限らなかった。
- **会話**：近くの草が探索対象に混ざり、NPCへ話しかけられない箇所があった。距離を比べる前に、会話・調査に対応する対象種へ絞った。
- **進行不能と境界条件**：爆弾の使い切りには補充手段を用意した。橋を開いても橋以外の穴は通れないこと、死亡フレームで出口へ移動しないこと、購入上限で代金を失わないことを検査・修正した。
- **表示**：HUDアイコンのはみ出し、案内文とボスHPの重なり、前のHUDまで流れる遷移、前室のポップアップ残りを画像で発見した。最後にはCI録画の先頭とプレイ録画の末尾にも不備が見つかり、追加修正になった。
- **外部検証と添付**：webtunnelやputsはsandbox外の既存認証が必要だった。途中で自動承認レビューの利用上限にも止められ、再開後に完了した。これはゲームの不具合とは分けて扱った。

### 次回の進め方への反省

最終段階の証拠確認で初回描画と録画終了の問題が出て、再撮影・再ビルド・CI再実行が必要になった。起動録画の先頭と末尾、短い操作録画、通常終了を最初の基本ループの時点で確認すると、後半の手戻りを減らせる。

PR本文の完成内容への更新は終盤に集中した。実装、テスト、撮影済み画像を更新する単位をもう少し小さくすると、途中のPRも実際の状態を把握しやすい。

### 主な実行コマンド

以下は実際に使った入口。Godotは通常 `/Applications/Godot.app/Contents/MacOS/Godot` を使用した。

```bash
make test GAMES=actionadventure
make screenshot GAMES=actionadventure
make movie GAMES=actionadventure
make build-all GAMES=actionadventure
make build-web GAMES=actionadventure
make actionadventure-run
make -C games/actionadventure movie-play quitcheck
python3 games/actionadventure/scripts/dev/generate_assets.py
python3 games/actionadventure/scripts/dev/generate_assets.py --visual-only
```

`ACTIONADVENTURE_RUN_CAPTURE=1 make actionadventure-run` では、実起動時のタイトル、CoreAudio出力、F11往復、通常終了を自動確認した。

Web検証は `webtunnel-cli.sh up actionadventure --software-webgl --ref game/actionadventure --wait` で起動し、`agent-browser --session actionadventure --cdp ...` で操作、終了後に `webtunnel-cli.sh down actionadventure` を実行した。CI画像・動画は `gh run download ... -n actionadventure-screenshot-and-movie` で取得した。

## 3. 欲しかったが無かったツール・skill・スクリプト

ここは今回専用コードや個別の操作で補った部分の再利用案であり、共有物へ実装済みという意味ではない。

- **通常入力による攻略テストの共通部品**：今回はキー保持・解放、目的座標までの移動、部屋到達待ち、期限付き失敗判定を `playthrough.gd` に書いた。テスト対象の状態を書き換えずに移動やUIを操作する共通部品があれば、ジャンルごとの攻略手順だけを書く量を増やせる。
- **キャラ別の動作一覧を作る入口**：今回は47枚の撮影と、8キャラ×5動作×3時点の切り出し・一覧生成を組み合わせた。キャラ名、シート、動作、撮影時刻を渡すと一覧と日本語の見出しを出すスクリプトが欲しかった。
- **録画の開始・終了確認をまとめた検証**：長さ、黒画面、先頭・末尾、終了ログ、音声解放を一つの入口で扱いたい。今回の灰色の末尾は単に動画が存在することや途中の一覧だけでは分からなかった。自動判定に加え、確認すべき先頭・末尾を必ず並べる仕組みが有効だと思う。
- **最終コミットと証拠の対応管理**：修正後にPNG、キャラ別一覧、動画フレーム、Web画像、CI artifactをどこまで更新したかを手で追った。コミット、生成コマンド、画像ハッシュ、目視結果を一覧にできると、古い証拠を混ぜる危険と再確認の量を減らせる。
- **音源の一括検査**：再生成の一致、飽和、音量、ループ境界をまとめる入口が欲しい。ただし数値検査だけで耳による品質評価を代替できるとは考えていない。
- **共有MakefileとCIの検証入口**：ルートに `movie-play` の委譲がなく、ゲームのディレクトリを指定して実行した。また、今回追加した `integration` / `playthrough` はローカルの `make test` に入るが、既存CIは個別targetを呼ぶため、この二つを実行しない。共有物への変更提案として知見に残した。

画像のアップロードとPRへの埋め込みは、最終的に既存の `pr-attach-screenshots` で解決できた。「無かったので新しく作るべきもの」には含めない。公開URLの内容検証まである点が特に役立った。

## 4. 素材の準備方法と使い勝手

### 画像

`generate_assets.py` で独自のSVGを生成した。主人公、徘徊・突進・遠距離・分裂・ボス、村人、商人の8種は、キャラごとに別の図案と別ファイルにした。各シートは96pxセル、横4フレーム、縦5動作。背景、タイル、小物、収集品、景観も別の素材として用意した。

藍・翡翠・琥珀の配色を生成コードで共有でき、サイズや姿勢の修正をまとめて再生成できた。固定した乱数種を使う箇所もあり、再生成結果の一致を確認できる。連続する動作のフレームを同じ形から作る用途には扱いやすかった。

一方、生成だけでは画面に置いた時の密度や見栄えまでは決まらない。景観の追加、陰影や装飾の調整、実際の表示サイズでの目視が必要だった。96pxの主人公スプライトをタイトルで大きく使うと鮮明さが足りず、同じベクター図案から480pxの独立したキーアートを作った。GodotへSVGを入れれば、どの表示倍率でも自動で十分に鮮明になるわけではなかった。

### BGM・SE

PythonでWAVを合成した。タイトル・フィールド・遺跡・ボス・結果のBGM5曲、剣・道具・被弾・扉・宝箱・撃破のSE6音を用意した。旋律、和音、低音、撥弦、ベル、木管風の音、打楽器などを重ね、場面ごとにテンポと主な音色を変えた。ループ設定はGodot側で行った。

外部録音や既存曲を加工せず、長さ・音量・タイミングをコードで調整できる点は便利だった。映像に合わせたSEも作りやすい。反面、振幅や出力を確認できても、「長く聞いて疲れないか」「音色が魅力的か」「ループが耳に自然か」は数値だけでは決められない。CoreAudioの実出力は確認したが、人の耳による音質評価は未実施である。

### フォントと素材源

日本語フォントは、既存の `survivors` に同梱されていた Zen Maru Gothic Medium を再利用し、OFL全文を同梱した。日本語の表示と柔らかい画風を揃えやすく、既存の出典記録も確認できた。

素材源は、画像・音声がプロジェクト独自生成、フォントが既存同梱のOFLフォントである。出典、生成方法、ライセンスを `assets/CREDITS.md` に記録した。今回、画像生成APIや外部の画像・音声素材集を実制作へ採用していないため、それらとの品質・検索効率の比較は評価していない。

## 5. 動作確認の方法と、効いた点・足りなかった点

### headlessのロジック・実入力検証

`selfcheck.gd` で計算、状態遷移、保存データの解釈などを検証した。保存形式はバージョン・型・値域・所持品と装備の整合を確認し、破損データで現在の状態を壊さないようにした。

`integration.gd` は100項目を検証した。キー・パッド入力、UI、剣の前後判定、道具での通路開放、会話、店、保存・復帰、被弾、死亡、購入上限などを扱った。個別の場面を作って検査するため、入力の誤設定や境界条件の回帰確認に効いた。

それだけでは全体の攻略順が成立する証明にならないため、`playthrough.gd` を別に作った。位置・HP・装備・所持品・フラグを書き換えず、通常のキー入力だけで全12室、道具、仕掛け、二つのハート宝箱、ボスと宝まで4304物理フレームで到達した。約71.7秒はゲーム内の時間であり、実行にかかった壁時計時間ではない。

### screenshot.gdとアニメーションの確認

描画付きGodotで代表画面47枚を撮影した。タイトル、各部屋、会話、店、メニュー、結果、斬撃・爆弾・遷移・被弾・ボス撃破などの途中を含む。全体一覧で確認した後、気になる箇所を原寸で見た。HUDのはみ出しや案内文との重なりは、この確認で発見できた。

アニメーションは `AnimatedSprite2D` の待機・移動・行動・被弾・消滅を実時間で再生し、開始・途中・終了を撮影した。8キャラそれぞれについて、行を5動作、列を3時点とした一覧を作り、姿勢の変化、形の欠損、はみ出しを目視した。静止画一覧はキャラを横断して比べやすいが、細かな動きの滑らかさや操作時の気持ちよさは十分には評価できない。

### movieと操作録画

起動録画は5秒、操作録画は26秒を作成した。ffmpegで2秒間隔の一覧と末尾を抽出し、起動直後のフレームも別に見た。起動時にタイトルの後ろへフィールドが透ける問題と、終了時にシーンを先に解放して灰色になる問題は、この先頭・末尾確認が効いた。

26秒の `demo.gd` は、見どころを収めるため部屋・装備・ボスHPを撮影用に準備し、操作自体は実入力で発生させた。通常ルールのクリア証明としては扱わず、状態を書き換えない `playthrough.gd` の結果と区別した。

### CI artifactとwebtunnel

CIでも撮影・起動録画を実行し、最終runの47PNGとmp4の0・2・4秒および末尾を確認した。ローカルとCIでは無敵点滅の撮影タイミングに違いがあり、ローカルの正常画像だけでは不十分だった。CIの実際の画像を確認したことで、描画後の可視判定へ撮影処理を直せた。

webtunnelではWebGL2とGodotの起動完了を確認し、実キー・マウスでタイトル→開始→フィールド移動→敵との接触でゲームオーバー→入口から再開→メニュー→タイトル復帰を確認した。専用の状態書き換えは使わず、操作後に自分のセッションを停止した。

Web実操作の対象は `a097935`。その後に初回表示と開発用の撮影・録画処理を修正し、最終 `181b832` はローカルとCIで再検証した。Web上で全12室の通常攻略を再実行したわけではない。

ローカルでは通常の起動targetでCoreAudio出力、F11の全画面往復、通常終了を確認し、別に `--quit-after` の終了も検証した。macOS・Windows・Linux・Webのエクスポートは成功したが、Windows/Linux実機の起動と物理ゲームパッドは未検証。初見の難度や主観的な音質評価も残る限界である。

### 証拠の共有

PRには、47画面、8キャラの連続画像、起動・操作録画のフレーム、Web操作画像の合計65枚を新規添付した。公開URLを再取得し、ローカルとSHA-256が一致することを検査した。最終CIは33件すべて成功。画像・動画・ログの実物を揃えることで、成功したコマンドと、実際に見える結果を分けて確認できた。

## 6. Godot固有のハマりどころと回避策

| 現象 | 原因・回避策 |
| --- | --- |
| importがexit 0でも `user://` の作成エラーが残る | sandbox権限とGodotの終了コードを別に扱う。絶対パスのログ出力に加え、ログ全文を検査し、許可された環境で再実行する |
| HUDのTextureRectが指定サイズからはみ出す | テクスチャ由来の最小サイズが残っていた。`expand_mode` と伸縮設定を先に決め、最後に表示サイズを設定する |
| SVGスプライトを大きく使うと粗く見える | ゲーム中のセル解像度とタイトルの表示用途を分ける。元の図案からタイトル用に大きい独立SVGを生成する |
| InputMapに登録したのに方向・ボタンが合わない | 数値の記憶に頼らず `Key` / `JoyButton` 定数と照合し、イベントを投入して実際に移動・決定・攻撃することを検証する |
| スクロールで旧HUDまで動く | 旧画面の全体画像を使っていた。プレイ領域だけを切り出して遷移に使う |
| 遺跡の暗さがUIまで影響する | 環境光と主人公の照明はワールドで扱い、HUDは独立した `CanvasLayer` に置く |
| 前室の獲得ポップやパーティクルが残る | 部屋変更時に演出ノードを置き換え、所属するTweenも一緒に終了させる |
| 起動直後にフィールドがタイトルへ透ける | 初回UI構築も透明からフェードしていた。初回は完成した画面を表示し、その後の切替にフェードを使う |
| 無敵点滅中の主人公がCI画像から消える | 物理フレーム時点の判定と描画結果がずれる。`RenderingServer.frame_post_draw` 後に可視状態を調べ、描画済みの画像を保存する |
| 終了時に音声関連のリーク警告が出る | 停止、stream参照の解放、ミキサー処理の待ちを終了処理に入れる。Movie Makerでは終了12フレーム前から音声を停止する |
| 操作録画の末尾が灰色になる | `queue_free()` 後に描画を待っていた。最後の画面を保持し、ノード解放は `SceneTree.quit()` の終了処理へ任せる |
| CIのV-Sync警告 | Xvfb/llvmpipeの切替非対応。既存規定のこの警告だけを許容し、ERRORやリークをまとめて除外しない。最終CIでは撮影・録画ログに各1件、ローカル最終ログでは0件だった |
| Web版を開いてすぐ操作すると画面がまだない | Godot既定HTMLの `#status` が除去されたこととWebGL2を確認してから操作する |
| Webのクリック位置がゲーム座標とずれる | canvasの実寸と1280×720の比率からスケール・余白を計算する。runnerのviewportはゲームと同じ縦横比とは限らない |

ログ検査では、撮影名に含めた `warning` という語が警告判定へ誤反応することもあった。撮影名を `bomb-fuse` に変更し、ログの警告検査そのものを広く緩める回避はしなかった。

今回特に再利用したいのは、通常入力の攻略テスト、音声解放と録画終了の扱い、描画後に可視状態を確認する撮影処理の三つである。
