# rhythm 手直しラウンドの振り返り

対象は issue #43 の次の手直しラウンド。既存のリズムゲームの仕様と受け入れ条件を維持しつつ、汎用的な夜空・パネル中心の画面から、画像生成した「祭りの切り絵」の世界へ作り替えた。

PR: https://github.com/bannzai/godotpractice/pull/77

## 1. 開発の進め方

最初に作業指示書、AGENTS.md、PROJECT.md、issue #43、前ラウンドの PR #51、過去のヒアリング、`documents/knowledge/rhythm.md` を読んだ。その後、変更前の `make rhythm-run` を実行し、タイトル、選曲、演奏画面を実際に操作・撮影した。ここで、画面下の共通操作ガイド、角丸パネル、夜空と街並み、ボタン式の選曲が他ゲームと似ており、タイトルを隠すと rhythm 固有の体験だと分かりにくいことを確認した。

実装は次の順で進めた。

1. 既存の3曲×2難易度、判定、保存、入力、結果画面を残す前提で、祭り会場を一つの世界として使う画面構成を決めた。選曲を「一覧から選ぶ」操作ではなく、左右入力で三つの屋台の前を歩く操作へ置き換えた。
2. `image_gen` で背景を先に生成し、その背景を画風参照にして、キツネの太鼓奏者、鳥の笛奏者、ウサギの三味線風奏者、コンボ用提灯を生成した。背景を先に固定したことで、黒い輪郭紙、朱・藍・山吹・生成りの配色、紙の質感を後続素材へ揃えられた。
3. Rampart One を取得し、既存の M PLUS Rounded 1c と交換した。生成PNGの寸法・RGBA・透過を確認してから Godot へ import した。
4. `main.gd`、`stage.gd`、`dancer.gd` を変更し、祭り会場、屋台選曲、太鼓の面と縁を模した判定線、提灯コンボ、太鼓の張りを模した成功ゲージ、紙影シェーダを組み込んだ。画面下の共通操作ガイドは廃止し、開始札、選択中の屋台、演奏する太鼓、結果画面の札のように、操作対象の近くへ案内を置いた。
5. 初回演奏前の「場内の稽古」を追加した。朱を一打、藍を一打、朱を350ms以上長押し、という順で実入力を受け付け、完了後に本番へ進む。スキップも同じ場面に置き、背後の操作が反応しないようにした。
6. 既存曲の長さ、BPM、譜面時刻を変えず、Pythonの生成スクリプトで和太鼓の面・縁、笛、三味線風の音色へ差し替えた。ざわめき、拍子木、遠花火、風鈴からなる24秒の環境音を別トラックとして追加し、全場面で流した。
7. selfcheck、実入力のintegration、22画面のスクリーンショット、5秒の起動録画、26秒の実入力録画を順に整備した。ローカル検証後に Web エクスポートを webtunnel で操作し、最後にCI artifactをダウンロードして再度目視した。
8. 変更前後、他ゲームとの識別比較、チュートリアル、アニメーション連続フレーム、Web実操作を比較画像にし、`puts upload` で公開してPR本文へ掲載した。実装、音と稽古、知見の3コミットに分けてpushし、CI全件成功後にPRをReady for reviewへ変更した。

詰まった点と解決方法は次のとおり。

- 生成した奏者と提灯を最初に `TextureRect` へ置いたところ、原画像の大きな寸法がControlの最小サイズへ効き、画面を覆った。`Sprite2D` へ変更し、配置枠の幅・高さをテクスチャ実寸で割った縮尺を明示して解決した。縮小一覧だけでなく原寸のスクリーンショットでも確認した。
- 前面へチュートリアルを重ねるだけでは、背後のボタンや通常演奏の入力が反応する可能性があった。背後のボタンをdisabledにし、F/J入力を通常演奏より先にチュートリアルへ分岐させ、パネルでマウス入力を止めた。
- Movie Maker は固定フレームのゲーム時間を実時間より速く進める一方、チュートリアルの長押し判定は `Time.get_ticks_msec()` を使う。録画スクリプト上の350msでは実時間が足りなかったため、押下から解放までを映像時間で1.5秒空け、実時間でも350msを超えることを実行結果で確認した。
- 画像生成素材ごとに紙影を変えられるようにする際、同じ `ShaderMaterial` を共有すると一つの変更が全素材へ波及する。各 `Sprite2D` に個別のMaterialを作る形にした。
- 環境音を独立トラックにした結果、BGMだけでなく環境音も通常終了、録画終了、headless検証の全経路で止めてstreamを解放する必要が生じた。`stop_audio()` に集約し、停止・解放後に待機することで終了リークを防いだ。
- CodexのsandboxではGodotの通常の設定・ログ保存先への書き込みが失敗することがあった。作業領域内のself-contained Godotと絶対パスの `--log-file` を使い、exit codeだけでなくログ全文を検査した。
- 正常な音声同期の計測名 `error_ms` がログのERROR検索に一致した。検査条件を緩めず、計測名を `deviation_ms` に変えた。

## 3. 欲しかったが無かったツール・skill・スクリプト

- **画像生成一式の管理入口**。背景を一度決め、その画像を画風参照として複数キャラクターとUI素材へ引き継ぎ、期待ファイル、RGBA、四隅だけでなく不透明領域の外接矩形と余白率まで一括検査する入口が欲しかった。今回は5回の生成と各画像の確認を個別に行った。
- **生成PNGのゲーム内占有率を検査する仕組み**。テクスチャ実寸、不透明領域、配置予定の矩形を入力すると、推奨scaleと画面占有率を返すスクリプトがあれば、`TextureRect` で巨大表示になった問題をimport直後に検出できた。
- **音声だけを再生成するオプション**。生成スクリプトには `--images-only` があるが、音色や環境音だけを直す時に `--audio-only` が無かった。全音声と画像を巻き込まず、BGM、SE、環境音を選択して再生成できると待ち時間と差分確認が減る。
- **Movie Makerと実時間を混ぜない入力シナリオ用の時計**。本番の長押し判定、integration、録画で同じ差し替え可能な時計を使えれば、`Time.get_ticks_msec()` と固定fpsの不一致を避けられる。今回は録画イベント間隔を実測で広げたため、マシン速度へ依存する余地が残る。
- **スクリーンショット・動画・CI artifactからPR証拠を作る一括処理**。役割別の画像一覧を渡すと、原寸検査、ラベル付き比較画像、動画の一定間隔フレーム、`puts upload`、PR本文用Markdownまで生成する仕組みが欲しかった。今回は22枚の確認、複数の比較画像作成、8回のアップロードを個別に行った。
- **webtunnel上のGodot向け入力再生**。ゲーム座標とブラウザ座標の変換、キーの押下・解放、指定時間の長押し、画面遷移の待機、console確認をシナリオとして保存できると、72秒の実操作と再撮影を再利用しやすい。

## 4. 素材の準備方法と使い勝手

### 画像

新しい見た目の中心は、ChatGPTのbuilt-in `image_gen` で生成したPNGである。まず1280×720の祭り会場を、黒い輪郭紙、朱・藍・山吹・生成り、三つの屋台、提灯、花火、文字なし、という条件で生成した。次にその採用画像を画風参照として、キツネの太鼓奏者、鳥の笛奏者、ウサギの三味線風奏者、UI用提灯を透過背景で生成した。

背景を先に作る方法は、空間構成と画風を一度に固定でき、文章だけで各素材を独立生成するより色、輪郭、紙の密度が揃いやすかった。手続きSVGよりも、衣装、屋台、色紙の断面、輪郭の揺れが自然で、祭りだと説明文より先に伝わる点が良かった。一方で再生成は非決定的で、正確なピクセル寸法、余白、重心、ゲーム内の占有率は指定どおりにならない。採用PNGとプロンプトの要点を残し、配置後のスクリーンショットを検査する必要があった。

前ラウンドの手続きSVGは、コードから同じ結果を再生成でき、部品、色、全フレームの規則的な修正には強い。今回は主役の見た目を生成PNGへ移したが、生成モデルは規則的なフレーム差分を保証しにくいため、一枚絵へ回転、移動、伸縮、色変化を加えて待機・拍ダンス・命中・ミス・祝福を表現した。この使い分けは、絵の質感には生成モデル、決定的な状態変化にはGodot側のアニメーション、という整理になった。

### BGM・SE

外部の楽曲・録音サンプルは使わず、既存の `scripts/dev/generate_assets.py` を変更してPython標準ライブラリでPCMを決定的に合成し、ffmpegでOGG/WAVへ変換した。3曲の長さ、BPM、譜面の基準時刻は維持し、ドラムを和太鼓の面と縁、旋律を笛と三味線風の音色へ置き換えた。入力SEも低い面と硬い縁で分けた。

ざわめき、拍子木、遠花火、風鈴は24秒の `festival-ambience.ogg` にまとめ、BGMとは別の `AudioStreamPlayer` で全場面に流した。独立トラックは曲を変えても再利用でき、祭りの場所としての連続性を出しやすい。反面、音声プレイヤーが増えるため、headless、通常終了、Movie Maker終了のすべてで停止・解放を検証する手間が増えた。

手続き音声は、BPMと譜面時刻を厳密に揃えられ、外部素材の権利確認が不要で、再生成も同じ結果になる点がリズムゲームに向いていた。一方、音楽的な自然さ、楽器らしさ、ミックスの好みは数値検査だけでは判断できない。今回確認できたのは再生、同期、非リークとゲーム内での聞き分けであり、外部スピーカーや各OS実機での聴感比較までは行っていない。

### フォントとライセンス

Rampart OneはGoogle Fontsを素材源とし、game-asset-searchの `fetch-asset.sh` で一覧を確認してから取得した。`RampartOne-Regular.ttf` と実際の著作権表示を含む `OFL.txt` を同梱し、SIL Open Font License 1.1、作者、取得URL、無改変であることを `assets/CREDITS.md` に記録した。既存のM PLUS Rounded 1cは画面から外した。

Google Fontsはファミリー名からフォント本体とOFLを一緒に取得でき、publicリポジトリへ入れる条件を確認しやすかった。画像生成物はCC0と断定せず、OpenAI利用規約に基づく独自生成物として、使用手段とプロンプト要点を記録した。外部のフリー画像、BGM、SEは採用していないため、素材サイトの検索・作者ごとのライセンス比較・加工は今回発生しなかった。

## 5. 動作確認の方法

| 方法 | 今回行った確認と効いた点 | 足りなかった点・限界 |
| --- | --- | --- |
| headlessのselfcheck | 譜面、スコア、ゲージ、保存、全6譜面のPerfect完走、時刻の進め方に依存しないMiss処理など、描画に依存しない回帰を高速に確認した | UIの重なり、巨大表示、紙の質感、音の聞こえ方は分からない |
| 実InputEventのintegration | キーボード、Joypadイベント、マウス、タッチ、左右の屋台移動、チュートリアル、通常・長押し、環境音とBGMの同時再生、終了時解放を本番シーンへ入力して確認した | Joypadイベントは物理ゲームパッドの接続確認ではない。制御した時計での完走は人が曲を演奏した感触の確認ではない |
| `screenshot.gd` | タイトル、屋台選曲、移動後のハイライト、音調整、チュートリアル4段階、通常演奏、長押し、fever、成功・失敗結果、三奏者、命中・ミスの開始・中間・終了を計22枚撮影した。原寸と縮小一覧の両方を目視し、巨大表示と重なりを検出できた | 静止画では動きの速度、補間の滑らかさ、入力に対する反応時間、音との一体感までは分からない |
| `make movie` | 無操作の5秒録画と末尾フレームを確認し、起動直後の描画崩れ、真っ黒、終了直前の消失がないことを確認した | タイトル以降の操作経路やプレイ中の演出は確認できない |
| `movie-play` | 26.03秒の固定30fps録画へ実キーイベントを送り、タイトル、稽古、通常ノーツ、長押し、12成功、47ミス、通常の失敗結果まで到達した。一定間隔と末尾フレームを目視した | 中盤は音声とゲーム時計を同期して終盤へseekしており、全曲の等速完走録画ではない。Movie Makerと実時間の差もある |
| ローカルの `make rhythm-run` | 実ウィンドウへ左右、F、J、長押しをOS経由で送り、通常終了がexit 0になることを確認した | 物理ゲームパッド、Windows/Linux実機、外部音響機器は未検証 |
| CI artifact | CI run 34108936299の全job成功後、Linux llvmpipeで生成された22枚と5秒動画を取得した。PNGを一覧と原寸、動画を1秒間隔で目視し、ローカル固有ではない描画を確認した | Xvfbとソフトウェア描画であり、各OSのGPU・音声・入力デバイスの実機確認にはならない |
| webtunnel | run 34104654544のソフトウェアWebGLで、タイトル、左右の屋台移動、朱・藍・500ms長押しの稽古、演奏中の朱・藍・600ms長押し、72秒の自然終了、失敗結果、屋台への復帰をChromiumから実操作した。consoleとerrorsが空であることも確認した | Web版の確認であり、デスクトップ固有の全画面切替、物理パッド、CoreAudio等は確認できない。長時間録画の全フレームではなく120秒間隔のサンプルを目視した |

アニメーションは一つの方法だけで完了扱いにしなかった。`screenshot.gd` で命中・ミスの開始、中間、終了を固定時刻で撮り、位置、回転、伸縮、色の差と画面内への収まりを比較した。三奏者の待機・拍ダンス・祝福も代表画面へ含めた。さらに `movie-play` の一定間隔フレームで連続した遷移を確認し、webtunnelの実操作中にも拍ダンスと入力反応を目視した。これにより、静止画で形の差、動画で時間方向のつながり、Web実操作で入力直後の反応を分担して確認できた。

すべてのGodotログは末尾だけでなく全文をWARNING、ERROR、ObjectDB、resource、leakの語で検査した。CIのllvmpipeが出す既知のV-Sync警告だけは既定の除外として区別し、それ以外の警告・エラー・終了リークがないことを確認した。

## 6. Godot固有のハマりどころと回避策

- **大きな生成PNGをControlへ直接置くと、原寸がレイアウトへ影響する。** `TextureRect` の最小サイズに4096px級の画像寸法が残り、親Containerや画面全体を押し広げた。自由配置する装飾は `Sprite2D` にし、目標矩形とテクスチャ実寸からscaleを計算した。縮小画像だけでなく1280×720の原寸画面で確認する。
- **Controlのフォーカスは画面を作り直すたびに設定し直す。** 屋台の黄色い紙縁とEnter/Aの行き先が一致するよう、選択変更と画面再構築の後に対象ボタンへ `grab_focus()` した。見た目だけ選択状態を変えると、フォーカスが古いボタンへ残る。
- **前面パネルの `mouse_filter` だけではキーボード入力を遮断できない。** チュートリアル中は背後のボタンをdisabledにし、F/Jを通常演奏より先にチュートリアルへ分岐した。長押しは押下時刻を保持し、対応する解放だけで確定する。
- **Movie Makerの固定fps時間と `Time.get_ticks_msec()` の実時間は一致しない。** 録画で長押しを検証する時は、フレーム上の350msだけで成功すると仮定せず、実行結果で判定を確認する。今回の応急策は押下間隔を十分広くしたことだが、将来は時計の差し替えが望ましい。
- **共有した `ShaderMaterial` は全ノードで同じ状態になる。** 画像ごとに紙影の値を独立させるため、各 `Sprite2D` にMaterialを生成した。共通リソースを直接変更しない。
- **複数の `AudioStreamPlayer` を増やすと終了経路も増える。** BGM、環境音、SEを `stop_audio()` で一括停止し、stream参照も解放した。通常終了では0.2秒待ち、Movie Makerでは末尾に解放用フレームを確保した。headlessのDummyドライバでも同じ終了経路を検証した。
- **headlessでは描画品質を検証できない。** selfcheckとintegrationが通っても、生成PNGの巨大表示や重なりは見つからなかった。`screenshot.gd`、Movie Maker、CIのXvfb artifact、ローカル実起動を別に実行する必要がある。
- **sandboxではexit 0でもログ内に保存ERRORが残ることがある。** 作業領域内へself-contained Godotを用意し、すべての起動で絶対パスの `--log-file` を指定した。exit codeだけでなくログ全文を成功条件にした。
- **Godot import後の生成物も管理対象になる。** 新しいPNG、OGG、TTF、shader、GDScriptを追加した後にimportを実行し、必要な `.import` と `.uid` を含めた。`.godot/`、録画、スクリーンショットは管理対象へ入れなかった。
- **ログ検査用の単純なERROR検索は正常な識別子にも一致する。** 音声同期の正常な計測名 `error_ms` を `deviation_ms` に変更した。除外条件を広げるより、正常ログ側の語を誤解されない名前へ直す方が検査の強さを保てた。
- **WebGLの起動成功とゲーム操作成功は別に確認する。** webtunnelでは `started=true` とWebGL2の有効化だけで完了せず、実キー入力で結果画面まで進み、consoleとerrorsも確認した。runnerのビューポートが1280×656、ゲームが1280×720なので、マウス操作ではcanvasの矩形と余白を考慮する必要がある。
