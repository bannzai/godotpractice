## 1. 開発の進め方

### 作った順序

1. 作業指示書、AGENTS.md、PROJECT.md、issue #7、第1ラウンドのknowledgeとhearingを読み、10分生存・3種の武器・3択強化・最後の30秒の強敵を維持する範囲を確認した。既存のタイトルとプレイを撮影して目視し、UIの読みやすさや入力座標を基準にした。旧版もキャラごとの静止SVGは存在していたため、実際の変更は静止画の再設計とキャラ別アニメーションの追加だった。
2. 早期にdraft PRを作り、青緑の夜森・金色の灯・敵の珊瑚色という美術方針を決めた。担当ファイルを分け、サブエージェントにキャラ画像・フレーム再生、音声、検証を依頼し、自分は背景・UI・演出と統合を進めた。
3. 灯守・葉の精・夜羽・石の巨獣・夜の主のスプライトシートを作った。各体は160px角のセルを横6枚×縦5動作で持ち、AnimatedSprite2Dから使う。アイテム・弾・UIアイコン、森・霧・キーアート・ロゴも独立した画像として生成した。
4. ゲーム進行を持つRunStateと表示を分け、arenaで背景・キャラを描画し、その上にHUDと操作UIを配置した。Themeと同梱フォントを使い、ボタン反応、HP・撃破・結果の数値変化、画面遷移を追加した。
5. CPUParticles2DとTweenで命中・撃破・回復・レベルアップ・吸引・範囲攻撃を実装し、ヒットストップ・画面揺れ・フラッシュを接続した。同時に、タイトル・プレイ・ボス・結果の4曲と9種SEを統合した。
6. 既存のselfcheck・実入力検証を維持しながら、表示ノードの寿命、アニメーションの終了、演出の上限、音声解放を検査した。スクリーンショットと操作録画で見つけた不具合を修正し、通常ルールの600秒プレイと描画付き負荷検証を行った。
7. デスクトップ3種とWebをエクスポートし、webtunnelで実操作した。撮影画像と動画をputsでアップロードしてPRへ掲載し、最終CIのartifactも目視した。最後に知見を追記し、PRをレビュー可能な状態へ切り替えた。マージはしていない。

### 特に詰まった点と解決

- **音声の終了処理が検証経路によって違った。** 通常のCoreAudio、headlessのDummy、Movie MakerのDummyを同じ扱いにできなかった。小さい検証プロジェクトとログで切り分け、録画時だけDummyでも再生すること、参照解放後の待ち方、録画の末尾に解放用フレームを残すことをそれぞれ実装した。
- **死亡アニメーションが画像と画面の両方で隠れた。** 画像では沈み込みが隣セルへ漏れ、画面では結果UIが先に出て主人公の死亡を覆っていた。セル内の余白を修正し、死亡の最終フレーム保持と敗北結果の0.65秒待機を入れた。
- **大量撃破で重要な演出が消えた。** 単純な件数制限では命中・撃破が枠を使い切り、範囲の輪などが初回描画前に消えた。演出をイベント単位で管理し、通常演出48組、重要演出込み64組に分けた。60体一斉撃破の実際の経路を検査した。
- **26秒の操作録画が途中で止まった。** ボス戦で自然に追加の強化が発生し、ゲームが強化選択待ちのままになった。追加の決定入力を入れ、結果からタイトルへ戻るまで成功することを録画で再確認した。
- **putsが既定のアップロード先の読み込みで待ち続けた。** アプリのSwiftDataから設定を読む箇所が詰まっていることを切り分けた。既存R2認証を子プロセスのPUTS環境変数へ対応付けて設定済みバケットを指定し、永続設定を変更せずアップロードした。秘密値はログに出していない。
- **途中のCIで別ゲームが失敗した。** 他ゲームの撮影終了時のリークだったため、そのログを確認して失敗ジョブだけ再実行した。survivorsは初回から成功していた。最終コミットのCIは全28ジョブが一度で成功し、他ゲームのコードは変更しなかった。

## 4. 素材の準備方法と使い勝手

### 画像

PythonでSVGを手続き生成した。再生成入口はgenerate_assets.py、画像の本体はgenerate_polish_art.py。キャラ5体のスプライトシート、各体の静止画像、アイテム・弾・UIアイコン・床・遠景・近景・霧・キーアート・ロゴなど、31点を用意した。

輪郭の差を優先し、灯守のランタンと帽子、夜羽の羽、石の巨獣の甲冑、夜の主の枝角と冠を描き分けた。各動作では部位の変形、移動、揺れ、透過などをフレームごとに変えている。全150フレームの差分を検査した。

手続き生成は、配色の統一、一定のセル寸法、再生成、余白修正に向いていた。部位や寸法を数値で直せるので、隣セルへの漏れを修正しやすい。一方、数値上フレームが違っていても自然な動きや魅力的なポーズになるとは限らない。小さく表示したときの輪郭、動作間の差、消え方は目視が必要だった。今回は絵本風の2D表現にまとめたが、写実的な素材や複雑な手描き動作での使い勝手は試していない。

### BGM・SE

generate_polish_audio.pyでPython標準ライブラリによる波形合成を行った。BGMはタイトル・プレイ・ボス・結果の4曲、SEは攻撃・被弾・成長・経験値取得・回復・ボス登場・結果・吸引・UIの9種類。外部の旋律・録音サンプルは使っていない。

撥弦、木琴、ベル、倍音パッド、ベース、ノイズ打楽器を組み合わせ、場面ごとに譜面・拍周期・音色を変えた。全13音源の再生成SHA-256一致、飽和の有無、ループ接続点を解析し、Godotで実際の音声出力も確認した。

この方法は長さ・テンポ・ループ位置・音量を制御しやすく、外部素材探しと利用条件確認の手間を減らせた。一方、数値の検査だけでは聴き心地、疲れにくさ、場面への感情的な適合までは判断できない。今回は人の耳による主観試聴をしておらず、その品質を検証済みとはしていない。音楽生成サービスとの実測比較もしていない。

### フォント・ロゴ・Theme

第1ラウンドから同梱されていたZen Maru Gothic Mediumを継続利用した。今回新しいフォントを探して取得したわけではない。入手元とOFL-1.1の記録を保持し、OFL全文を同梱している。

https://fonts.google.com/specimen/Zen+Maru+Gothic

日本語表示をOS側のフォントに依存させず、macOS・LinuxのCI・Webで同じ字形を使えた点が有効だった。タイトルロゴはfontToolsでフォントの輪郭からSVGを生成し、実行環境でのSVG内の文字描画に依存しない形にした。ロゴ生成にはfontToolsが必要だが、生成済み素材の読み込みやゲームのビルドには不要。

Themeリソースに同梱フォントとボタンの各状態をまとめ、HUDや操作UIと配色を揃えた。素材の作者・生成手段・利用条件はCREDITS.mdへ記録した。独自生成物を根拠なくCC0と表記することはしていない。

### アニメーションの検証をどう組み合わせたか

1. 元素材をラスタライズし、全150セルの画像差分と透明余白を確認した。これでフレームの作り忘れや隣セルへの漏れを調べた。
2. 実際のAnimatedSprite2Dについて、5動作×6フレームの構成、キャラ固有の画像、時間によるフレーム進行、同じ動作で先頭へ戻らないこと、攻撃・被弾・死亡の完了通知を検査した。
3. screenshot.gdで、各キャラの待機・移動・攻撃・被弾・死亡を開始・途中・終了で並べた画像を撮り、目視した。画像ファイルの存在確認だけでは終わらせなかった。
4. 操作録画の時系列画像で、戦闘中のキャラ・演出・画面遷移をまとめて確認した。死亡後の再挑戦やフェードの終了は、静止画に加えて状態検査でも確認した。

この組み合わせでフレーム再生と画面上の崩れを確認できた。ただし2秒間隔の一覧は、6フレームの各動作を連続再生で鑑賞する代わりにはならない。主観的な滑らかさやゲーム全体の手触りを完全に評価したとはしていない。

### 主な実測と検証の終わり方

- 指定されたtest・screenshot・movie・desktop export・Web exportと、操作録画・通常起動の代替経路はexit 0。PR #25が当時未マージだったため、ルートのsurvivors-runはゲームディレクトリのrunで代替した。
- 通常ルールの600秒プレイはseed42、Lv89、撃破5810、HP100/100、3武器最大、敵数最大226、実行14.28秒。第1ラウンドと同じ戦績だった。
- 描画負荷はApple M4 Max、GL Compatibility、1280×720、計測10.027秒・1242フレーム。平均123.86fps、p95 10.618ms、敵342〜360体、画面内最小308体、ゲーム時間9.653秒。敵数を維持するためHPなどを調整した検証用状態で測った。
- 起動動画は音声平均-27.6dB・最大-13.3dB、操作動画は平均-28.5dB・最大-13.0dB。無音の動画を成功扱いにしない検査を入れた。
- Webは状態を注入せず、Enterで開始し、生存1分20秒・撃破125・Lv1の敗北結果まで進み、マウスでタイトルへ戻った。ブラウザエラーはなく、専用セッションとwebtunnelを終了した。
- 最終ローカル検証ログ26本にWARNING・ERROR・リーク診断なし。最終CIは28ジョブ成功。CIの撮影・録画には既存Makefileで許容しているV-Sync非対応警告が各1件あり、それ以外の診断・終了リークはなかった。
- PRに画像29点と操作動画1点を掲載した。うちローカルの撮影対象は23枚で、残りは操作録画の一覧・末尾とWeb4画面。CI artifactは別途ダウンロードして目視した。

## 6. Godot固有のハマりどころと回避策

| 問題 | 今回の回避策 |
| --- | --- |
| AnimatedSprite2Dへの移動指示で攻撃・被弾を途中で消してしまう | 表示側に再生の責任を持たせ、攻撃・被弾中の待機・移動要求は保留する。同じ動作の要求で再生位置を戻さない |
| 死亡表示をゲーム状態の敵削除と同時に消してしまう | 敵の安定したIDで状態と表示を対応付け、死亡中は専用の表示用子ノードへ移す。カメラ追従を続け、再開始時に破棄する |
| 死亡動作が待機指示で復活する、再挑戦でも死亡のままになる | 死亡は最終フレームを保持する。再挑戦だけ明示的なreset_motionで待機へ戻す |
| スプライトシートの動きがセル外へはみ出す | SVGをラスタライズして透明余白を検査する。死亡時の沈み込みも含め、160px角内に全動作を収める |
| 結果UIが死亡アニメーションを覆う | 敗北時だけ0.65秒待って結果UIを出す。状態検査とスクリーンショットの両方で確認する |
| CPUParticles2D・Tween・浮くLabelが増え続ける、重要演出が追い出される | 1回の演出を親ノードでまとめて寿命管理し、通常演出と重要演出の上限を分ける。終了後に子が残らないことと混雑時の実経路を検査する |
| 範囲表示をSprite2Dの幅で拡大すると、透明余白の分だけ攻撃範囲とずれる | Line2Dの頂点をRunStateの実際の攻撃半径から生成し、Tween終了時の半径まで検査する |
| ヒットストップで画面演出まで止めると、フラッシュや揺れが進まない | ゲーム状態へ渡す時間だけ短く止め、表示側の時間を進める |
| headlessのDummy音声とMovie MakerのDummy音声を混同する | 通常Dummyでは再生を開始せず、Engine.get_write_movie_path()で明示録画を判別して録画Dummyでは再生する |
| stopだけでは終了時に音声の参照が残る | stop、stream=null、音源辞書の解放を行い、通常の音声ドライバでは次のミックス反映を短時間待つ。shutdownは重複呼び出しで処理を繰り返さないようにした |
| --quit-afterでは次のゲームフレームが来ず、録画音声の解放が間に合わない | Godotがこの引数をGDScriptへ渡さないことを確認し、Makefileのフレーム数をSURVIVORS_MOVIE_FRAMESでも渡す。録画の最後の2フレームを解放に使う |
| Web単一スレッドで音声停止の同期待機をすると、再生処理自体も止める | デスクトップと同じ同期待機をWebには入れず、ブラウザ側の解放に委ねる |
| headlessのrootサイズと実画面サイズが違い、マウス座標がずれる | 引き継いだ入力検証を含め、検証用rootを1280×720に揃える。Webはcanvas外の余白を含む実画面座標へ合わせる |
| macOSのF11全画面切替は非同期 | 描画付きの入力検証で、各切替後にOSの遷移が完了するまで待つ |
| importや終了処理はプロセスがexit 0でも診断を出すことがある | exit codeに加えてログ全文と成功マーカーを確認する。既知のV-Sync警告は文字列を限定して区別し、他の警告・エラーを広く隠さない |
| ローカルsandbox内でGodotの設定・アプリデータやCoreAudioの操作が制限される | エンジンやゲームの問題と決めつけず、許可付きの実行で切り分けた。実際に成功した起動・終了結果を採用した |

今回有効だったのは、ゲームの状態、表示ノードの状態、描画結果、音声の実出力を別々に観測して突き合わせることだった。headlessが通ったことだけで見た目を保証せず、録画ができたことだけで操作や音声を保証しないようにした。

未検証として残るのは、人の耳による主観試聴、物理ゲームパッド、Windows/Linuxの実機起動、人間の初見難度、全機種での性能。エクスポート成功や合成入力、自動プレイの結果と区別してPRにも記載した。
