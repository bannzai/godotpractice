# platformer 開発過程のヒアリング

対象は、この worktree で行った「そらいろ便」の第2ラウンドの品質向上と、その後の main 取り込み。既存の2ステージとゲームルールを土台に、キャラ画像・アニメーション・演出・背景・UI・音声を更新した。第1ラウンドの記録を参照した部分は、今回新たに作ったものと区別して記す。

成果物の PR:
https://github.com/bannzai/godotpractice/pull/26

## 1. 開発の進め方

1. 依頼書、PROJECT.md、ゲームの issue、既存コード、前回の知見を読み、変更範囲と完了条件を確認した。地形・当たり判定・移動速度・残機などは維持し、既存の主人公と敵2種を対象にした。ボス・NPC・弾は既存仕様にないため追加しなかった。
2. draft PR を作り、画像生成、音声生成、キャラと演出の実装をサブエージェントへ分担した。画像のセル寸法・足元・動作名を揃え、自分は背景、タイトル、Theme、HUD、画面遷移、統合と検証を進めた。
3. キャラ別のSVGシートと物体・背景・UI素材を作り、`AtlasTexture` と `AnimatedSprite2D` へ組み込んだ。主人公7動作、敵は各5動作、各動作6枚の計102フレームになった。BGMは場面別5曲、SEは8種類へ更新した。
4. 粒子、光輪、得点表示、ヒットストップ、画面揺れ、フラッシュを実装した。背景は多層の視差と空のシェーダ、UIはフォント・配色・パネル・ボタンを統一し、実際の画面を撮って調整した。
5. selfcheck・playcheckを拡張し、キャラのフレーム、入力割当、実際の状態遷移、演出の解放を確認した。続いて画面撮影、起動録画、実キー入力によるプレイ録画、通常終了とフレーム数指定終了、各OSとWebのエクスポートを検証した。
6. push後のCI artifactを取得してPNGと動画の抽出フレームを見た。Webtunnelで通常起動したWeb版を実操作し、タイトル・プレイ・結果・タイトル復帰を撮影した。確認済みPNGをputsで公開し、PRへ埋め込み、知見を更新してPRをreadyにした。
7. 最後にPR #25を含むmainを取り込んだ。競合はなく、`run: import` と既存のmkdir・ENGINE_LOG付きレシピが残った。`make -C games/platformer test` と実ウィンドウの起動・正常終了を再確認し、マージコミットをpushした。

主な詰まりと対処は次のとおり。

- **フレーム数があっても絵が重複した。** sinだけで姿勢を変えると周期内に同じ姿勢が現れた。cosも使って位相を分け、各動作の6枚がすべて異なることを画像差分で検査した。
- **録画の自動操作が途中で止まった。** 別のGodotウィンドウにフォーカスが移ると保持中のキーが解除され、自動操作側の状態と食い違った。`Input.is_physical_key_pressed()` から現在の状態を読むようにし、録画用スクリプトでは入力蓄積を無効化した。最後に最新の画面で録画し直した。
- **終了コード0でも音声のリーク警告が出た。** 通常終了と`--quit-after`を分けて調べ、停止を音声スレッドへ反映する時間を確保した。警告を無視するだけでは完了としなかった。
- **Webで右入力のはずが左に動いた。** 配信物の取り違えを確認した後、受信キーを一時観測した。ゲームのInputMapとは別に、操作ツールの長押しが物理キーAを送る問題を特定し、正しく届く操作で検証した。
- **putsがアップロード前に停止・失敗した。** 保存済み設定を読む際のmacOSアプリデータアクセスとSQLiteの問題だった。許可が通った実行でアップロードし、残りの確認画像を1枚へまとめて追加のアップロード回数を減らした。

代表的な検証コマンド:

```bash
make test GAMES=platformer
make screenshot GAMES=platformer
make movie GAMES=platformer
make -C games/platformer movie-play
make -C games/platformer exitcheck
make build-all GAMES=platformer
make build-web GAMES=platformer
make -C games/platformer run RUN_ARGS='-- --verify-close'
```

`--verify-close`は、このゲームに用意した開発用引数。通常のメインシーンを起動し、ウィンドウを閉じる処理を自動で通して終了させた。Godotの標準オプションではない。

Webtunnelでは次の形で起動した。

```bash
WEBTUNNEL_REPO=bannzai/godotpractice bash ~/.agents/skills/webtunnel/scripts/webtunnel-cli.sh up platformer --software-webgl --ref polish/platformer --wait
```

CI画像の取得には`gh run download <run ID> -n platformer-screenshot-and-movie -D <保存先>`を使った。終了時は`down platformer`を実行した。commit・push前には既存の電話番号差分検査スクリプトも使用した。main取り込み時の検出は、確認した範囲ではSVGの描画座標による誤検知だった。

## 4. 素材の準備方法と使い勝手

### 画像

第1ラウンドの素材生成コードを残しつつ、`generate_polish_art.py`で第2ラウンド用の23個のSVGを生成した。キャラ別3シート、収集物・補給ケース・地形・ゴール、草原と洞窟の遠景・近景、タイトルのキーアートとロゴ、UIアイコン、粒子画像を用意した。

- 主人公は64×80のセルを6列×7行、敵は64×56を6列×5行とした。足元を揃え、表情・脚・腕・小物を動作別に描いた。
- SVGコード生成は、パレット・透明背景・セル寸法・足元を厳密に揃えやすく、修正と再生成も容易だった。タイトルには大きな専用画像を作れた。
- 一方、姿勢やシルエットの魅力は自動では得られない。周期式だけだと同じ絵が出る問題もあり、画像を見て調整し、差分検査を追加した。セル内に収める調整や背景の継ぎ目処理も必要だった。
- GodotがSVGをインポートするため、生成しただけでは表示確認にならない。import後の実描画で、切り出し・大きさ・背景との見分けやすさを確認した。

外部の画像素材サイト、画像生成サービス、既存作品の素材は使っていない。そのため、今回の経験からそれらとの品質・費用・速度の優劣は評価できない。

### BGM・SE

`generate_polish_audio.py`で、Python標準ライブラリだけを使い32 kHz / 16-bitステレオWAVへ合成した。既存曲・録音・サンプルは使っていない。

- BGMはタイトル、草原、洞窟、成功結果、ゲームオーバーの5曲。ベル、撥弦、リード、和音、低音、ドラムを場面別に組み合わせた。
- SEはジャンプ、踏みつけ、コイン、強化、退場、配達完了、被弾、UIの8種類。BGMの余韻はループ先頭へ折り返し、SEは両端を無音にした。
- コードで音量・長さ・音色を調整でき、13ファイルの再生成ハッシュが一致した。検査ではBGMのピーク0.62、SEは0.70以下、ループ境界差は最大0.00272だった。
- 外部アカウントや素材ライセンスの選別を必要とせず再現できる点は便利だった。一方、数値検査では音楽の良さや聴感上の不自然さは判断できない。聴覚評価は未実施であり、「音が良い」と確認した扱いにはしていない。

### フォントとクレジット

フォントは第1ラウンドで同梱済みのNoto Sans JPを継続利用した。素材台帳ではGoogle Fonts由来、SIL Open Font License 1.1として記録されている。今回、新しく取得し直したものではない。

https://fonts.google.com/specimen/Noto+Sans+JP

日本語をOSの代替フォントに頼らず表示でき、ゲームのThemeと確認画像の見出しに同じフォントを使えた。可変フォントのウェイト指定にはGodot側の注意点があるため、既存の600指定を引き継いだ。OFL全文と素材台帳を同梱する構成も維持した。

画像・音声はプロジェクトのオリジナル生成素材として、生成コード・用途・出典を`assets/CREDITS.md`に記録した。第三者のCC0素材として扱ってはいない。

## 5. 動作確認の方法と、効いた点・足りなかった点

| 方法 | 実際に確認したこと | 効いた点と限界 |
| --- | --- | --- |
| headlessのcheck / selfcheck | シーンのロード、Sessionの状態、残機・得点・時間・ステージ遷移、入力割当、素材とクレジット、アニメーション定義 | 短時間で繰り返せた。描画の見栄え、フォント、音の聴感は分からない。 |
| headlessのplaycheck | 物理フレームを進め、移動・ダッシュ・跳躍・ブロック・強化・踏みつけ・被弾・再挑戦、合成キーボード/パッド入力、2ステージ走破を確認 | 状態だけを直接設定する検査で見逃す入力割当の誤りを検出した。物理ゲームパッド実機の接続検証にはならない。 |
| 描画付きscreenshot.gd | タイトル、草原、洞窟、強化・踏みつけ、ポーズ、各結果、全画面、縮小画面、キャラ動作一覧、物体、8演出の時系列 | 実際のGodot描画で文字・余白・切り出し・背景・UIを見られた。1枚だけでは動作速度や遷移の自然さを判断できない。 |
| movie | 起動からの5秒動画を作り、0.5秒間隔と末尾のフレームを確認 | 起動直後の黒画面や描画欠落を確認できた。操作しない録画なのでゲームプレイの確認は別に必要。 |
| movie-play / demo.gd | タイトルから実キーイベントを投入し、座標の書き換えや無敵付与なしで2ステージを走破 | 最新版の動画は29.93秒、最終結果へ26.82秒で到達。2秒間隔の15枚と末尾を目視した。全フレームの連続視聴や全ルートの網羅ではない。 |
| exitcheck / 通常run | 通常close、`--quit-after`、音声再生中の終了 | exit 0だけでは見逃す音声リークを検出できた。最後のmain取り込み後にもimport→実ウィンドウ起動→正常終了を確認した。 |
| CI artifact | LinuxのXvfb + llvmpipeで撮った画面・キャラ・物体・演出と起動mp4をダウンロードして目視 | ローカルだけで成立する表示ではないことを確認できた。既知のV-Sync未対応警告が描画ログに各1件あり、それとゲームの警告を区別した。 |
| Webtunnel | 自分のブランチのWeb版でタイトル→プレイ→残機切れの結果→タイトル復帰。キー・クリック操作と画面・コンソールを確認 | エクスポート成功だけでは分からないブラウザ上の入力を確認できた。Webの結果でデスクトップ固有機能の確認を代用しない。 |
| build-all / build-web | macOS、Windows、Linux、Webの出力生成 | 全targetのexit 0を確認した。Windows/Linuxの実機起動は未検証。 |

### アニメーションの確認をどう分けたか

1. **素材の成立**: 各キャラに4種類以上の動作があり、各動作6枚、再生速度が正、切り出しが画像内に収まることをselfcheckで確認した。各6枚の画素がすべて異なることも検査した。
2. **絵の見え方**: 全動作の1・3・6枚目を固定表示したPNGをキャラ別に生成し、姿勢・セルの切れ・キャラ同士の違いを見た。この一覧自体は時間を進めた録画ではない。
3. **ゲーム内の遷移**: playcheckで実際に走る・踏む・被弾する・死亡する状況を作り、対応するアニメーションへ移ることを確認した。被弾・退場・踏みつけの非ループ設定も確認した。
4. **演出の時間変化**: コイン、ケース開封、着地、強化、踏みつけ、被弾、退場、配達完了の8演出は、実時間を進めて開始・途中・終端を撮影した。演出ノードの解放と画面揺れの収束はplaycheckでも検査した。
5. **実プレイとの組み合わせ**: movie-playとWeb操作で、背景・HUD・キャラ・演出が一緒に表示される状況を確認した。PNGと抽出フレームで見た範囲を超えて、全動作の全フレームを目視済みとはしていない。

ローカル検証では保存ログ全文をWARNING/ERRORで調べた。CIはmain取り込み前の最終実装で全ジョブ成功し、該当artifactも確認した。最後のmain取り込み後は依頼されたtestとrunを再実行した。main取り込み後に全エクスポート・Webtunnel・全画像撮影をやり直したわけではない。

## 6. Godot固有のハマりどころと回避策

### 今回の実装・検証で確認したこと

- **`--quit-after`を`OS.get_cmdline_args()`から読めなかった。** エンジンが消費した引数が残らず、終了フレームを推定して先に音を止める案は機能しなかった。通常closeでは停止後にTimerで待ち、終了中の`_exit_tree()`では音声停止後に150 ms待つ実装にした。この待機時間は今回の環境で検証した対処であり、すべてのGodot環境に共通する保証ではない。
- **音声リソースの解放は停止命令と同時に完了しない。** 音声スレッドへ反映される前に終了するとリーク警告が出た。headlessでは再生を始めず、描画付きの通常close、`--quit`、`--quit-after`、Dummy/CoreAudio、複数SE再生中を分けて確認した。
- **InputMapの数値が間違っていてもアクション名のテストは通る。** 既存の左右キー数値に誤りがあった。Godot 4.7で`KEY_LEFT=4194319`、`KEY_RIGHT=4194321`を実測して修正し、割当検査と物理キーイベントの移動検査を追加した。
- **フォーカス喪失が録画用の合成入力にも影響した。** 別ウィンドウの検証を並行すると保持キーが解除された。入力送信側のキャッシュだけを信じず、Godotが保持している物理キー状態を読むようにした。
- **Themeの最小寸法がHUDの指定高さに影響した。** 進行バーが想定より厚くなったため、Themeと最小寸法を整えてから高さを指定し、撮影し直して確認した。
- **SpriteFramesの存在だけではアニメーション品質を保証できない。** 同じ姿勢の重複やセルからのはみ出しは別に検査する必要があった。足元を基点に変形し、状態別のフレーム差分を検査した。
- **背景の視差には画像の継ぎ目も必要だった。** 異なる速度で動かすだけでなく、繰り返し画像の左右端の高さを揃えた。空のシェーダと多層画像はGL Compatibilityのまま実装した。
- **ヒットストップを全体の時間倍率へ適用すると他の処理にも影響する。** 今回は各ゲームノード内の短い停止で実装し、UIや終了処理の時間まで変えない構成にした。停止・揺れが終わることも検査した。
- **Web上のlogical keyとphysical keyが一致しない場合があった。** `agent-browser keydown ArrowRight`は論理値が右でも物理値がAだった。`press ArrowRight`は正しく、長押しはDで確認できた。操作ツールの問題へInputMapを合わせず、受信値を観測して切り分けるのが有効だった。
- **Webの診断起動にもエンジンの初期化手順が必要だった。** releaseテンプレートでは今回`--script`による診断が機能せず、一時的な診断PCKを使った。Engineの`preloadFile` / `start`を使う際は、先に`init("index")`が必要だった。診断ファイルは一時ファイルとして扱い、ゲームの配信ソースには含めなかった。
- **Webのポートと余白はcallerの設定に依存した。** 一般例の8080ではなく、このworkflowは8000を使っていた。ブラウザの1280×656とゲームの1280×720が異なるため、左右余白と縮尺を考慮してクリックした。
- **インポートと実ウィンドウ起動にはsandboxの制約があった。** Makefileの`--log-file`を作業ディレクトリ内の絶対パスへ向ける既存対策を維持し、必要な実行権限の下で確認した。mainからの`run: import`取り込み後もこのレシピを残した。

### 第1ラウンドの記録から引き継いだ注意点

以下は既存コード・知見を読んで踏襲したもので、今回新たに同じ不具合を再現したという意味ではない。

- `_draw()`内だけで`load()`したテクスチャは、描画前に参照が消えて白い矩形になった記録がある。`preload`定数などで参照を保持する構成を維持した。
- 背景をワールドと同じCanvasItemへ描くとカメラ移動で流れ去る。背景専用CanvasLayerと、カメラ位置を使った視差の構成を引き継いだ。
- Noto Sans JP可変フォントのウェイトには、文字列だけでなく`TextServer.name_to_tag("wght")`の数値タグを使う対策を引き継いだ。
- メニューのButtonは独自のconfirmだけでなく`ui_accept`も使うため、パッドAの割当を両方で維持した。今回も合成パッド入力でメニュー操作を確認した。

Godot以外の周辺要因として、putsのmacOSアクセス許可、ブラウザ操作ツールのキー変換、CIのllvmpipe警告があった。ゲームのバグと環境・操作ツールの問題を分けるため、生成物・受信イベント・ログを実物で照合する作業が有効だった。
