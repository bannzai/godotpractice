# 潮風カート 開発ヒアリング

対象は issue #38 の3Dカートレース。実装、ローカル検証、Web実操作、CI確認、PRのレビュー待ちへの切替までを振り返る。

- PR: https://github.com/bannzai/godotpractice/pull/53
- ゲーム実装の最終コミット: `5ab93a0`
- 知見追記を含む最終コミット: `a3b2f1c`

## 1. 開発の進め方

### 作った順序

1. 作業指示書、issue、プロジェクトの制約、既存ゲームの実装・知見を読み、GL Compatibility、GDScript、ゲーム固有ディレクトリ内での作業という条件を確認した。
2. 「潮風カート／サンゴ湾サーキット」という独自テーマを決めた。自由な車両物理ではなく、コース上の距離と左右位置から3D座標を求めるアーケード方式を選んだ。コース関数を表示、走行、チェックポイント、ミニマップで共有した。
3. 担当ファイルを分け、サブエージェントにレースロジック、3Dカートとアニメーション、画像・音声を分担した。親はメイン画面、コース表示、HUD、統合と検証を担当した。
4. タイトルと車種選択から、3周レース、結果、再走・タイトル復帰までのループを作り、draft PRを出した。CPU、アイテム、ドリフト、落下復帰、ベスト保存を詰めながら、キャラクター表現・音・UIを統合した。
5. selfcheckと実入力の統合検証を整え、モデルの連続撮影、代表画面の撮影、実入力プレイ録画を追加した。画像を見てHUDや結果画面の文字配置を直し、ゴール待機中のタイム表示も修正した。
6. ローカルのテスト、録画、全プラットフォームへのエクスポート、通常起動と終了を検証した。Webでは実入力で3周を完走し、結果からタイトルへ戻った。
7. CI artifactを目視し、公開画像40枚をPRに掲載した。知見を追記してpushし、最新CIの全31ジョブ成功を確認してPRをレビュー待ちにした。マージはしていない。

### 詰まった点と解決

- **分担後の統合**: ロジック、見た目、音が別々に完成しても、実際の入力と画面遷移がつながるとは限らない。統合テストと実入力デモを置き、操作から結果までを通して確認した。
- **録画の操作が安定しない**: 一度だけのドリフトはCPUの攻撃と重なると潰れた。開発用シナリオの乱数を固定し、回復後に再試行した。アクセルもデモ中に継続して入力し、走行距離・アイテム取得・ブーストが成立しなければ失敗させた。
- **終了時の音声リーク**: 通常終了とMovie Makerでは音声処理のタイミングが異なった。停止と解放待ちを共通化するだけで済ませず、録画では終了フレームの前に音声を止める経路を作った。
- **Webの撮影が応答しない**: ページの起動判定は成功しても、agent-browserと直接CDPの撮影が応答しないセッションがあった。期限切れ後に新しいrunnerを起動し、DOM応答、画面プレビュー、CDP撮影を切り分けて確認した。新runnerでは撮影できたが、旧runnerの不調の原因は断定できていない。
- **GitHub CLIの接続タイムアウト**: curlで疎通できる一方でghが接続に失敗する場面があった。コマンド単位で `GODEBUG=netdns=cgo` を付けて接続できた。システム設定は変更していない。

進め方として、機能ごとの成功だけでなく「ループを通す」「実際に描画する」「終了する」を早期に検証した点は有効だった。一方、Web操作の完走確認が後半まで残り、撮影の不調への対処に時間を使った。次回は最小ループが動いた段階でWebの撮影と入力疎通も確認したい。

実行した主要な検証コマンドは次のとおり。単に用意したコマンドではなく、最終検証で終了コード0を確認したもの。

```bash
make test GAMES=kartrace
make screenshot GAMES=kartrace
make movie GAMES=kartrace
make -C games/kartrace movie-play
make build-all GAMES=kartrace
make build-web GAMES=kartrace
make kartrace-run RUN_ARGS='--script res://scripts/dev/run_smoke.gd'
```

`test` はlint・起動・selfcheck・integrationを含む。通常ウィンドウの起動確認は `run_smoke.gd` から閉じる通知を送って終了まで確認した。これとは別に、裸の `--quit-after 60` と `--quit-after 2` でも通常起動の終了を確認した。

## 3. 欲しかったが無かったツール・skill・スクリプト

今回の開始時点で、そのまま適用できず個別に作ったもの、または既存の仕組みに追加したいもの。

- **3Dモデルの全アニメーションをまとめて撮る手順**: モデル、状態名、撮影時点を渡すと、同じ照明・カメラで全車種を並べて撮影し、一覧まで作れるとよい。今回は `model_gallery.gd` を作った。開始・中間・終了直前だけでなく、状態遷移の前後を短い動画にする機能も欲しい。
- **実入力デモと録画終了処理の共通雛形**: 時刻ごとのキー・パッド入力、入力保持、乱数固定、達成条件、音声の事前停止、ログのエラー検査をまとめたい。今回は `demo.gd`、`movie.gd`、統合テストで個別に実装した。
- **Godot Webの撮影不調を切り分ける診断スクリプト**: runnerの生存、CDP応答、`#status` の消滅、WebGL、画面プレビュー、撮影要求を順に調べ、どこまで成功したかを出してほしい。新しいセッションへ切り替える際の接続先更新も含めると手戻りが減る。
- **証拠画像とPR本文の更新をまとめる仕組み**: ローカル画像のハッシュで未変更ファイルの再アップロードを省き、画面名・公開URL・検証元コミットを管理したい。今回は `upload-evidence.py` と `build-pr-body.py` を一時作成した。40枚を手で貼り直す負担は減らせた。
- **CI artifactの確認用一覧生成**: PNGの全件一覧、動画の一定間隔と末尾、ログ全文のエラー候補を一度に出せるとよい。目視そのものは残し、確認に必要な素材を揃える部分を自動化したい。
- **ゲーム固有の知見ファイルを考慮したCI対象判定**: `documents/knowledge/kartrace.md` だけの追記でも全ゲームのCIが走った。同名ゲームに対応付ける改善を提案した。共有物の変更は今回の担当範囲外なので実施していない。

後半に利用可能になったskill名だけを見て、今回使ったことにはしていない。上記のうち既存skillに統合できるものは、次回の整備時に内容を確認して重複を避けたい。

## 4. 素材の準備方法と使い勝手

### 画像・3Dモデル・背景

- `scripts/dev/generate_assets.py` でSVGを12点生成した。キャラ肖像3点、アイテム3点、UI画像6点を別ファイルにした。カワウソ、キツネ、フクロウは顔、耳、目、装備を描き分けた。
- 3Dカートは `kart_visual.gd` の独自メッシュ構成とマテリアルを使い、車種ごとに独立した `.tscn` を用意した。色だけでなく車体や顔・装備の形を変えた。背景もGodot上で海、島、灯台、ヤシ、雲などを組み立てた。
- タイトル用の `keyart.svg` は生成したが、最終タイトルの主ビジュアルには実際の3Dコースとカート展示を採用した。素材を生成したことと、その素材を画面で採用したことは区別する。
- 手続き生成はパレットの統一、部品の修正、再生成、第三者素材の追跡負担の小ささが利点だった。反面、コードを書けば絵の品質が自動的に上がるわけではなく、形状・構図・見え方の目視調整が必要だった。今回は単純な立体で統一した海辺の表現に向いていた。

### BGM・SE

- Python標準ライブラリで、倍音を持つベル・和音パッド・ベースと、キック・スネア・ハイハットを合成した。22050 Hz、16 bit、monoのWAVを生成した。
- BGMはタイトル、レース、最終周、結果の4曲。テンポ、移調、音の密度を変えた。SEはエンジンを含む8音で、取得、被弾、加速、カウントダウン、ゴール等を用意した。
- エンジン音はループ境界が連続になる周期の波形を合成し、ゲーム側で速度に応じてピッチを変えた。
- 外部APIや音源の取得が不要で再生成しやすかった。波形・ファイル・再生状態を機械的に確認できた一方、聴感による音楽的な良さや長時間聴いたときの疲れは未評価。再生できることを、聴感評価済みとは扱っていない。

### フォント・素材源

- 日本語フォントは既存のrollballに同梱されていたM PLUS Rounded 1c Mediumを無改変で複製した。OFL本文と著作権表示を保持し、共通Themeで使用した。新たな探索やダウンロードを省け、日本語表示を早期に安定させられた。
- 出典は `assets/CREDITS.md` に記載した。外部フォントと独自生成物を分け、独自生成物を根拠なくCC0とは宣言しなかった。
- 画像生成モデル、外部の3Dモデル集、外部BGM・SE素材集は今回は使用していない。そのため、それらの生成品質や検索・購入・ダウンロードの使い勝手は今回の実測としては評価できない。

## 5. 動作確認の方法と効いた点・不足した点

| 方法 | 実際の確認と有効だった点 | 限界・不足 |
| --- | --- | --- |
| headless selfcheck | コース配置、チェックポイント順、逆走、復帰、アイテム、順位、保存の解釈などを検証。計算と状態遷移の不具合を素早く切り分けた | 画面の文字重なり、モデルの見え方、実際の操作感は分からない |
| integration | InputEventから操作と画面ループを検証。マウス選択後のEnter、パッドイベント、F11の全画面化と復帰も確認 | 実物のゲームパッドを接続したプレイではない。全画面はheadlessだけでは検証できない |
| screenshot.gd | タイトル、カウントダウン、走行、所持アイテム、発動、ドリフト、加速、被弾、ゴール、結果の14枚を撮影 | 演出や所持品の状態を直接準備する画像は、実操作による到達の証拠とは分けた |
| モデル連続撮影 | 3車種を同じ画面に並べ、6状態を0%、50%、95%で撮影した18枚を確認。部位の動きと粒子、キャラの形の違いを比較しやすかった | 3時点の静止画だけでは補間全体や全ての状態遷移を保証できない |
| 起動movie | 5秒の起動動画をフレーム一覧と末尾で確認。真っ黒や初期表示の崩れ、録画終了時の問題に有効だった | 操作なしなのでゲームの中核を遊べるかは分からない |
| movie-play | 25.53秒の実入力走行を録画し、2秒間隔と末尾を確認。走行・取得・ブーストの成立条件もコードで判定した | 抽出フレームだけでは短い不具合を見落とす余地がある。全車種・全操作の長時間プレイではない |
| CI artifact | run 34035605388 の32PNGと5秒動画を取得。全画像、動画の0.5秒間隔と末尾を目視し、ローカル以外の描画環境でも確認した | llvmpipeの結果でありWindowsやLinux実機の操作確認ではない。V-Sync非対応の既定通知は残った |
| webtunnel | run 34047008328 のChromiumに実キー入力を送った。アクセル、短い左操舵、アイテムで3周を走り、44.10秒の結果からEscapeでタイトルへ戻った。4画面を撮影した | SwiftShaderでは進行が遅く、固定の実時間だけでは完走を判断できなかった。デスクトップ固有機能の保証にはならない |

アニメーションはAnimationPlayerの待機、走行、ドリフト、ブースト、被弾、歓喜の6状態を対象にした。連続画像で姿勢の差、被弾回転、歓喜の手上げ、火花・加速粒子を確認し、実入力録画では走行中の演出も確認した。結果画面の文字重なりは、終了コードやselfcheckではなく画像の目視で発見して修正した。

ローカルの最終ログは全文をWARNING／ERRORと終了時のリソース残存で検査した。CI描画ログにある既定除外のV-Sync通知は、ログが完全に無警告だったという報告には置き換えていない。

最終CI run 34047509012 は全31ジョブ成功。最後の変更は知見文書だけなので、目視したartifact・Web実操作のゲーム実装と最終HEADのゲームディレクトリが同一であることも確認した。PRに掲載した40枚は再取得してSHA256が一致した。CodeRabbitのステータスはpass表示だったが、説明は回数制限だったため、自動コードレビュー済みとは扱っていない。

未検証として残ったのは、物理ゲームパッドを接続した操作、Windows／Linux実機でのプレイ、聴感による音楽評価。エクスポート成功や合成InputEventで代替できたとは判断していない。

## 6. Godot固有のハマりどころと回避策

1. **sandboxとエディタ設定・user://**: 通常のGodotをsandbox内で動かすと補助ディレクトリ等への保存に失敗した。自己完結版を作業ディレクトリ内に準備し、GUI確認は許可された通常起動として実行した。
2. **Movie Makerと音声解放**: 録画は音声をフレーム単位で同期処理する。終了通知中に待つだけでは次のmixが進まず、裸の `--quit-after` を使った録画でリークを再現した。専用スクリプトから事前停止し、streamを外して複数フレーム待った。任意フレーム数の録画には `--audio-stop-at-frame` を用意した。
3. **消費済みのコマンドライン引数**: Godotが処理した `--quit-after` は `OS.get_cmdline_args()` に残らなかった。そこから終了フレームを推測する処理を除き、開発用のユーザー引数を明示的に渡した。
4. **Controlによる決定入力の消費**: 車種カードをクリックした後、ButtonがEnterを先に消費する場合があった。ゲームの決定操作を `_input` で扱い、処理済みにして画面遷移を確実にした。
5. **macOSの全画面切替は非同期**: F11で切り替えた直後に再度入力すると復帰検証が成立しなかった。ウィンドウ移行の実時間を待ち、全画面化と元の状態への復帰を両方検証した。
6. **Tween中断後の値の残存**: 演出を中断すると途中のフラッシュ色が残った。次のポップアップ開始時にフラッシュのアルファを初期化した。
7. **3Dの横方向ベクトル**: 坂で右ベクトルの長さが変わると、左右の移動量と表示・当たり判定がずれた。正規化した同じベクトルを共用した。
8. **路面メッシュと落下判定の不一致**: ショートカットの終端を別々に定義すると、橋の先の空中を走れてしまった。本線と木橋の路面存在判定をコースデータに集約した。
9. **ゴール時刻と画面遷移時刻の違い**: 全車を待って結果を表示するため、経過時間をそのままHUDに出すと自分の完走後もタイムが増えた。自分のfinish_timeに固定し、ベスト保存も自分のゴール時点で実行した。
10. **描画完了前の撮影**: 画像取得前にフレームを進め、`RenderingServer.frame_post_draw` を待った。モデル撮影はAnimationPlayerを指定時点へseekしてpauseし、粒子の表示待ちも入れた。これは全時刻を同じ状態に固定した試験ではなく、モデル姿勢を揃えて比較するための撮影方法である。
11. **WebGL2とソフトウェア描画**: Web起動には `--software-webgl` を使った。Godotの既定HTMLでは `#status` の消滅で起動を確認したが、それだけで画面が正常とはせず、実画像も確認した。低速環境ではフレーム落ちに備えてロジック更新を小刻みにし、検証では周回と結果の表示を見て進行を判断した。

次回へ最も再利用したいのは、音声を含む終了処理、全車種の連続撮影、実入力デモの達成判定、Web撮影の診断、証拠画像の更新の5点。今回のコードと実測をもとに、既存skillへ追加するか独立したskillにするかを検討できる状態になった。
