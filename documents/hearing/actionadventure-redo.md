# 「残り火の森」開発ヒアリング

対象は、このセッションで新規制作した `games/actionadventure/`。開始時には対象ディレクトリが存在しなかった。既存の `documents/knowledge/actionadventure.md` には過去版の記録があったが、その素材や実装を復元・流用した作業ではない。以下は今回実行した内容だけを記載する。

## 1. 開発の進め方

1. 作業ディレクトリ、Git の状態、Godot のバージョン、プロジェクト文書と適用規約を確認した。`game/actionadventure` ブランチは変更なし、ローカル Godot は 4.7 stable だった。
2. 「森で鍵を取得 → 北の祠の押し石 → 灯火を取得 → 東の庭の燭台二本を点灯 → 灯台の守護者 → エンディング」という短い冒険を設計した。五部屋を画面境界で行き来する構成にした。
3. サブエージェントへ画像と音源の生成を委譲し、本体では Godot プロジェクト、メインシーン、進行を保持する autoload、起動用 Makefile を作成した。アトラスのセル番号と用途を先に共有して、素材の完成を待たずに描画側を実装できるようにした。
4. 移動と壁の衝突、部屋移動、剣、回避、敵の追跡と攻撃予告、被弾・死亡、炎の飛び道具、鍵・押し石・燭台・勝利まで実装した。地図、一時停止、回復、敗北後の再開、タイトルと案内も加えた。
5. Godot へ読み込ませ、構文エラーを修正した。描画付きのキー入力・撮影スクリプトを作り、代表画面を目視した。境界条件の selfcheck は素材を終えたサブエージェントへ続けて委譲した。
6. 検証で見つかった封印の迂回経路、案内表示の重なり、撮影開始直後の入力の不安定さ、終了時の音声リソース残留に対応した。
7. 個別の状態検証だけでは実際に最後まで進める保証が弱いと考え、進行フラグ・敵の体力・主人公の位置を直接変更しない通しクリア検証を追加した。移動と戦闘によって初期状態からエンディングまで到達した。
8. 最終のログと画面を確認し、README、素材の出典、開発知見を記録した。差分と個人情報を点検してコミット・push、PR 作成、検証済み画像三枚の添付まで実施した。

詰まった点は、ゲームロジックだけでなく検証環境にもあった。特に、import の exit 0 を成功とみなさずログに現れた Parse Error を拾うこと、描画確認と headless の検証を分けること、サブエージェントの報告を実ログで確認することが必要だった。

## 2. 使ったツール・skill・コマンド

### ツール

- `functions.exec` と `exec_command`：シェル実行、ログ取得、独立した確認のまとめ実行。
- `apply_patch`：プロジェクト、ゲームコード、検証スクリプト、文書を作成・修正。
- `collaboration.spawn_agent`、`followup_task`、`send_message`：素材生成と、その後の selfcheck 実装を委譲。検証で見つかった接続の不具合も報告してもらった。
- `view_image`：Godot が描画して保存した PNG の目視確認。
- `write_stdin`：自分で起動したコマンドの終了結果を受領。

### 読んで使用した skill

- `commit-create-pr`：コミット前の機密情報点検、PR 本文、セッション再開欄、画像添付の手順に使用。プロジェクトで変更禁止の共有 CI・テンプレートは変更していない。
- `pr-attach-screenshots`：画像の機械検査、公開アップロード、公開 URL のハッシュ照合、PR 本文への埋め込みに使用。

Godot と UI 検証、素材ライセンス、Makefile、情報の一元化に関する規約ファイルも読んだ。`godot-development` は規約内の参照として現れたが、今回その SKILL.md を読んで手順を実行したわけではない。`imagegen`、Gemini、外部素材検索、webtunnel、ブラウザ操作、コードレビューの skill は使用していない。

## 3. 欲しかったが無かったツール・skill・スクリプト

いずれも今回使用した手順に組み込まれていなかったもの。環境全体に同等のツールが存在しないと調査・断定したわけではない。

- **Godot の検証を安全に終了する小さな共通スクリプト**：ウィンドウのフォーカス、入力の押下と解放、描画完了後の PNG 保存、シーン解放、終了コードを扱う部分を毎回書かずに済むとよい。ゲーム固有の画面構成や受け入れ条件まで固定する雛形にはしない。
- **部屋の接続と鍵による通行制限の検査**：座標上の隣接とは別に、実際の接続と解錠条件を検証する例が欲しかった。今回のような「目的地へ行けるが、解くべき仕掛けを迂回できる」不具合を検出する用途。
- **高速な通しプレイの検証例**：ケース別の状態設定と、進行を書き換えない実操作による検証を区別する手順。今回は経路探索と戦闘操作を自作した。
- **素材の機械検査**：アトラスのセルごとの非透明画素、寸法、再生成時の一致、音声の無音・クリッピング・ループ境界をまとめて検査するスクリプトがあれば、画像と WAV を作った後の手作業が減った。今回は画像寸法と WAV の形式・長さの確認までで、音声品質の網羅的な検査はしていない。

既存の `pr-attach-screenshots` は実際に手作業を減らした。アップロード後の公開 URL 確認や PR 本文の画像区間更新を今回独自に書く必要はなかった。

## 4. 素材の準備方法と使い勝手

### 画像

サブエージェントが `scripts/dev/generate_assets.gd` に画素の配列と色を定義し、Godot の `Image` で 256×16px の横並びアトラスを生成した。16×16px のセルに、地形、旅人、敵、宝箱、祠、石、スイッチ、花、灯火などを収めた。ゲーム側では通常2倍で描き、守護者などは別倍率にした。

利点は、外部素材の検索・ダウンロードや画像ライブラリ導入が不要で、コードから再生成できたこと。セル番号を先に決めると、画像生成とゲーム実装を並行できた。制約は、一枚の静止スプライトが中心で、歩行の方向別・複数フレームの表現までは作っていないこと。小さな上下動、剣の弧、回避の残像、粒子などをゲーム側で加えた。

### BGM・SE

同じ GDScript で正弦波などを合成し、`AudioStreamWAV.save_to_wav()` で書き出した。BGM は16秒、22050 Hz、16 bit、mono。SE は剣、被弾、取得・解錠の三種類。ゲームでは BGM の終了シグナルから再生を繰り返し、SE は複数の `AudioStreamPlayer` を使った。

利点は、画像と同じ制作経路で短時間に音源を用意でき、外部の録音・楽曲の権利確認が不要だったこと。音源の存在・形式・読み込み・音声出力の初期化は確認したが、人間の耳による聴感評価、ループの継ぎ目、長時間聴いたときの快適さは確認できていない。波形生成に成功したことと、音として心地よいことは別の評価になる。

### フォント

フォントファイルはダウンロードせず、Godot の `SystemFont` に Hiragino Sans、Noto Sans CJK JP、sans-serif を指定した。macOS の実描画では日本語が表示された。ファイルの同梱やライセンス全文の管理を省ける一方、別 OS で同じ字体や日本語表示になる保証は弱い。Windows・Linux の実行は未検証。

### 出典と比較の限界

画像・音声は今回用にコードで制作したオリジナルで、制作方法を `assets/CREDITS.md` に記録した。画像生成 AI サービス、CC0 配布サイト、有料素材、既存ゲーム由来の素材は使用していない。それらとの使い勝手の比較は今回の実体験としては述べられない。

## 5. 動作確認の方法

### 読み込みと境界条件

Godot の editor import でスクリプトと素材を読み込ませ、ログ全文の warning/error を確認した。`scripts/dev/selfcheck.gd` は実際のメインシーンを生成し、自動の物理更新を止め、条件を設定して67項目を検証した。剣の向き・距離・連射制限、被弾無敵、回避、死亡再開、討伐の保持、宝箱の条件、鍵、押し石、祭壇、重複点灯、勝利、全部屋の出口の移動と壁衝突などを含む。

### 通しクリア

`scripts/dev/playthrough.gd` は新規開始から、通れるマスの経路を探索して移動し、剣と灯火で敵を倒し、調べる操作で進めた。進行フラグ・敵の体力・プレイヤー位置は直接設定しない。論理時間を手動で進める高速な検証で、実時間のキー入力による人間のプレイを再現するものではないが、「個別の仕掛けは動くのに最初からはクリアできない」を確認するのに効いた。エンディング到達時の体力は6だった。

### 実入力と描画

`scripts/dev/verify.gd` を headless なしで実行し、`Input.parse_input_event()` からキー入力を送った。開始、移動、回避、東端の部屋移動、剣、地図と一時停止、押し石、灯火取得、燭台、死亡と再開、エンディングを確認した。後半は部屋や取得物のフィクスチャを使うため、このスクリプト単独を通しクリアの証拠にはしていない。

`RenderingServer.frame_post_draw` 後にビューポートを PNG に保存し、タイトル、岸、森、地図、祠、庭、守護者、再開、エンディングの九画面を確認した。森の宝箱案内と出口案内が重なっていた点は、テストの成功ログでは分からず、画像を見て修正できた。攻撃予告や剣の描画も保存画面で確認した。

### 結果と不足

- 最終の `make -C games/actionadventure test` は exit 0。67項目と通しクリアが成功し、ログ全文に warning/error なし。
- 最終の描画・入力検証は exit 0、失敗0件、ログ全文に warning/error なし。
- ログは `tmp/actionadventure-test.log`、`tmp/actionadventure-visual.log`、`tmp/selfcheck.log` に残した。
- 画面を見て操作する人間による難易度・操作感評価、音声の聴感評価、長時間プレイ、Windows・Linux、配布用エクスポートは未検証。動画は撮影していないため、動きの滑らかさや音と映像の同期を録画で評価してもいない。
- CI・コードレビューはプロジェクトの指示に従って実施していない。

## 6. Godot 固有のハマりどころと回避策

### エンジン既存メソッドと独自ヘルパーの名前衝突

独自の楕円描画ヘルパーを `draw_ellipse` と名付けたところ、Godot 4.7 の `CanvasItem` に同名メソッドがあり、シグネチャの不一致で Parse Error になった。`draw_shadow` に改名して解消した。以前の知識だけで「空いている名前」と判断せず、実エンジンのコンパイル結果を見る必要があった。

### import の exit 0 だけではスクリプトの成功を判定できない

上記の Parse Error と `Failed to load script` が出ていても、editor import 自体は exit 0 だった。ログ全文のエラー検査と、その後の実シーン生成で検証した。`make` の成功だけを根拠にしない点が重要だった。

### macOS のユーザーデータ保存先とサンドボックス

素材担当の実行で、通常の Godot 設定・ユーザーデータ保存先への書き込みがサンドボックスに拒まれた。設定保存の ERROR に加えて、プロジェクト指定後には signal 11 / exit 134 になった回もあった。対象を指定した通常の Godot 実行を必要な権限で行い、素材生成とゲーム検証を正常終了させた。ゲームコードの不具合と、保存先の権限問題を切り分ける必要があった。

### 高速な論理検証と実時間の音声処理

headless で論理時間を一気に進めると、音声再生の処理が残り、終了時に ObjectDB や resources still in use の警告・エラーが出た。検証側で音声を抑えたり解放時間を設ける試行を行った後、最終的には headless のときは BGM と SE を再生予約しないようにした。描画付きでは通常どおり音声を再生する。最終の両方の検証ログで warning/error が消えたことを確認した。

### シーン解放直後の終了

描画検証でシーンを解放してすぐ終了すると、リソースが残る回があった。`queue_free()`、検証側の参照解除、数フレームの処理を経て終了する形に変更した。途中のリーク件数を減らしただけで終えず、最終ログで解放を確認した。

### 起動直後の入力とウィンドウのフォーカス

描画検証の再実行で、D キーの移動量が不足した回があった。フォーカスの影響を疑い、`root.grab_focus()` と開始前のフレーム処理を追加し、移動を確認するフレーム数も増やした。最終実行は成功した。ただし原因をエンジン内部まで特定したわけではなく、検証開始の安定化による対処である。

### 部屋配置と通行可能な接続の混同

これは Godot のエンジン不具合ではなく、今回のゲーム実装上の落とし穴。地図の座標が隣り合う部屋を自動的に接続すると、祠から灯台へ直接行けて封印を迂回できた。`Journey.CONNECTIONS` を実際の接続の正とし、部屋移動と地図の両方がそれを参照する形へ修正した。selfcheck でも迂回経路が存在しないことを確認した。
