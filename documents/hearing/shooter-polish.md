# shooter 品質向上ラウンドの振り返り

対象は第2ラウンドの開発。第1ラウンドで存在していたゲームの進行・入力・当たり判定・検証コードを引き継ぎ、素材、アニメーション、演出、画面、音声と検証を更新した。以下は実際の作業、コード、実行ログと画像で確認した内容であり、第1ラウンドの実装を今回新しく作ったものとは扱わない。

成果物のPR:
https://github.com/bannzai/godotpractice/pull/28

## 1. 開発の進め方

### 作業の順序

1. 作業指示書、AGENTS.md、PROJECT.md、issue #5、既存の知見とヒアリングを読み、変更できる範囲と受け入れ条件を確認した。既存コードと変更前のスクリーンショットを確認し、約3分のゲーム進行を維持したまま表示と手触りを更新する方針にした。
2. 早い段階でdraft PRを作った。独自の軌道防衛メカという方向を決め、自機・敵3種・旗艦を色と形の両方で区別することにした。
3. 担当ファイルを分け、サブエージェントに画像と機体アニメーション、音声、戦闘演出を分担してもらった。親側は背景・HUD・Theme・画面構成、操作録画、統合検証、PRと証拠の整備を進めた。共有するmain.gdの変更は統合側で調整した。
4. 画像生成スクリプト、機体別スプライトシート、AnimatedSprite2Dの表示層を追加し、既存の位置・衝突計算へ接続した。続いて粒子・衝撃波・数字の表示、ヒットストップと揺れ、メニューの反応と遷移、多層背景、4場面の音声を組み込んだ。
5. headlessの検証を維持しながら、スクリーンショットと操作付き録画を拡張した。PNGを見てからフォント、ボムの線幅、表示の重なりなどを直し、連射中のボスの被弾姿勢は統合検証にも追加した。
6. 通常終了、フレーム数による終了、Movie Makerの終了を個別に調べ、音声の解放待ちを修正した。ローカルのテスト・撮影・録画・3OSとWebのエクスポート・通常起動を通した。
7. 作業ブランチをpushしてCIを確認し、webtunnelでWeb版を実操作した。Webで見つかったキー記号の文字化けを修正し、画像と録画を更新した。
8. putsで画像・録画をアップロードし、公開された内容をローカルと照合した。PRへ画像40枚と26秒のプレイ録画、検証結果、未検証の範囲を掲載した。最新コミットのCI全28ジョブと成果物を確認してready for reviewへ切り替え、知見を追記した。

### 詰まった点と解決

- **見た目の不具合はlintと起動成功では分からなかった。** フォントが細い、ボムの輪が太い帯になる、補給表示が重なる、タイトルの機体が重複する、といった問題を実描画のPNGで確認して修正した。
- **ボスが被弾姿勢のままになる問題があった。** 連射のたびに被弾時間を更新していたため、非ループの被弾アニメーションから戻れなかった。演出の再発火間隔を0.6秒、被弾姿勢の継続を0.22秒に分け、攻撃への復帰を検証した。
- **音声を止めるだけでは終了時のリークが消えなかった。** 通常実行とMovie Makerでは解放の進み方が異なった。通常終了には時間とフレームの待ちを入れ、Movie Makerには録画終了より前の音声停止を入れた。詳細はGodot固有の項目に記載した。
- **putsが既定の保存先設定を読むところで停止した。** プロセスのサンプルでSwiftDataの既定ストア読み取りに留まっていることを確認した。既存のR2用環境変数をputsの環境変数へプロセス内で渡す一時スクリプトを作り、putsによるアップロードを完了した。新しい認証情報は発行していない。
- **Webの実操作では撮影時刻にも注意が必要だった。** 射撃開始後に待ちすぎると、戦闘画面を撮るつもりでも既にゲームオーバーになっていた。画像の中身を確認し、開始直後の戦闘、ボム使用後のポーズ、結果をそれぞれ撮り直した。
- **変更していない別ゲームのCIが一度失敗した。** crewrtsのログとartifactを確認すると、描画後の終了時リークだった。そのゲームのコードは変更せず、失敗ジョブだけを再実行して成功を確認した。最後の知見追記コミットでも全28ジョブが成功した。

## 4. 素材の準備方法と使い勝手

### 画像

Python標準ライブラリの `scripts/dev/generate_art.py` で独自SVGを28枚生成した。外部の画像生成API、既存作品の素材、フリー素材サイトからの新規画像取得は使っていない。

- 自機・直進機・狙撃機・編隊機・旗艦に別々の形と装備を与えた。青緑、朱色、金色、紫色などの配色に加え、翼・砲塔・コアの配置を変えた。
- 1機種につき4列×5行のシートを用意した。通常機のセルは128×128、旗艦は256×160。待機・移動・攻撃・被弾・撃破を各4フレームにした。
- 弾、強化・ボム・得点のアイテム、背景の各層、タイトルのキーアート、パネルとHUDの部品も別ファイルにした。
- 固定シードと生成元を残したため、輪郭や色を変えても同じ構成を再生成しやすかった。機体間とフレーム間で絵柄を揃えやすく、セル寸法もコードから検査できた。
- 一方、手描きの質感や大きなポーズ変化には今回踏み込めていない。部品を動かす4フレームの表現なので、画像枚数が増えただけで豊かな動きになるわけではなく、状態の切替と演出を組み合わせる必要があった。

### BGM・SE

既存の音声生成スクリプトを拡張し、Pythonの波形合成と固定譜面で制作した。タイトル・ステージ・旗艦・結果のBGMをOGG、射撃・爆発・アイテム・ボムのSEをWAVとして用意した。BGMはffmpegでVorbisへ変換した。

持続音、FMのベル音、矩形波、倍音を重ねた低音、打楽器、ステレオの遅延を組み合わせた。タイトル84 BPM、ステージ132 BPM、旗艦156 BPM、結果100 BPMと、場面でテンポと譜面も変えた。音源サンプルや外部の音楽生成サービスは使っていない。

再生成2回で8ファイルのSHA-256が一致した。デコード成功、最大ピーク0.7869、BGMの先頭と末尾の差が最大0.007464であることを数値として確認した。生成元から音量や音色を調整しやすく、ファイルの再現性も確保できた。

ただし、数値が良いことと聴感上の完成度は別だった。実際に聴取する手段がなく、BGMとSEが重なる場面のバランスや、ループ境界が耳で気にならないかは未検証。場面別の曲が存在し、ゲーム側が切り替えることまでを検証済みとして扱った。

### フォントとクレジット

第1ラウンドから同梱されていたNoto Sans JPとOFL全文を引き続き使用した。今回新しくフォントをダウンロードしたわけではない。素材元はGoogle Fonts、ライセンスはSIL Open Font License 1.1としてCREDITS.mdに記録されている。

https://fonts.google.com/specimen/Noto+Sans+JP

日本語を含むUIの統一に使いやすかったが、同梱だけでは可変軸の指定や特殊記号の表示までは保証されなかった。Themeの太さ設定を修正し、Webで欠けた改行キー記号は `Enter` 表記に置き換えた。

独自画像・音声は本プロジェクト向けの新規制作物として、生成元と方針を `games/shooter/assets/CREDITS.md` に記録した。独自生成物を外部CC0素材として扱うことはしていない。外部画像生成APIや素材サイトは今回使用していないため、その使い勝手の比較評価はできない。

## 5. 動作確認の方法、効いた点と足りなかった点

### headlessのselfcheckと統合検証

`make test GAMES=shooter` でlint、起動、selfcheck、integration_check、終了検証を実行した。既存の操作・当たり判定・出現と進行の検査に加え、機体5種の5状態・各4枚、AtlasTextureの寸法と領域の非重複、再初期化、SpriteFramesの共有、連射中のボスの姿勢復帰、4場面のBGM切替を検証した。

全ステージの統合検証はゲーム時間165.87秒でクリアした。これは既存の検証用の無敵と3連射の条件を使った進行確認であり、人間が通常難易度で通して遊んだ結果ではない。保存先も検証用に分け、通常プレイの記録を変更しないようにした。

ロジックの維持、素材の参照やフレーム構成、終了時の解放を短時間で反復するのに効いた。一方、フォントの細さ、線幅、重なり、絵の印象はheadlessでは確認できなかった。

### screenshot.gdとアニメーションの確認

`make screenshot GAMES=shooter` で32枚を生成した。内訳はタイトル・戦闘・結果など12枚、機体別のアニメーション一覧5枚、5種類の演出を3時点ずつ撮った15枚。

機体別の一覧では、待機・移動・攻撃・被弾・撃破の各行に開始・途中・終了を並べた。セルのはみ出し、状態ごとの違い、分解後の見え方を目視した。ボム・被弾・強化・補給・旗艦撃破も発生直後から時間を進めて撮り、粒子と衝撃波、文字の残り方を確認した。

これは状態ごとの絵を比較するのに有効だった。ただし、撮影用に状態を準備するため、通常操作からその状態へ到達できることを証明するものではない。静止画だけでは再生速度や状態遷移も確認しきれないため、統合検証と操作録画を組み合わせた。

### 起動movieと操作付きmovie-play

`make movie GAMES=shooter` は操作なしの5秒録画。起動直後に黒画面や描画崩れがないことと、録画終了時のリークがないことを確認した。

別の `movie-play` では `demo.gd` から実InputEventを時刻ごとに投入した。タイトルから出撃し、終盤の経過時間140秒・3連射を初期条件として、移動、連射、ポーズと再開、ボム、旗艦の撃破、結果表示を26.27秒・30fpsで記録した。旗艦への照準合わせも左右キーの押下・解放で行い、結果を直接クリアへ変更する処理は使っていない。

mp4を2秒間隔の13枚と末尾へ分割して目視した。戦闘から旗艦の段階変化、撃破、結果への遷移が終了することを確認できた。短い録画に全3分を収める方法ではないため、ステージ全体は別の統合検証で補った。

2秒間隔の画像だけでは、その間の短いちらつきや全フレームの滑らかさを網羅できない。Movie Makerの固定fps録画は、実時間での処理落ちを測る性能検証でもない。この限界を残したまま「全環境で滑らか」とは判断していない。

### CI artifact

最新コミット `8a836c0` のCI全28ジョブが成功した。`gh run download` で `shooter-screenshot-and-movie` を取得し、PNG 32枚とmp4から取り出した末尾を目視した。Linuxの仮想描画でも日本語、機体、HUD、演出が表示されることを確認できた。

CIのログも全文を検査した。Linux仮想描画のV-Sync非対応警告は既存Makefileの限定的な除外対象だったが、shooterのスクリプトエラーとObjectDB／音声リソースの終了時リークは無かった。

https://github.com/bannzai/godotpractice/actions/runs/34026249643

### webtunnel

自分のブランチを `--software-webgl` 付きで起動し、専用のagent-browserセッションで操作した。タイトルから出撃、連射、移動、ボム、ポーズと再開、22秒でのゲームオーバー、結果ボタンからタイトル帰還を確認し、5枚を撮影した。ゲーム状態をJavaScriptから直接書き換える操作は使っていない。終了後はブラウザを閉じて `down` し、録画artifactも取得した。

Web固有のフォント差を実際に発見できた点が大きかった。Godotの起動表示が消えたことと画面の中身を確認してから操作する必要があり、時間待ちだけでは撮影した状態を保証できなかった。

Web実操作は、Windows／Linux実機でのプレイ、物理ゲームパッド、デスクトップの全画面切替の代替ではない。今回の3OS確認はエクスポート成功までで、物理ゲームパッドの接続と他OS実機のプレイは再検証していない。

### 証拠の掲載

putsでアップロードしたファイルを公開URLから取得し、SHA-256でローカルと一致することを確認した。Pythonの標準HTTPクライアントでは403となった取得があり、curlでブラウザのUser-Agentを指定すると取得できた。PR本文へ画像40枚とプレイ録画を掲載し、古い「作業中」の記述が残っていないことも確認した。

## 6. Godot固有のハマりどころと回避策

### 音声の停止と終了方法の違い

`AudioStreamPlayer.stop()` と `stream = null` の直後にも、AudioServer側に再生参照が残っていた。通常closeでは停止後に時間とフレームを待った。`--quit` / `--quit-after` による終了時は、`_exit_tree` 内で短い同期待ちを入れた。待ちはゲーム進行中ではなく終了処理に限定した。

Movie Makerでは音声の処理が録画フレームに同期するため、終了時に実時間だけ待っても解放が進まなかった。Makefileから終了フレーム数を独自の `--capture-frames` 引数で渡し、最後の12フレーム前から音声を停止する方式で解決した。30fps録画の末尾0.4秒は音声解放の区間になる。

また、今回使用したGodotでは `--quit` / `--quit-after` が処理後に通常の引数一覧から取り除かれ、`OS.get_cmdline_args()` から終了予定を得る初案は機能しなかった。`--` 以降のuser argsで必要な値を別に渡した。

### 非ループの被弾アニメーションと連続命中

同じ被弾状態を維持し、毎弾タイマーだけを延ばすと、非ループアニメーションが終端に到達したまま戻らなくなる。被弾姿勢の継続時間と再発火可能になるまでの時間を別々にした。被弾中に発砲した場合も、復帰後に攻撃姿勢が表示されるようにした。

機体ごとのSpriteFramesとAtlasTextureは共有し、同じ機種でsetupを繰り返しても再生成しない構成にした。共有するのは資源で、現在の姿勢やフレームは各AnimatedSprite2Dが持つ。

### Line2DをTweenで拡大すると線幅も太くなる

衝撃波のscaleを大きくするだけでは線幅も拡大され、ボムが帯のようになった。scaleの変化と同時にwidthを逆数で調整し、見た目の線幅を約2.5pxに保った。数式だけで完了とせず、演出の途中のPNGで確認した。

### FontVariationの軸指定とWebの文字

Themeの `variation_opentype` に文字列の `wght` を置いた初版は意図した太さにならなかった。整数のOpenTypeタグ `2003265652` をキーにして太さを指定し、PNGを確認して調整した。

さらに、macOSで表示できた改行キー記号がWebでは四角になった。フォントの同梱で済んだと判断せず、Webの実描画を確認し、出撃ボタンの説明を `Enter / A` に変更した。

### 描画順、揺れ、演出の寿命

背景、機体、演出、HUDの描画順を分けた。戦場だけを揺らし、HUDを固定したことで、被弾時も残機やスコアを読みやすくした。粒子と数字を戦場でクリップし、撃破した機体の残像は論理上の敵が消えた後も演出として残す必要があった。結果メニューも撃破直後に全てを覆わず、演出の後からフェードで表示した。

### SceneTreeの検証、autoload、描画の待機

第1ラウンドで得られていた「autoload参照シーンを検証スクリプトのconst preloadで先に読み込まない」という方針を引き継いだ。新しい検証スクリプトでも `call_deferred` 後にmain.tscnをloadし、実ツリーへ追加した。これは今回新しく発見した問題ではなく、既存知見を再利用した点。

スクリーンショットはprocess_frameと描画完了を待ってからViewportの画像を保存した。ゲームの論理時間を速く進める統合検証と、粒子・Tween・音声・描画が進む実フレームは同じではないため、待ちを省くと検証したい状態にならない。状態の準備、描画待ち、終了待ちを分ける必要があった。

### ログと一時ファイルの配置

制限された実行環境では、Godotの標準ログやエディタ設定の保存先への書き込みが問題になった。ログはゲーム内tmpの絶対パスを `--log-file` で渡し、必要なGodot実行は通常権限で行った。ログ先の変更だけで、エディタ設定の保存まで全て解決するわけではなかった。

tmpに `.gdignore` を置き、撮影した大量のPNGを次回のimportでゲームのアセットとして再取り込みしないようにした。また、既存の `screenshot-alert.png` という名前を維持した。`warning` を含む成功時のファイル名でも、ログのWARNING全文検索に一致するという第1ラウンドの知見を引き継いだ。

### Webの起動と座標

runnerのChromiumでは `--software-webgl` を使ってGodotのWebエクスポートを描画した。Tailscaleの確認コマンドは制限された実行環境内で異常終了したが、通常権限で接続状態を読むとREADYになった。失敗表示だけで接続不可とは決めず、実際の状態とブラウザ画像を確認した。

1280×720のゲームが1280×656の表示領域へ収まるため、左右の余白と縮尺を考慮してマウス座標を決めた。Web版で確認できたことと、デスクトップ固有の機能を分けて報告した。
