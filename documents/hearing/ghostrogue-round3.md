# ghostrogue 開発ヒアリング

対象はホラーローグライク「夜を継ぐ者」。実際のコード、実行ログ、素材クレジット、開発中の確認結果をもとに振り返る。今回のヒアリングはこのファイルだけに記録し、コミットしない。

開発成果のPR:
https://github.com/bannzai/godotpractice/pull/62

## 1. 開発の進め方

1. 作業指示書、issue #61、発案のIdeaMemo、プロジェクトの制約を読んだ。近いジャンルのdeckrogueとmonsterquestについて、実装・検証スクリプト・知見・品質向上時のヒアリングを参照した。
2. タイトル→プレイ→結果→タイトルの最小ループと検証入口を先に作り、コミットしてdraft PRを出した。
3. ロジック、素材・音・演出、操作検証をサブエージェントへ分担し、親は画面と統合を担当した。担当ファイルを分け、霊の識別子・イベント・表示更新の接点を調整した。
4. 12層の分岐、12種の霊、速さ順の属性戦闘、永久ロスト、闇堕ち、警察、6つの会話、5つの結末、保存再開を埋めた。霊と技の定義を図鑑と共有し、進行はGameStateへ集約した。
5. キャラ画像と5動作、多層背景、照明、BGM・SE、獲得・被弾・霧散、画面遷移、ボタンの反応を統合した。撮影で見つかった文字の折り返し、タイトルの見づらさ、戦闘中のHP表示を修正した。
6. ローカル検証、録画、各OSへのエクスポート、CI artifactの目視、webtunnelの実操作を実施した。証拠87枚をPRに掲載し、最終CI成功後にready for reviewへ切り替えた。

一番詰まった統合箇所は、前衛が倒れて控えが昇格する途中の表示だった。戦闘後の配列だけから画面を作ると、消えた霊と昇格した霊の表示位置・HPが食い違う。行動イベントに霊の識別子と昇格時の状態を含め、演出中も同じ個体を追跡するようにした。

環境面ではGodotの設定保存、描画時のLaunchServices接続、putsのKeychainアクセスに詰まった。作業内のGodot環境と絶対パスのログを使い、必要な処理だけ追加権限で実行した。画像送信の自動承認が拒否された際は、元の作業指示の明示許可、目視済み画像、設定済み送信先を確認して再申請した。

反省点は、最小ループの後の実装コミットが大きくなったことと、最後のHUD修正で撮影・エクスポートをやり直したこと。機能単位で統合する区切りと、撮影前に画面変更を止める区切りを早めに置くと、確認の重複を減らせた。

主に実行した入口は `make test GAMES=ghostrogue`、`make screenshot GAMES=ghostrogue`、`make movie GAMES=ghostrogue`、`make build-all GAMES=ghostrogue`、`make build-web GAMES=ghostrogue`。プレイ録画は `make -C games/ghostrogue movie-play`。起動入口は `make ghostrogue-run` に `RUN_FLAGS='--quit-after 90'` を渡して検証した。通常終了は別の終了検証スクリプトでも確認した。

commit・push前には電話番号検査スクリプトも使用した。SVG座標の一部が誤検出されたため、該当行の現物を確認して判断した。

## 3. 欲しかったが無かったツール・skill・スクリプト

既存skillで個々の作業はできたが、今回の一連の作業をまとめる仕組みは足りなかった。

- **検証証拠の一覧管理**: コミット、撮影条件、画像、目視結果、公開URLを対応させ、変更後に撮り直す画像を抽出する仕組み。今回は一覧画像作成、アップロード記録、PR本文生成を一時Pythonスクリプトで補った。
- **Godot内での素材プレビュー**: 画像生成直後にGodotへインポートし、本体・可動部・背景を一覧化する仕組み。SVGの外部プレビューと実ゲームの差を早く見つけたかった。
- **全キャラの動作比較の雛形**: キャラ一覧を渡すだけで、全動作の開始・途中・終了と演出途中を撮れるスクリプト。今回のscreenshot.gdを再利用候補にできる。
- **Canvasゲームのブラウザ操作補助**: ゲーム解像度とcanvasの実寸からクリック座標を変換し、入力・撮影を記録する仕組み。今回は専用の一時スクリプトを作った。
- **保存再開・永久ロスト・終了処理の検証雛形**: 乱数の続き、控え昇格、BGM・SE再生中の通常終了とquit-afterをまとめて検査するもの。

共有CIではゲーム固有の知見文書だけの変更でも全ゲームが対象になった。対象ゲームを絞る提案は知見へ記録し、共有設定の変更は行わなかった。

## 4. 素材の準備方法と使い勝手

**画像**はPythonで独自SVGを生成した。霊12種、主人公の闇4段階、警官、ボスの計18体を固有の輪郭にし、本体と武器・翼・尾などの可動部を分離した。背景・ロゴ・キーアート・アイコンを含め76SVGを用意し、再生成一致を検査した。

この方法は、同じ色・線・寸法で大量の差分を揃え、後から部位や装飾を修正しやすかった。一方、版画調の表現を超える細かな絵作りには限界があり、構図と読みやすさはゲーム画面を見ながら調整する必要があった。外部レンダラで見えていた衣服のSVG patternがGodotでは消えたため、明示的なpathに展開して直した。

**BGM・SE**はPythonのPCM合成で独自生成した。鈴の非整数倍音、撥弦、息のノイズ、太鼓の減衰を組み合わせ、タイトル・地図・戦闘・警察・ボス・結果の6曲とSE11種を作った。22,050Hz・16bit・ステレオで、全17ファイルの再生成一致、ピーク0.72、クリッピング0、BGMのループ境界を検査した。場面別の音を揃えやすく、数値で再現性を確かめられた。ただし、聴感や長時間聴いた際の疲れ、音量バランスの評価は未実施であり、数値検査だけで音楽の品質が確定したとは扱っていない。

**フォント**は既存deckrogueに導入済みのZen Old Mincho Regularを、OFL全文とともに再利用した。和風の画面と合わせやすく、日本語本文とロゴの統一に役立った。長文の折り返しは実寸での確認が必要だった。

フォントの素材源:
https://github.com/googlefonts/zen-oldmincho

画像生成APIや外部の画像・音声素材集は今回利用していないため、それらとの使い勝手の比較は未評価。実際に使用した生成方法と帰属はassets/CREDITS.mdへ記録した。

## 5. 動作確認の方法と不足した点

| 方法 | 使い方と効いた点 | 限界・不足 |
|---|---|---|
| headless selfcheck | 64シードの道、属性9通り、技・図鑑、闇の境界、警察、永久ロスト、結末、保存再開・破損データを検査 | 文字の欠け、素材の描画、音の聴感は判定できない |
| integration.gd | ボタン・キー・ゲームパッドのInputEventを使い72項目を検査。編成、技、保存再開、自然な闇堕ちを確認 | 物理ゲームパッドの接続は未検証 |
| screenshot.gd | 各画面・全キャラ・演出の62PNG、643項目を確認。日本語説明文のはみ出しやHP表示の問題を発見 | 固定状態で撮る画面もあるため、通常プレイでの到達証明には別の検証が必要 |
| movie | 5秒・30fpsで起動を記録し、開始・途中・末尾を目視 | 起動だけでは進行や選択の不具合を拾えない |
| movie-play | 通常の初期状態から実入力だけで30秒・900フレーム。2秒間隔15枚と末尾を確認 | 全分岐を一本の録画では覆えない。短い演出は連続フレーム撮影で補った |
| CI artifact | 最終CI31ジョブ成功。Linuxの62PNGと動画0・2・4秒・末尾を取得して目視 | 同じコードでもPNGのSHA256は62枚とも相違した。画素差もあり、ハッシュ一致だけで描画の成否は判定できなかった |
| webtunnel | Chromiumでシード20260907を入力し、墓・依代・警察・物語を選んで7辻・8霊・闇100の結果とタイトル帰還を確認。9画面を撮影 | Web版の確認であり、デスクトップ固有の操作は別途確認が必要 |

アニメーションは18体それぞれについて、待機・移動・攻撃・被弾・霧散の5動作を開始・途中・終了の同じ条件で並べて目視した。色の変化だけでなく、武器・翼・尾の動き、攻撃姿勢、霧散後に姿が残らないことを確認した。戦闘の被弾・HP減少・控え昇格は操作検証と演出途中の画面で補った。

movie-playは684フレーム目で結果、767フレーム目でタイトルへ戻った。Web実操作も同じ結末まで進め、ブラウザのエラー一覧は空だった。検証後にwebtunnelをdownし、録画artifactも取得した。

画面62枚、プレイ録画16枚、Web9枚の計87PNGをputsで公開しPRへ掲載した。ローカルとCIの終了ログを全文確認した。CIではllvmpipeのV-Sync変更非対応という既知警告だけを区別し、それ以外のWARNING/ERRORと終了時リークがないことを確認した。

## 6. Godot固有のハマりどころと回避策

- **64bit乱数stateとJSON**: 数値として保存すると精度を失うため文字列化した。画面の再開だけでなく、その後の抽選も一致することを検証した。
- **音声停止と終了の時間差**: stop後にstream参照を外し、音声スレッドに停止が反映される時間を確保した。通常終了ではツリーを保持して待ち、quit-afterの終了通知ではawaitで延命できないため同期的な待ちを設けた。headlessでは音声再生を抑止し、描画環境でもBGM・SE再生中の終了を検査した。
- **SVGインポートの差**: 外部で表示できるpatternがGodotでも表示できるとは限らなかった。pathへ展開し、Godotがインポートした実画像で確認した。
- **UI更新と演出中の状態**: 前衛配列の添字だけで個体を追うと永久ロスト・昇格で崩れる。識別子とイベント時点の状態を持たせた。遅延フォーカス処理も、対象ノードの有効性とツリー所属を確認してから行った。
- **日本語の長いButton文言**: 見出しと補足を別Labelに分けて折り返しと高さを指定した。戦闘の技名・コスト・ヘッダ補足は1280×720の撮影で調整した。
- **ログ・保存・再インポート**: ログは作業内の絶対パスへ出し、一時出力とビルド成果物に.gdignoreを置いた。テスト用の保存先は実プレイのuser://から分けた。
- **macOSの隔離環境**: インポートが外部の設定へ書き込もうとする問題には作業内のGodot環境を使った。描画時のLaunchServices接続は必要な追加権限で解決し、システム設定は変更しなかった。
- **Webの起動と座標**: software-webglを指定し、HTMLのstatus要素が消えてから操作した。実際のcanvasは1279×656だったため、1280×720のゲーム座標を縮小し、中央寄せの余白を加えてクリック位置を求めた。

Godot以外では、putsがカレントディレクトリにdefault.profrawを生成した。LLVMプロファイルを調べてputs由来と確認し、その後は作業内の一時ディレクトリから実行した。検証用の生成物をソース差分へ混ぜないためにも、ツールごとの出力先確認が有効だった。
