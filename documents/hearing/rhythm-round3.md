# rhythm 開発の振り返り

対象は issue #43 の「星灯りのリズム便」。Godot 4.7 / GDScript / GL Compatibility で、3曲×2難易度の2Dリズムゲームを実装した。

PR: https://github.com/bannzai/godotpractice/pull/51

## 1. 開発の進め方

最初に作業指示書、AGENTS.md、PROJECT.md、issue の受け入れ条件を読み、既存ゲームの実装・検証用スクリプト・知見を確認した。特に shooter の実装と品質向上時のヒアリングを参考にした。ゲーム本体は `games/rhythm/`、継続して残す知見は `documents/knowledge/rhythm.md` に閉じた。

まずタイトル→演奏→結果の最小ループを作り、早い段階で draft PR を出した。その後、素材、判定・保存ロジック、検証を担当ファイルごとにサブエージェントへ分担し、自分は画面・入力・音声と各担当の統合を進めた。最初から完成した絵を待つ必要がなく、画面遷移とデータの接続を先に確かめられた。

中核は、進行・選曲・記録を持つ `RhythmState` と、判定計算・保存値の解釈を扱う `rhythm_rules.gd` に分けた。3曲と6譜面、2レーン、長押し、Perfect/Good/Miss、スコア・コンボ・精度・ゲージ、成功/失敗、記録保存を順次接続した。選曲・試聴・補正設定・中断と、キーボード・パッド・マウス・タッチの操作も追加した。

見た目は「夜の街へ音楽を届ける3人の動物奏者」に揃えた。固有画像、状態別スプライトシート、拍に同期する踊り、判定演出、多層背景、Theme、シェーダ、場面別音声を重ねた。音声を止めるヒットストップは使わず、奏者の姿勢を短時間止めて命中の反応を出した。

統合検証では、次の問題を見つけて修正した。

- パッドBをノーツ入力に使うと既定のキャンセル操作と競合したため、キャンセルをEscape/Startに変更した。
- 長押しの解放を広く拾う修正で、中断ボタンがマウスの解放を受け取れなくなった。ゲームが追跡している解放だけを消費するようにした。
- 高スコアの失敗記録で過去のクリア経験を消さないよう、最高スコアとクリア経験の更新を分けた。
- 長押しの終端と未入力ノーツのMiss期限を期限順に処理し、細かく時間を進めた場合とフレームが飛んだ場合でコンボ・ゲージが変わらないようにした。

最後にローカル検証、各OSとWebのエクスポート、CI、Web実操作、証拠のアップロードを揃えた。最終コミットは `be88c75`、最新CIは31ジョブすべて成功。PRをready for reviewにし、マージは行っていない。

時間がかかったのは、実装そのものに加えて、macOSのsandbox下でのGodot起動と、Webの画面取得・証拠整理だった。前者は作業領域内のself-contained Godotとログ保存先の明示で対応した。Webでは撮影タイムアウトを描画失敗と決めつけず、接続確認と実画面の取得を分けた。途中で自動承認レビューが利用上限により失敗した区間は完了扱いにせず、ユーザーの再開指示後に残りを完了した。

## 2. 使ったツール・skill・コマンド

skillは、内容を読んで作業に適用したものと、そのskillが案内する実行ツールを区別して記す。

| ツール・skill | 実際の用途 |

| game-asset-search | 素材の生成・ライセンス確認・CREDITSへの記録方針を適用。外部画像や楽曲の検索・採用は行わず、独自生成を選んだ |

実行した主な検証コマンドは以下。ローカルでは必要に応じて `GODOT` に作業領域内の同じ4.7の実行ファイルを指定した。

```bash
make test GAMES=rhythm
make screenshot GAMES=rhythm
make movie GAMES=rhythm
make build-all GAMES=rhythm
make build-web GAMES=rhythm
make rhythm-run RUN_ARGS='--script res://scripts/dev/run_check.gd'
```

`games/rhythm/` 内では `make movie-play` を実行した。素材生成には `scripts/dev/generate_assets.py` と、その画像だけを生成する `--images-only` を使った。commit前・push前には電話番号差分検査スクリプトも実行した。

Webでは `webtunnel-cli.sh up rhythm --software-webgl --ref game/rhythm --wait`、`agent-browser --session rhythm --cdp ...` を使い、終了時にブラウザ接続を閉じて `webtunnel-cli.sh down rhythm` を実行した。撮影が停滞した際は、curlによるCDP接続確認、Node.jsによるCDPの応答確認と撮影の試行、webtunnel標準プレビューのフレーム取得も行った。直接CDPでの撮影試行はタイムアウトし、最終的な証拠は再開後のagent-browser撮影で揃えた。

## 3. 欲しかったが無かったツール・skill・スクリプト

既存の共通入口は役立ったが、この作業でそのまま使える形が無く、都度組み立てたものがある。

- **リズムゲームの音声同期検証例**。音声時計、ミックス経過、出力遅延、補正値、譜面時刻、判定線からの距離を一度に記録し、実入力で判定まで確認する例が欲しかった。今回の `integration.gd` をgodot-developmentへ一般化すると、フレーム時間だけで同期を検証してしまう失敗を減らせる。
- **複数入力源の長押し検証例**。キーとマウスの同時保持、最後の入力源の解放、領域外での解放、GUIボタンの解放を奪わないことまで含む例があれば、入力統合の試行錯誤が減った。
- **キャラ別・状態別のアニメーション撮影入口**。キャラと状態の一覧を渡すと開始・途中・終了を撮り、ラベル付き一覧にする仕組みが欲しかった。今回は `screenshot.gd` のギャラリーと一時スクリプトを作った。
- **証拠をPRへ掲載する一連の処理**。ローカル画像、録画フレーム、Web画像、CI artifactの対応を管理し、変更のあった画像だけをputsへ送り、本文を更新して公開URLの内容まで検査する処理が欲しかった。今回は一時スクリプトとSHA-256の記録で対応した。
- **sandbox対応のGodot実行準備**。実行ファイル、設定、ログ、userデータを作業領域内へ収め、描画・音声に必要な権限を切り分ける準備がまとまっていると起動確認が速くなる。
- **生成する素材の種類を選べる入口**。画像修正で3曲分の音声まで再生成するのは重いため、今回 `--images-only` を追加した。画像・音声・譜面を分けて再生成する例はgame-asset-searchでも再利用できる。

CIについては、知見文書だけの最終更新でも複数ゲームを再検証した。当時の変更検出を `documents/knowledge/<slug>.md` と対象ゲームに対応付ける提案を知見へ残し、共有CI自体は変更しなかった。

これらは今回の不足と改善候補であり、同名・同機能のツールが現在もどこにも存在しないという意味ではない。

## 4. 素材の準備方法と使い勝手

### 画像

PythonでSVGを生成した。キツネのドラマー、トリの鍵盤奏者、ウサギのベーシストを、輪郭・顔・耳や羽・衣装・楽器で描き分けた。各キャラの独立画像に加え、1キャラ1枚のスプライトシートを用意した。シートは待機・踊り・成功・ミス・祝福の5状態×4フレームで、腕、楽器、耳、表情も変化させた。

背景は空・街・手前の電飾の3層、UIはロゴ・ノーツ・星・月などを別ファイルにした。色だけに頼らず、丸・ひし形・矢印でもノーツを区別した。

手続きSVGは、色や形の修正を全フレームに反映しやすく、別キャラ間のサイズや画風を揃えやすかった。ソースコードから再生成できることも利点だった。一方、絵筆の質感や自然な体のひねりには向かず、図案的な表現になる。今回はその性質に合う平面的な画風を選んだ。image_genやGeminiによる画像生成は使っていないため、それらとの実測比較はしていない。

### BGM・SE

Python標準ライブラリで波形を合成し、WAVを書き出してffmpegでOGGへ変換した。単一の正弦波だけで済ませず、倍音、ノイズ、音量の立ち上がりと減衰を組み合わせ、ドラム・ベース・和音・旋律を重ねた。

演奏曲は112 BPM・72秒、128 BPM・75秒、144 BPM・70秒の3曲。中盤の変化と後半の盛り上がりを配置し、タイトル・選曲・成功・失敗の音源と、ノーツ別命中・長押し・満タン・ミスのSEも生成した。音源の第0拍と譜面の基準時刻を揃えられるため、リズムゲームの譜面作成には扱いやすかった。

生成は再現可能で外部サンプルの権利確認も不要だったが、画像より処理が重く、音楽的な自然さや音色の好みをコードと自動検証だけで評価するには限界がある。演奏・音声時計の動作は検証したが、人間による聴感評価や端末間の音質比較を済ませたとは扱っていない。

### フォント・素材源

M PLUS Rounded 1c Regularを既存ゲームから無改変で複製し、OFL全文と作者情報を同梱した。日本語を含む見た目を既存資産で揃えられ、新たなフォント探しが不要だった。

公式の素材源は以下で、実際のこの作業での取得経路は既存ゲームからの複製だった。

https://fonts.google.com/specimen/M+PLUS+Rounded+1c

https://github.com/google/fonts/tree/main/ofl/mplusrounded1c

画像・BGM・SEは独自生成で、外部のフリー画像・楽曲・音声サンプルは採用していない。したがって外部素材サイトの検索性や、ダウンロード素材を加工する手間の比較はしていない。生成物を根拠なくCC0とはせず、外部素材未使用の独自生成物として `assets/CREDITS.md` に作り方を記録した。

## 5. 動作確認の方法

指定されたheadless検証、スクリーンショット、起動録画、実入力のプレイ録画、CI artifact、webtunnelをすべて使った。

| 方法 | 実施内容と効いた点 | 足りない点・注意点 |
| --- | --- | --- |
| headlessのselfcheck | 譜面の時刻・範囲、判定境界、スコア、状態遷移、保存値、クリア経験の保持、時刻飛びを検証。細かな回帰を短時間で検出できた | 実際の描画崩れや音の聞こえ方は分からない |
| 実InputEventのintegration | 全6譜面のPerfect完走が100万点になること、Good/Miss、長押し・途中解放・複数入力源、GUI操作、中断、再演奏、保存、音声時計を確認。純粋関数の検証では拾えないGUIとの競合が見つかった | パッドイベントの投入は物理パッドの接続検証ではない。制御した時計での譜面完走も、曲を実時間で聴き通す検証とは異なる |
| screenshot.gd | 17枚の代表画面、各キャラの状態別連続フレーム、命中・ミス演出の開始・途中・終了、長押し、満タン、成功/失敗を撮影して目視 | 静止画だけでは実時間の滑らかさや操作の気持ちよさを断定できない |
| movie | 5秒の起動録画を作り、起動からタイトルまでと末尾の描画を確認 | 操作のない録画なので、プレイの成立は別に確認する必要がある |
| movie-play | 26.03秒の実キー入力シナリオ。2秒間隔の一覧と末尾を目視し、通常ノーツ、長押し、判定演出、結果への遷移を確認 | 最初の約20秒は等速だが、その後は音声と時計を終盤へseekしている。省略表示を映像に入れ、省略したノーツは通常のMissとして処理した。全曲の等速完走動画ではない |
| CI artifact | 最新CI `34047329534` の31ジョブ成功後、`rhythm-screenshot-and-movie` のPNG17枚と動画末尾を再目視。前のCIでは動画の1秒間隔の一覧も確認した | Linuxの描画確認であり、全デスクトップ実機の操作確認にはならない |
| webtunnel | 自分のブランチをChromiumで開き、キー入力でタイトル→選曲→演奏→72秒の曲終了による失敗結果→選曲と記録表示まで確認。5画面を撮影した | Webでの成功演奏を確認したものではない。成功はローカル検証で確認。Web操作だけではデスクトップ固有の全画面・物理パッド・音響遅延は確認できない |
| ローカルの描画付き起動 | make rhythm-runから実行し、専用シナリオでF11往復と終了通知を送り、全画面・ウィンドウ画面を目視 | Windows/Linux実機での操作は未検証 |

アニメーションは、状態ごとに開始・途中・終了を同じ画像へ並べたことで、キャラの部位や表情が変わるかを比較しやすかった。ループの「終了」をちょうど周期末にすると先頭フレームへ戻るため、周期直前を撮影した。録画の2秒間隔抽出も、最初は意図した0秒・2秒と抽出位置がずれることがあり、30fpsのフレーム番号を使う `select='not(mod(n,60))'` に変更した。

音声同期はCoreAudioの実再生時計でも検証し、補正後の最初の拍への入力差8.712ms、判定線換算2.962pxでPerfectになった。ただし、これはエンジンとドライバの時計を使った照合であり、スピーカー出力とディスプレイ表示を外部機器で測った遅延ではない。

終了は通常の終了通知と `--quit-after` の両方を検査した。Godotログは全文をWARNING / ERROR / リーク文言で検索し、末尾だけを見て成功判定しなかった。CIのllvmpipeが出す既定除外のV-Sync警告は、ゲームのエラーやリークと区別して記録した。

最後にputsへ25画像・2動画をアップロードし、27の公開URLをcurlでGETしてSHA-256が元ファイルと一致することまで確認した。アップロード成功だけでPRの証拠掲載を完了扱いにしなかった。

## 6. Godot固有のハマりどころと回避策

- **音声位置は単純なフレーム時間で代用しない。** `get_playback_position() + get_time_since_last_mix() - get_output_latency()` を基準にした。ミックス境界で小さく逆行する時刻はState側で抑制し、同じ補正後の時刻を表示と判定に使った。
- **Webの音声再生方式を揃える。** BGMの `playback_type` を `AudioServer.PLAYBACK_TYPE_STREAM` にし、Webでも音声位置を読む設計と合わせた。
- **演出の停止で音楽を止めない。** リズムゲームで音声やゲーム時計を止めると次のノーツとの同期が崩れる。今回は奏者の姿勢だけに停止感を持たせ、譜面と音声は進めた。
- **拍に同期する踊りと判定への反応を分ける。** AnimationPlayerのframeトラックと位置・回転・伸縮のトラックを併用し、踊りは音声の拍からseek、命中・ミス・祝福は独立した反応として再生した。
- **InputMapの既定操作との衝突を確認する。** `ui_cancel` の既定パッドBが演奏操作と重なった。Escape/Startへ明示的に割り当て直した。
- **入力イベントの処理済み指定はGUIにも影響する。** 長押しの解放対応で、追跡していないマウス解放まで消費するとボタンが反応しなくなる。追跡している入力源だけを解放・消費し、GUIへ渡すべきイベントは残した。
- **音声停止とリソース解放には待ち時間が必要だった。** 通常終了は停止・stream解放後に0.2秒待ち、フレーム指定終了では `_exit_tree` でも回収を待った。Movie Makerでは末尾15フレームを解放区間にした。通常終了だけ成功しても `--quit-after` の確認は省略できない。
- **インポートのexit 0だけでは不十分。** sandboxではログやeditor_settingsの書き込み先が範囲外になり、exit 0でもERRORが出た。self-contained配置と絶対パスの `--log-file` を使い、ログ全文で確認した。描画・CoreAudioへの接続はheadlessと分けて検証した。
- **一時ファイルをGodotのインポート対象にしない。** tmpやbuildに `.gdignore` を置き、エクスポートには必要なJSON・クレジット・OFLを含め、検証用スクリプトや一時出力を除外した。
- **計測名がログ検査に一致することがある。** 正常な計測欄の `error_ms` がERROR検索に一致した。検査を緩めず、計測名を `deviation_ms` に変更した。
- **WebGL起動と画面取得の失敗を分ける。** webtunnelでは `--software-webgl` を付け、Godotの起動表示が消えたことと実画面を確認した。CDPの撮影が止まった際は、HTTP応答だけで描画成功とも失敗とも結論せず、標準プレビューを確認した。新しいセッションでは同じコードの撮影が成功し、根本原因をゲーム側の不具合とは断定していない。
- **Webのcanvasとゲームの座標は一致するとは限らない。** runnerのビューポートは1280×656で、ゲームは1280×720。クリックにはcanvasの矩形・スケール・余白からの変換が必要になる。最終のメニュー操作は主にキーボードで行った。

音声時計の設計で参照したGodot公式資料:

https://docs.godotengine.org/en/stable/tutorials/audio/sync_with_audio.html
